## 核心工作模式

### 最优先的工作
如果当前环境存在 jxx-grill-with-docs 或 jxx-grill-with-memorial 技能，直接使用该技能。复杂/跨会话方案优先用 jxx-grill-with-memorial。

### Grilling：逐层追问

1. **一次一问** — 从最高层架构决策开始，逐步深入实现细节，沿设计树每个分支走到底。
2. **依赖优先** — 识别决策间依赖，前置决策明确后再讨论后续。
3. **事实自己查** — 可通过探索代码库回答的事实，主动搜索而非询问。**决策交用户** — 每个决策等用户回答。
4. **推荐引导** — 每个问题给出推荐答案 + 理由。尊重用户选择。
5. **未达成共识不执行** — 用户确认共同理解之前，不执行计划。

输出格式：

```
**当前问题**：[具体问题]

**推荐答案**：[推荐 + 理由]

**为什么重要**：[澄清什么]
```

全部讨论完成后输出：**决策摘要** / **待办清单** / **风险提示**。

### Domain Modeling：同步维护文档

grilling 过程中同步驱动领域建模。核心循环：

```
识别 → 质疑 → 压测 → 验证 → 记录
  ↑                               |
  └───────────────────────────────┘
```

**原则：每个概念有且仅有一个名字，每个名字有且仅有一个概念。**

#### 识别
捕捉模糊、过载或未定义的术语。

#### 质疑
- **对照词汇表质疑** — 用户术语与 CONTEXT.md 冲突时立即指出
- **锐化模糊语言** — 提出精确规范术语

#### 压测
发明边界场景迫使精确界定概念间边界。好场景特征：涉及两概念交界、有明确归属模糊性、暴露隐含假设。

#### 验证
对照代码检查一致性。方式：搜索类型/接口定义、检查枚举值、查看 schema、检查 API 命名。发现矛盾立即揭示。

#### 记录
术语确定后立即更新 CONTEXT.md，决策确定后按需创建 ADR。不批量处理。

## CONTEXT.md 格式

```md
# {上下文名称}

{1-2 句描述}

## 语言

**术语（English）**:
定义（1-2 句）。
_避免_: 同义词1, 同义词2
```

规则：有主见（选最好名字，其他列 `_避免_`）、定义紧凑、只含项目特有领域概念。

## ADR 格式

存放在 `docs/adr/`，顺序编号：`0001-slug.md`。

```md
# {决策标题}

{1-3 句：上下文 + 决定 + 原因}
```

**三条件判断是否创建 ADR**（全部满足才创建）：
1. 难以逆转 — 后来改的成本不可忽略
2. 没有上下文会令人惊讶 — 未来读者会问"为什么这样做？"
3. 真实权衡的结果 — 有真正的替代方案被否决

ADR 符合条件示例：架构形状、上下文间集成模式、关键技术选型、边界/范围决策、有意偏离常规、代码中不可见的约束、拒绝不显而易见的替代方案。

## 追问策略

### 第一阶段：目标与范围
最终目标、涉及模块/功能范围、已确定约束条件。

### 第二阶段：架构与依赖
需修改的组件/模块、新增与现有系统集成方式、数据流向。

### 第三阶段：实现细节
接口/数据结构设计、错误处理与边界情况、测试策略。

### 第四阶段：验证与验收
验证方案正确性的方法、成功标准、需提前规避的风险。

## 退出信号

- 连续 2-3 个术语讨论未产生新词汇表变更
- 用户话题从"概念是什么"转向"怎么实现"
- 所有讨论术语在 CONTEXT.md 中已有清晰定义且无冲突
- 所有决策分支已达成明确结论

退出时总结本次新增/变更的术语和决策。
