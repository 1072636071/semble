# 通用敏感信息泄露分析指导（语言无关）

> 目的：为面向任意编程语言的静态/代码审计或人工检视提供统一的敏感信息泄露判断框架与证据模板。**仅作分析与判定指引，不包含任何修复或缓解建议。**

---

## 能力目标

* 基于敏感信息生命周期与数据流，判断是否存在真实的泄露风险并定位可达的泄露点。
* 提供可复现的证据链（代码/文本位置 → 数据流 → 暴露面 → 可利用性）。
* 区分合理/合规的数据处理与可能的滥用或误用导致的泄露。
* 适配不同语言与运行时（但不依赖语言特性做判断）。

---

## 前置收集项（必须先确认）

* **敏感信息类型**：凭证（password/secret/token）、密钥、个人信息（PII）、配置/连接信息、调试/堆栈信息、支付信息等。
* **产生/来源点**：用户输入、配置文件、环境变量、第三方返回、测试数据、构建/CI 输出等。
* **存储位置**：文件系统（持久/临时）、数据库、缓存、日志、内存、快照/备份、云存储、提交历史。
* **传输途径**：HTTP/HTTPS/Socket/消息队列/命令行/环境变量/IPC/外部进程调用。
* **生命周期阶段**：生成 → 使用 → 转换（编码/序列化）→ 存储/传输 → 清理/删除。
* **访问控制与可见性**：谁能访问（本地用户、远程用户、第三方服务、运维），审计/权限设置。
* **上下文环境**：开发/测试/生产、CI/CD、容器化、云托管、备份策略。

---

## 分析流程（通用步骤）

1. **识别敏感源（Sources）**

   * 列出所有可能产生或包含敏感数据的位置（配置、输入、第三方响应、文件、环境等）。

2. **静态指纹查找**

   * 搜索敏感关键词、模式（如 `password`, `secret`, `api_key`, 长 base64/jwt-like 字符串、信用卡正则等），并记录文本上下文与位置（文件/行/资源）。

3. **正向数据流追踪（从源到汇聚点）**

   * 跟踪从敏感源到输出（日志、网络、文件、外部命令、UI、第三方）的一切路径，标注中间的序列化/编码/格式化节点。

4. **反向追踪（从可疑输出回溯源）**

   * 从日志条目、错误响应、外部记录（访问日志、监控、备份样本）回溯可能的源头，验证是否与代码位置匹配。

5. **跨边界/跨系统追踪**

   * 识别是否跨进程、跨容器、跨网络或由第三方库/服务传播；标注边界（IPC、命令行、环境变量、HTTP、消息队列）。

6. **转换与持久化分析**

   * 记录所有对敏感数据的转换（拼接、格式化、序列化、编码、日志化），并评估转换后数据是否仍包含可识别/可利用的信息。

7. **可达性与可利用性评估**

   * 判断暴露点是否能被攻击者/未授权方访问、攻击者能否利用该暴露点来获取有用信息（证据要写清楚“如何获取/在哪可见”）。

8. **证据链构建**

   * 将“代码位置/文本片段 → 数据流路径 → 暴露点（哪里/如何可见） → 利用场景（简单说明攻击者如何获得）”组成清晰链条。

9. **不确定性与假设标注**

   * 明确哪些判断是基于可观察事实，哪些依赖假设（例如“假设部署在生产且日志未脱敏”），并列出需要的额外验证点（例如运行时配置、日志权限、网络可达性）。

## 风险模式分类（通用条目 + 轻量案例说明）

> 每一类都给出触发条件与简短示例（示例为文本/配置/日志片段，避免语言绑定）。

### A. 错误/异常信息包含敏感信息

**触发条件**：错误或异常消息包含连接串、堆栈、内部路径或明文凭证，且这些输出可见给外部或写入日志。
**示例（日志/控制台）**：

```
Error: DB connect failed: postgresql://admin:passw0rd@db.internal:5432/appdb
Stack: NullPointer at com.example.Service.process(...)
```

### B. 调试/测试残留凭证或输出

**触发条件**：开发/测试时硬编码凭证、注释中包含真实密钥，或测试输出打印真实凭证并提交到版本库或包中。
**示例（配置/注释）**：

```
# TODO remove before release: api_key=sk_live_ABCDEF123456
```

### C. 日志记录含敏感字段或完整请求体

**触发条件**：日志记录了未脱敏的请求/响应或用户输入（含 password、token、card_number 等）。
**示例（日志行）**：

```
INFO Received request: {"user":"alice","password":"P@ssw0rd!"}
```

### D. 源代码/仓库中硬编码或提交的敏感信息

**触发条件**：配置文件、示例或常量包含真实凭证，或凭证出现在提交历史/PR中。
**示例（.env / config）**：

```
API_KEY=live_sk_9f3a... (committed in repo)
```

### E. 存储或传输前未被适当处理（明文/可逆编码）

**触发条件**：敏感信息以明文或仅被可逆编码（例：Base64）存储或通过非加密通道传输。
**示例（网络/存储）**：

```
Request POST http://api.example.com/pay with body: {"card":"4111111111111111"}
```

### F. 使用后未清理（内存/临时文件/缓存/备份）

**触发条件**：敏感数据在内存中、临时文件、缓存或备份中长期存在且可被访问或包含在核心转储/快照中。
**示例（系统观察）**：

* `/tmp/payment.tmp` 包含明文卡号。
* 备份文件 `backup.sql` 包含 `INSERT INTO users (username,password) VALUES ('u','plainpass')`。

### G. 通过进程/命令行/环境变量泄露

**触发条件**：凭证通过命令行参数或环境变量传递到子进程/外部工具，并可能出现在进程列表或环境快照中。
**示例（命令/ps 输出）**：

```
mysqldump -u root -pMySecretPass ...   # 可被 ps 查看到
```

### H. 第三方库/服务意外记录或透传敏感数据

**触发条件**：依赖的组件将请求/响应或内部状态记录到自身日志或回传到第三方，包含敏感字段。
**示例（第三方日志）**：

```
3rd-party-lib: outgoing request body {"token":"eyJhbGciOi..."} logged
```

### I. URL/Referer/Query 中包含凭证或令牌

**触发条件**：敏感令牌被放在 query string、Referer 或可被日志化的地址中。
**示例（访问日志）**：

```
GET /callback?token=eyJhbGciOiJI...  — logged in access.log
```

### J. 媒体/截图/监控暴露敏感信息

**触发条件**：UI 截图、监控录像、演示材料或错误截图包含敏感值并被共享。
**示例**：会议共享的截图显示开发者控制台内的 `api_key=...`。

## 分析视角与检查点（通用）

* **数据流分析**：源→中间处理→输出（逐步列出每一步的处理函数/模块/服务与数据格式转换）。
* **可达性检查**：谁/什么进程/网络路径可见该输出（本地运维、远端攻击者、第三方服务）。
* **可利用性评估**：攻击者是否能利用暴露的信息（短期/长期有效性、是否可链式利用）。
* **持久化与残留**：是否写入磁盘、备份、缓存、日志、快照或提交历史。
* **运行时差异**：开发 vs 生产差异（配置、日志级别、调试开关）。
* **最小必要性**：记录输出是否超出调试或业务必须范围（记录的字段是否合理）。
* **复杂转换识别**：编码（Base64、Hex）、压缩、加密（判断是否真正加密或仅编码）、序列化（是否将敏感字段包含在可读文本中）。
* **第三方链路**：识别外发到第三方的所有内容与日志策略。
* **证据完整性**：保存可复核的片段（文件名/行号/日志时间戳/请求 id 等）。

## 严重性判断要点（用于标注高/中/低）

* **高**：敏感信息以明文或可直接识别形式暴露在外部可访问位置（公网日志、访问日志、备份、命令行、错误响应等）。
* **中**：敏感信息在内部系统或受限位置暴露，但可通过常见操作或权限提升被访问。
* **低**：敏感信息仅存在于受控/受限环境，且有明显保护或短期有效性；但仍需关注误配置或权限变化带来的风险。

（当做出严重性判断时，必须在结论中列出影响面、可利用路径与假设。）

```
## 结论
[问题存在/问题不确定/未发现] + 严重性: 高/中/低

## 敏感信息与泄露点
- 敏感信息类型: [...]
- 产生位置: [文件/路径:行号] / [服务/模块]
- 泄露点: [日志/网络/文件/命令行/第三方/...]
- 可见性: [谁能看到/访问条件]
- 生命周期位置: [传输/存储/残留等]

## 证据链与推理
1. 代码/文本证据：摘录（文件:行号）或日志片段（包含时间戳/请求id）
2. 数据流追踪：源 → 中间节点（格式化/序列化）→ 输出位置（行号/日志/文件）
3. 可达性证明：说明如何访问该输出（本地/远程/第三方）
4. 利用可行性：简述攻击者可如何获得并利用该信息（仅说明链，不给 remediation）
5. 假设与不确定性：列出未验证但影响判断的项（例如“假设生产启用了 debug 日志”）
```

## 典型误报（不应报告为漏洞的场景）

* 使用托管密钥管理系统/机密存储且能证明访问控制和审计存在。
* 配置文件仅包含占位符或示例（明确标注为示例/placeholder）。
* 日志条目已被脱敏/掩码（例如 `password=***`）且能证明脱敏规则有效。
* 使用一次性/已吊销/测试凭证且可证实无生产影响。
* 敏感字段仅出现在本地开发环境且不可对外访问（并且日志级别/配置有明显区分）。
* 明确的业务合理共享（有合规证明或合同/审计记录支撑）。

## 检测/告警词典（便于规则化）

> 作为审计时可优先抽查的关键词/模式（仅用于定位，不绝对判定）

* 关键词：`password`, `passwd`, `pwd`, `secret`, `token`, `api_key`, `access_key`, `private_key`, `client_secret`, `ssn`, `credit_card`, `card_number`, `cvv`
* 模式：长 Base64/JWT-like 字符串（`^[A-Za-z0-9-_]{80,}$` 类似）、连接串模式（`://.*:.*@`）、信用卡号简单正则（注意误报）
* 输出载体：`Set-Cookie:`, `Authorization:`, `Bearer `, `password=`, `pwd=`, `key=`, `token=`
