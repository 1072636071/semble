## 能力目标

基于数据流和上下文分析，判断真实注入风险，识别可达的注入点，区分合法操作和恶意注入。适用于所有编程语言的通用注入分析策略。

---

## 前置判断

获取：
- **输入来源**: 用户输入/网络数据/文件内容/环境变量/数据库/外部API
- **输入类型**: 字符串/结构化数据(JSON/XML)/命令参数/URL路径/二进制数据
- **数据流路径**: 从输入到执行点的完整传递链
- **处理机制**: 是否有输入验证、过滤、转义、编码、类型转换
- **执行上下文**: 注入点所处的执行环境(命令行/数据库/标记语言/模板引擎/日志系统)
- **语言特性**: 该语言的类型系统、字符串处理、安全API
- **框架防护**: 是否使用ORM、模板引擎、参数化API等安全抽象层

---

## 分析流程

### Step 1 — 识别疑似注入点
定位可能的注入执行点：
- **命令执行**: 系统调用、进程启动、脚本执行
- **查询语言**: 数据库查询、搜索表达式、查询DSL
- **标记语言处理**: HTML/XML/JSON/YAML解析和生成
- **表达式求值**: 动态代码执行、模板渲染、表达式引擎
- **日志和输出**: 日志记录、错误消息、响应头
- **文件和资源**: 文件路径操作、URL构建、资源定位

### Step 2 — 追踪污点数据流
- **正向追踪**: 从用户输入到所有可能的影响点
- **反向追踪**: 从注入点回溯数据来源
- **跨边界追踪**: 函数调用、模块导入、网络传输中的数据流
- **数据转换链**: 识别数据传递过程中的转换、编码、验证操作
- **污点消失点**: 消毒函数、强类型转换、白名单验证

### Step 3 — 验证防护机制
- **输入验证**: 
  - 白名单验证(类型、格式、长度、字符集)
  - 黑名单过滤(特殊字符、危险模式)
  - 业务逻辑约束
- **输出处理**:
  - 上下文感知编码(HTML/XML/URL/Shell/SQL转义)
  - 参数化API(预编译语句、参数绑定)
  - 模板引擎自动转义
- **权限和隔离**:
  - 最小权限原则
  - 沙箱执行环境
  - 资源访问控制
- **框架级防护**:
  - ORM自动参数化
  - CSP(内容安全策略)
  - 安全配置和特性标志

### Step 4 — 判断真实风险
- **可达性**: 注入点是否可被外部输入触发
- **可控性**: 攻击者能否完全或部分控制注入的payload
- **语法有效性**: 注入内容在目标上下文中的可执行性
- **影响范围**: 成功注入后的潜在危害程度

## 风险模式分类

### 模式1: 命令注入
应用程序将不受信任的数据传递给系统命令解释器执行。

**触发条件**:
- 字符串拼接构建系统命令
- 未对Shell元字符进行转义或验证
- 通过环境变量或参数传递用户输入
- 使用不安全的命令执行API

**分析方法**:
1. 识别所有系统调用、进程启动函数
2. 追踪命令字符串的构建过程
3. 检查是否使用参数化执行方式(参数数组而非字符串)
4. 验证输入白名单或元字符过滤

**典型漏洞模式**:
```
# 危险模式：直接拼接
execute_command("process_file " + user_filename)

# 安全模式：参数化或白名单
if is_valid_filename(user_filename):
    execute_with_args(["process_file", user_filename])
```

**防护措施**:
- 优先使用参数化API(参数数组)而非字符串拼接
- 实施严格的输入白名单验证
- 转义或移除Shell元字符: `| & ; $ ( ) < > \` \n \t * ? [ ]`
- 最小化执行权限，使用受限环境

---

### 模式2: 跨站脚本(XSS)
应用程序将不受信任的数据插入到网页中，未经适当的转义或验证。

**触发条件**:
- 用户输入直接插入HTML文档
- 动态DOM操作使用未转义内容
- JavaScript字符串拼接用户输入
- 输出上下文编码不正确

**分析方法**:
1. 追踪用户输入到HTML/JavaScript输出的路径
2. 识别输出上下文(HTML内容、属性、脚本、样式、URL)
3. 检查模板引擎的转义配置
4. 验证上下文感知编码的使用

**典型漏洞模式**:
```
# 危险模式：未转义输出
render_html("<div>" + user_input + "</div>")

# 安全模式：使用转义或安全API
render_html("<div>" + html_escape(user_input) + "</div>")
# 或使用模板引擎的自动转义
```

**防护措施**:
- 使用模板引擎的自动转义功能
- 根据输出上下文选择正确的编码方式
- 实施内容安全策略(CSP)
- 对富文本使用白名单过滤器

---

### 模式3: 标记语言注入(XML/JSON)
应用程序将不受信任数据插入结构化数据格式，未进行适当的编码。

**触发条件**:
- 字符串拼接构建XML/JSON
- 未转义特殊字符(< > & ' " 等)
- 不安全的解析器配置
- 允许外部实体或扩展

**分析方法**:
1. 识别结构化数据的构建和输出位置
2. 检查是否使用字符串拼接而非API构建
3. 验证特殊字符的转义处理
4. 检查解析器的安全配置(禁用外部实体)

**典型漏洞模式**:
```
# 危险模式：字符串拼接
xml_string = "<user>" + username + "</user>"
json_string = '{"name":"' + user_name + '"}'

# 安全模式：使用API构建
xml_element = create_element("user", username)
json_object = encode_json({"name": user_name})
```

**防护措施**:
- 使用标准库或框架API构建结构化数据
- 对插入内容进行适当编码
- 禁用XML外部实体(XXE防护)
- 限制数据大小和嵌套深度(XEE防护)

---

### 模式4: 查询语言注入(SQL/NoSQL/LDAP等)
应用程序将不受信任数据拼接到查询语句中，可能导致数据泄露或篡改。

**触发条件**:
- 字符串拼接构建查询语句
- 动态查询构建未使用参数化
- 未对查询元字符进行转义
- ORM使用不当(如原始查询)

**分析方法**:
1. 识别所有查询语句的构建位置
2. 检查是否使用参数化查询或预编译语句
3. 验证用户输入是否参与查询拼接
4. 评估ORM或查询构建器的安全使用

**典型漏洞模式**:
```
# 危险模式：字符串拼接
query = "SELECT * FROM users WHERE name='" + username + "'"

# 安全模式：参数化查询
query = prepare_statement("SELECT * FROM users WHERE name=?")
query.bind_param(username)
```

**防护措施**:
- 始终使用参数化查询或预编译语句
- 使用ORM的参数化方法
- 实施输入验证和类型检查
- 最小化数据库账户权限
- 避免在存储过程中动态拼接SQL

---

### 模式5: 表达式注入
应用程序允许执行不受信任的代码或表达式，可能导致任意代码执行。

**触发条件**:
- 使用动态代码执行函数(eval类函数)
- 不安全的反序列化
- 模板引擎允许代码执行
- 表达式引擎未限制功能

**分析方法**:
1. 识别所有动态代码执行点
2. 检查反序列化操作的数据源验证
3. 验证模板引擎和表达式引擎的安全配置
4. 评估代码执行的必要性

**典型漏洞模式**:
```
# 危险模式：动态执行
evaluate_expression(user_input)
deserialize_object(untrusted_data)

# 安全模式：限制功能或使用安全替代
# 使用受限的表达式引擎
safe_evaluator.evaluate(user_input, allowed_functions)
# 或验证反序列化数据
if verify_signature(data):
    deserialize_object(data)
```

**防护措施**:
- 避免使用动态代码执行函数
- 使用安全的模板引擎(仅支持数据绑定)
- 反序列化前验证数据源和完整性
- 使用白名单限制可调用的函数或类
- 在沙箱环境中执行不受信任的代码

---

### 模式6: 路径遍历和资源注入
应用程序允许不受信任数据指定系统资源位置，可能导致未授权访问。

**触发条件**:
- 用户输入直接用作文件路径
- 路径拼接未进行规范化
- 未验证路径是否在允许范围内
- URL或网络地址未验证(SSRF风险)

**分析方法**:
1. 识别所有资源访问操作(文件、URL、网络)
2. 检查用户输入如何影响资源路径
3. 验证路径规范化和边界检查
4. 检查是否限制可访问的资源范围

**典型漏洞模式**:
```
# 危险模式：路径遍历
file_path = base_directory + user_filename  # 可能包含 ../
content = read_file(file_path)

# 危险模式：SSRF
response = fetch_url(user_provided_url)

# 安全模式：路径验证
normalized_path = normalize_path(base_directory + user_filename)
if is_within_directory(normalized_path, base_directory):
    content = read_file(normalized_path)
```

**防护措施**:
- 规范化路径并验证其在允许范围内
- 使用白名单限制可访问的文件或目录
- 对URL进行域名白名单和内网IP检查
- 避免直接使用用户输入作为资源标识符

---

### 模式7: 日志注入
应用程序将不受信任数据直接写入日志，未转义控制字符。

**触发条件**:
- 用户输入直接记录到日志
- 未转义换行符和控制字符
- 日志格式可被注入内容破坏
- 日志用于监控或审计时被篡改

**分析方法**:
1. 识别所有日志记录调用
2. 检查用户输入是否直接写入
3. 验证控制字符的转义或移除
4. 考虑日志的后续解析和使用方式

**典型漏洞模式**:
```
# 危险模式：直接记录
log("User login: " + username)
# username = "admin\nSUCCESS: Privilege escalation" 会伪造日志

# 安全模式：规范化或转义
log("User login: " + sanitize_for_log(username))
# 或使用结构化日志
log_structured({"event": "login", "user": username})
```

**防护措施**:
- 转义或移除控制字符(\r \n \t等)
- 使用结构化日志格式(JSON)
- 对敏感信息脱敏处理
- 限制日志文件的访问权限

---

### 模式8: HTTP头注入(CRLF注入)
应用程序将不受信任数据插入HTTP响应头，未过滤换行符。

**触发条件**:
- 用户输入用于设置响应头
- 未过滤CR(\\r)和LF(\\n)字符
- 重定向URL未验证
- Cookie值未转义

**分析方法**:
1. 检查所有HTTP响应头的设置位置
2. 追踪响应头值的构建过程
3. 验证是否过滤CRLF字符
4. 检查HTTP库的安全使用

**典型漏洞模式**:
```
# 危险模式：未过滤换行符
set_header("Location", user_redirect_url)
# user_redirect_url = "http://evil.com\r\nSet-Cookie: session=hijacked"

# 安全模式：验证和过滤
safe_url = remove_crlf(user_redirect_url)
if is_valid_url(safe_url):
    set_header("Location", safe_url)
```

**防护措施**:
- 移除或转义所有CR(\\r)和LF(\\n)字符
- 对响应头值进行严格验证
- 使用HTTP库的安全API
- 验证重定向URL的合法性

---

### 模式9: 服务器端请求伪造(SSRF)
应用程序根据用户输入发起服务器端请求，可能访问内部资源。

**触发条件**:
- 用户输入用作URL或主机名
- 未验证目标地址是否为内部IP
- 允许访问云元数据服务
- 未限制可访问的协议或端口

**分析方法**:
1. 识别所有服务器端HTTP请求
2. 检查URL或主机名的来源
3. 验证是否有IP白名单或黑名单
4. 检查DNS重绑定防护

**典型漏洞模式**:
```
# 危险模式：未验证URL
response = http_get(user_provided_url)
# user_provided_url = "http://169.254.169.254/metadata" (云元数据)

# 安全模式：URL验证
if is_allowed_domain(user_provided_url) and not is_internal_ip(user_provided_url):
    response = http_get(user_provided_url)
```

**防护措施**:
- 实施URL白名单验证
- 检查并拒绝内部IP地址(10.x, 172.16-31.x, 192.168.x, 127.x)
- 阻止访问云元数据服务(169.254.169.254)
- 限制允许的协议(http/https)和端口
- 使用DNS重绑定防护

## 代码分析视角

### 污点分析框架
1. **污点源识别**:
   - 用户输入: 表单数据、URL参数、请求头、Cookie
   - 外部数据: 文件内容、数据库查询结果、API响应
   - 环境数据: 环境变量、配置文件、命令行参数

2. **污点传播追踪**:
   - 直接传播: 变量赋值、参数传递
   - 间接传播: 字符串拼接、数组操作、对象属性
   - 跨边界传播: 函数调用、模块导入、网络通信

3. **污点汇聚检测**:
   - 命令执行点: 系统调用、进程启动
   - 查询执行点: 数据库查询、文件操作
   - 渲染输出点: HTML生成、模板渲染
   - 日志记录点: 日志函数、错误处理

4. **污点消毒识别**:
   - 验证函数: 白名单检查、格式验证
   - 编码函数: HTML转义、URL编码、SQL转义
   - 类型转换: 强类型约束、类型断言
   - 过滤函数: 黑名单过滤、内容清理

### 上下文感知分析
1. **输出上下文识别**:
   - HTML上下文: 内容、属性、脚本、样式、URL
   - 查询上下文: SQL、NoSQL、LDAP、XPath
   - 命令上下文: Shell、系统API、脚本解释器
   - 日志上下文: 文本日志、结构化日志

2. **编码需求判断**:
   - HTML实体编码: < > & " '
   - URL编码: % + ? & =
   - JavaScript编码: \\ ' " 控制字符
   - SQL转义: ' " \ 特定于数据库
   - Shell转义: 根据Shell类型

3. **语法有效性验证**:
   - 注入内容是否在目标语法中有效
   - 是否能突破当前上下文
   - 是否能执行恶意操作

### 数据流分析策略
1. **正向数据流**:
   ```
   用户输入 → 变量赋值 → 函数参数 → 字符串拼接 → 危险函数
   ```

2. **反向数据流**:
   ```
   危险函数 ← 参数来源 ← 数据转换 ← 输入点
   ```

3. **跨函数追踪**:
   - 函数参数传递
   - 返回值使用
   - 全局变量共享
   - 闭包捕获

4. **跨模块追踪**:
   - 导入导出
   - 模块间调用
   - 共享状态

## 典型触发条件总结

| 注入类型 | 核心触发条件 | 关键检测点 |
|---------|-------------|-----------|
| 命令注入 | 字符串拼接 + 系统调用 | Shell元字符、参数化API |
| XSS注入 | 未转义输出 + HTML渲染 | 输出上下文、转义函数 |
| SQL注入 | 字符串拼接 + 查询执行 | 参数化查询、ORM使用 |
| XML/JSON注入 | 字符串拼接 + 解析 | API构建、特殊字符 |
| 表达式注入 | 动态执行 + 用户输入 | eval函数、反序列化 |
| 路径遍历 | 路径拼接 + 文件操作 | 路径规范化、边界检查 |
| SSRF | URL拼接 + HTTP请求 | IP验证、域名白名单 |
| 日志注入 | 直接记录 + 控制字符 | CRLF过滤、结构化日志 |
| CRLF注入 | 响应头设置 + 换行符 | CRLF过滤、头验证 |

## 案例分析示例

### 案例1: 命令注入 - 文件处理器

**场景描述**:
一个文件处理应用允许用户指定文件名进行压缩操作。

**代码片段**:
```
function compress_file(user_filename):
    command = "compress --output=/tmp/compressed " + user_filename
    execute_system_command(command)
```

**数据流分析**:
1. 污点源: `user_filename` (用户输入)
2. 污点传播: 字符串拼接到 `command`
3. 污点汇聚: `execute_system_command()` 执行点
4. 污点消毒: **无**

**漏洞分析**:
- **注入点**: `execute_system_command(command)`
- **输入来源**: 用户提供的文件名
- **攻击向量**: `; rm -rf / #` 或 `| cat /etc/passwd`
- **缺失防护**: 未验证文件名格式，未转义Shell元字符

**触发条件**:
```
user_filename = "file.txt; malicious_command #"
# 执行结果: compress --output=/tmp/compressed file.txt; malicious_command #
```

**风险评估**:
- 可达性: 高(直接接受用户输入)
- 可控性: 高(完全控制注入内容)
- 影响范围: 高(任意命令执行)

**修复方案**:
```
function compress_file(user_filename):
    # 方案1: 白名单验证
    if not is_valid_filename(user_filename):
        raise ValidationError("Invalid filename")
    
    # 方案2: 参数化执行
    execute_with_parameters(["compress", "--output=/tmp/compressed", user_filename])
```

### 案例2: XSS注入 - 用户评论显示

**场景描述**:
一个评论系统直接显示用户提交的评论内容。

**代码片段**:
```
function display_comment(comment_text):
    html = "<div class='comment'>" + comment_text + "</div>"
    render_html(html)
```

**数据流分析**:
1. 污点源: `comment_text` (用户输入)
2. 污点传播: 字符串拼接到 `html`
3. 污点汇聚: `render_html()` 输出点
4. 污点消毒: **无**

**漏洞分析**:
- **注入点**: HTML渲染
- **输出上下文**: HTML内容
- **攻击向量**: `<script>malicious_code()</script>`
- **缺失防护**: 未进行HTML实体编码

**触发条件**:
```
comment_text = "<img src=x onerror='alert(document.cookie)'>"
# 渲染结果: 执行JavaScript窃取Cookie
```

**风险评估**:
- 可达性: 高(评论系统公开可用)
- 可控性: 高(完全控制注入内容)
- 影响范围: 中(会话劫持、钓鱼攻击)

**修复方案**:
```
function display_comment(comment_text):
```

### 案例3: 路径遍历 - 文件下载

**场景描述**:
一个文件下载功能允许用户指定文件名。

**代码片段**:
```
function download_file(requested_file):
    file_path = "/app/public/" + requested_file
    content = read_file(file_path)
    return content
```

**数据流分析**:
1. 污点源: `requested_file` (用户输入)
2. 污点传播: 字符串拼接到 `file_path`
3. 污点汇聚: `read_file()` 文件操作
4. 污点消毒: **无**

**漏洞分析**:
- **注入点**: 文件系统访问
- **攻击向量**: `../../etc/passwd`
- **缺失防护**: 未规范化路径，未验证边界

**触发条件**:
```
requested_file = "../../etc/passwd"
# 实际路径: /app/public/../../etc/passwd → /etc/passwd
```

**风险评估**:
- 可达性: 高(公开的下载接口)
- 可控性: 高(可指定任意路径)
- 影响范围: 高(读取敏感文件)

**修复方案**:
```
function download_file(requested_file):
    # 规范化并验证路径
    base_dir = "/app/public/"
    full_path = normalize_path(base_dir + requested_file)
    
    # 验证路径在允许范围内
    if not full_path.starts_with(base_dir):
        raise SecurityError("Path traversal attempt")
    
    content = read_file(full_path)
    return content
```

## 典型误报场景

**不应报告为注入漏洞的情况**:

1. **正确使用安全API**:
   - 参数化查询或预编译语句
   - 使用数组参数的命令执行
   - 模板引擎的自动转义

2. **严格的输入验证**:
   - 白名单验证通过的输入
   - 强类型约束(如整数ID)
   - 格式化验证(如正则表达式匹配)

3. **框架自动防护**:
   - ORM的自动参数化
   - 模板引擎的默认转义
   - HTTP库的自动编码

4. **内部数据流**:
   - 常量或配置文件的值
   - 不可被外部影响的内部变量
   - 已验证的可信数据源

5. **上下文安全的使用**:
   - 经过适当编码后的输出
   - 使用安全库处理后的数据
   - 限制在安全沙箱中的操作

6. **业务逻辑约束**:
   - 需要身份认证的内部功能
   - 权限限制下的操作
   - 业务规则已确保安全的场景
