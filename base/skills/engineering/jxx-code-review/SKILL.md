审查 `HEAD` 与用户指定固定点（fixed point）之间的 diff。**审查维度数由执行模式决定**：

- **委托模式**（检测到 `ocr` CLI）— **3 个维度**：标准 + spec + **规则**。
- **内置模式**（未检测到 `ocr`，降级路径）— **2 个维度**：标准 + spec。

各维度的含义：

- **标准** — 代码是否符合仓库文档中记录的编码标准？
- **spec** — 代码是否忠实实现了原始 issue / PRD / spec？
- **规则**（仅委托模式）— 代码是否违反 OCR 为该文件解析出的规则组？即 OCR 内置的多语言规则集（NPE、线程安全、XSS、SQL 注入、依赖与配置等）。

各维度作为**并行子 agent** 运行，上下文互不污染，然后本技能汇总它们的发现。

Issue 跟踪器应已配置好 — 若 `docs/agents/issue-tracker.md` 缺失，运行 `/jxx-setup-skills`。

## 流程

### 0. 选择执行模式

本技能有两种执行模式，**按当前环境是否安装 `ocr` CLI 自动选择**：

| 模式 | 触发条件 | 审查维度 | 分工 |
| --- | --- | --- | --- |
| **委托模式** | 检测到 `ocr` | **3 维度**：标准 + spec + **规则** | OCR 负责确定性工程（文件筛选、规则解析、范围判定）；**宿主 Agent（即运行本技能的 harness）用自身 LLM 能力执行实际代码审查**。OCR 端**不需要任何 LLM 配置**。 |
| **内置模式**（降级） | 未检测到 `ocr` | **2 维度**：标准 + spec | 沿用本技能原有的双轴并行子 agent 流程（步骤 1–5），无「规则」维度。 |

**只检测一次**：直接运行二进制自证存在 —— 这是跨 shell 唯一不会写错的探针（无重定向、无 `which`/`where`/`command -v` 的 bash↔PowerShell 差异）。

```bash
ocr --version
```

（PowerShell 中同样直接 `ocr --version`，语法一致，无需改写。）

- 打印出版本号（如 `open-code-review v1.12.4 ...`）→ **先跑步骤 0b**，再走**委托模式**（下方 D1–D5），完成后直接跳到步骤 6「更新工单状态」。
- 报「command not found」/「不是内部或外部命令」/「无法将 ocr 项识别为 cmdlet」或非零退出 → **先明确告知用户**「未检测到 ocr，已降级为内置模式」，**先跑步骤 0b**，再走**内置模式**（步骤 1–5），然后步骤 6。

> **切勿**把探测写成 `where ocr 2>$null; command -v ocr 2>$null` 这类混写（曾在真实运行中出现）。
> bash 下 `$null` 展开为空 → `ambiguous redirect`，命令不执行 → 零输出 → 误降级；
> PowerShell 下 `where` 是 `Where-Object` 别名（不搜 PATH）、`command -v` 不存在 → 同样零输出。
> 直接 `ocr --version` 判存在，绕开以上全部陷阱。

用户可显式指定 `--mode delegate` 或 `--mode builtin` 覆盖自动选择。

### 0b. 外部契约取证（固定动作 · 两种模式共用，不可跳过）

放在两条模式流程之前（紧随步骤 0），因为委托模式（D1–D5）与内置模式都要跑它；若把它嵌进其中一条流程，按另一条流程线性执行的会话会整段漏跑。

**触发**：diff 里的代码消费了不在本仓的契约——HTTP/RPC 接口、消息/文件格式、DB schema、路由与字段名，或由另一仓库/另一分支维护的服务端行为（典型：前端与 MCP 面在主仓，服务端契约真源在 fork 仓的 `fork/<卡id>` 分支）。

**取证坐标的出处**：工单正文或工单卡「外部契约」节写的 `仓库 + 分支 + SHA + 文件:行`。两种失败都要报，不要互相冒充：
- 该节**留空**而实现明显消费了外部接口 → 发现项「契约坐标缺失」（spec 维度，Medium 以上）；
- 该节**已给坐标** → 按下条取证，坐标本身错了（分支不存在、行号对不上）同样按发现项报告。
- 卡上**根本没有该节**（该卡早于模板加节的版本）→ 视同留空判：只按「实现是否消费外部接口」裁定，**不因缺节本身打回**。

**动作**：到真源取证。**不得**凭本仓内的命名、注释、测试桩或 PRD 表格反推契约成立。

- 只读取证：`git -C <对方仓根> show <SHA>:<路径>`（基线钉 SHA，别写 `HEAD`/分支名——对方分支会被推进或 rebase，写 `HEAD` 的证据合入即失效）。跨分支搜索带**子目录限定**：`git -C <对方仓根> grep <pattern> <SHA> -- <子目录>`；裸 `grep <pattern> <分支>` 会命中 swagger 注释一类声明文本，正是下面要防的误名来源。**禁止** checkout 对方分支、禁止改对方工作树。
- 报告里为每条契约断言写全取证坐标：仓 + 分支 + commit SHA + `文件:行`，以及被对照的本仓断言位置（`文件:行`）。
- 接口名/路径以对方**注册点**自证（如路由注册文件、真实响应结构体），别把 MCP 工具名、PRD 表名或 handler 函数名当成 REST 路径——这是已知误名来源。
- 可选字段声明（`field?` / `?:`）是失真掩体：证到实际响应形状（构造点或契约测试）才算闭合。
- 取不到真源（分支不存在、无读权限、本地未 fetch 到该分支）→ 在 **spec** 维度按 Medium 以上发现项报告，标「契约未取证」，**不得默认通过**。

### 0c. 验收点逐条判定（两种模式共用，不可跳过）

紧随 0b，同一理由：不嵌进任一条模式流程，否则按另一条流程线性执行的会话会整段漏跑。验收点的权威规范 = `../jxx-to-tickets/references/acceptance-criteria.md`（§五 判定表、§四 劣化门禁），**本处只给动作，不复制规范正文**。

0. **先跑机械闸**：`node <jxx-to-tickets 技能目录>/scripts/ac-audit.mjs <工单文件或功能目录>`——报告里的硬问题（编号断号 / 缺类别 / 缺载荷验证方式 / 类别不足 / 缺回归或负向）一律计入发现项，严重度**中**（形式缺陷，不算功能缺失）。
1. **定位 AC 源**：① diff 内 commit 消息的工单 / PRD 引用 → ② 用户给定路径 → ③ `.scratch/` 下与卡 id / 分支名匹配的工单文件。取工单里的 `- [ ] AC-<n> [<类别>]` 行全集。
2. **逐条判定**：每条 AC 输出 `met` / `partial` / `missing` + **审查者自己取的证据**（命令 + 输出摘要，或 `文件:行`）。**严禁**引用执行者的勾选框、自述、「处理步骤」打卡——那是被审对象，不是证据（质量宪章一、三：审查与执行各自独立取证）。
3. `partial` = 只实现一半 / 只在主路径成立 / 靠硬编码或桩通过；`missing` = 找不到实现与用例。**两者一律发现项，功能缺失按 High**。
4. **假实现检测**：AC 勾了但代码是桩、硬编码、`TODO`、空实现 ⇒ High，**单独成条**（别并进 partial 稀释）。
5. **无 AC 可核对**（工单找不到、或工单无验收段）：报告首行写「未审：无验收点可核对」，并注明这属**生产侧缺陷**（回 `jxx-to-spec` / `jxx-to-tickets` 补 AC），**不得静默通过**（质量宪章二：举证责任在提出方）。

**劣化门禁（与逐条判定同批跑；每项给「通过 / 发现项 + 取证命令」）**：判据 = 规范 §四五条，此处只列**本技能的取证命令**。

| 项 | 命令（空输出 / 一致 = 通过） |
| --- | --- |
| 回归 | 仓库全量测试命令（如 `pnpm test`），贴末行汇总——不是只跑新增用例 |
| 公共符号 | `git diff <fixed-point>...HEAD -U0 \| grep -nE -e '^-[^-].*[[:space:]]export[[:space:]]' -e '^-[^-].*[[:space:]]interface[[:space:]]'` → 有输出逐行核对签名，确需变更的须在工单声明 |
| 断言放宽 | `git diff <fixed-point>...HEAD \| grep -nE -e '\.skip\(' -e '\.todo\(' -e '\.only\(' -e 'as any' -e '[A-Za-z0-9_)]!\.' -e 'timeout'` → 空输出 = 通过 |
| 依赖 | `git diff <fixed-point>...HEAD -- '*lock*' package.json` → 空 = 通过 |
| 行为基线 | `git worktree add ../base-<fixed-point> <fixed-point>` 后在两个工作树各跑工单点明的命令，`diff` 两份输出 → 无差异 = 通过；跑完 `git worktree remove ../base-<fixed-point>` |

任一项为发现项 ⇒ 按 **High** 报：劣化正是「测试仍全绿却弄坏既有」的形态（规范 §四）。

### 委托模式（ocr 可用时启用）— D1–D5

委托模式专为订阅制 AI 编码代理设计（Claude Code、Codex、Cursor、Open Code、Qoder 等）—— 这些工具已内置 LLM 订阅额度，委托模式直接复用宿主 Agent 的额度做审查，**无需额外配置模型或 API Key**。适用于：

- 你的 AI 编码代理是订阅制，希望复用已有额度审查 —— 无需 API Key 或模型端点。
- 你只需要 OCR 的工程脚手架 —— 文件过滤、规则解析、排除逻辑 —— 由宿主 Agent 负责全部 LLM 推理。
- 你在构建自定义 Agent 流水线，需要结构化输入（文件列表 + 规则）喂给自己的审查步骤。

**前置条件**：只需安装 `ocr` CLI（`which ocr || npm install -g @alibaba-group/open-code-review`）。**无需配置 LLM** —— 委托模式在 OCR 端不调用任何 LLM，因此不需要 `ocr config set` 或任何 LLM 环境变量。

#### D1. 确定审查范围

```bash
ocr delegate preview [--from <ref> --to <ref>] [--commit <hash>] [--exclude <patterns>]
```

输出：`mode`（workspace / range / commit）、ref 元数据（from、to、commit、merge_base）、可审查文件列表（路径、状态、增删行数）、已排除文件及排除原因。

| 场景 | 命令 |
| --- | --- |
| 工作区变更 | `ocr delegate preview` |
| 分支对比 | `ocr delegate preview --from main --to feature` |
| 单次提交 | `ocr delegate preview -c abc123` |

用户若给了固定点（commit / branch / tag），用 `--from <fixed-point> --to HEAD` 或 `-c <commit>`，与内置模式语义对齐。加 `-f json` 得到机器可读输出。

#### D2. 获取文件规则

```bash
ocr delegate rule <path1> <path2> ...
```

传入 D1 输出的可审查文件路径。输出**按规则内容分组** —— 共享相同规则的文件归为一组，避免重复。

#### D3. 获取 diff

按 D1 的 `mode` 与 ref 元数据，用 git 直接获取：

- **Range 模式**（有 `merge_base`）：`git diff <merge_base>..<to> -- <path>`
- **Commit 模式**：`git show <commit> -- <path>`
- **Workspace 模式**：`git diff HEAD -- <path>`（已跟踪文件）；`cat <path>`（未跟踪新文件）

#### D4. 审查每个文件

对每个可审查文件：取它的 diff（D3），由**宿主 Agent 用自身 LLM** 按下方三个维度并行深入审查，按需探索上下文。

委托模式在内置 2 维度之上**新增「规则」维度**，共 **3 个维度**并行（上下文互不污染）：

1. **标准维度** — 仓库记录的编码标准 + 代码异味基线（基线全文见步骤 3，来源判定同步骤 3）。
2. **spec 维度** — 原始 issue / PRD / spec（来源判定见步骤 2；消费外部契约时按步骤 0b 取证）。**必须输出逐 AC 判定表**（列：AC 编号 / 类别 / 判定 / 证据），判定与劣化门禁按步骤 0c 执行——spec 维度不用「看起来实现了」结案。
3. **规则维度**（委托模式新增）— D2 输出的该文件所属规则组。OCR 按规则内容把文件分组、同组共享一份规则；逐条对照该规则检查 diff。

「规则」维度是 OCR 的工程产出 —— **没有 `ocr` 时该维度不存在**，因此内置模式只有 2 个维度（标准 + spec）。

#### D5. 报告

按严重程度分类：

- **Critical / High** — Bug、安全问题、数据丢失风险。**始终报告。**
- **Medium** — 性能问题、错误处理缺失。附带上下文报告。
- **Low** — 风格建议、细微改进。**静默丢弃**，除非确有价值。

每个发现给出：文件 + 行号（或代码块）、**所属维度（标准 / spec / 规则）**、依据（引用的仓库标准、spec 行，或 OCR 规则条目）、严重程度。

汇总时按三个维度分节呈现（`## 标准` / `## spec` / `## 规则`），**不要**合并或跨维度重新排序（理由见「为什么分维度」）。

`## AC 覆盖` 小节排在这三个维度节**之前**（格式见步骤 5）——它是「功能有没有做到」的机械面，丢在各维度叙述里就没人能核。

**委托模式通用标志**

| 标志 | 描述 |
| --- | --- |
| `--from <ref>` | Range 模式源引用 |
| `--to <ref>` | Range 模式目标引用 |
| `-c, --commit <hash>` | 单次提交模式（别名 `d`：`ocr d preview`） |
| `--repo <path>` | 仓库根目录（默认 cwd） |
| `--rule <path>` | 自定义 rule.json 路径 |
| `--exclude <patterns>` | 逗号分隔排除模式（与 rule.json 的 exclude 合并） |
| `-f, --format` | text / json（委托模式**不支持** sarif） |
| `-b, --background <text>` | 业务上下文 |
| `-B, --background-file <path>` | 从 Markdown 读取业务上下文（优先于 `-b`） |

### 内置模式（ocr 不可用时降级）— 步骤 1–5

### 1. 确定固定点

用户指定的任何固定点 — commit SHA、branch 名、tag、`main`、`HEAD~5` 等。若用户未指定，则询问。

只执行一次 diff 命令：`git diff <fixed-point>...HEAD`（三点语法，比较 merge-base）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录 commit 列表。

继续前确认固定点可解析（`git rev-parse <fixed-point>`）且 diff 非空。无效引用或空 diff 应在此处中止 — 而非在两个并行子 agent 内部。

**diff 持久化**：将 diff 输出写入当前项目的 `/.temp/` 目录，文件名格式 `code-review-<YYYYMMDD-HHmmss>.diff`。`/.temp/` 目录若不存在则创建。子 agent 通过读取该文件获取 diff，避免在提示中传递大量 diff 文本。

### 2. 识别 spec 来源

按以下顺序查找原始 spec：

1. commit 消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）— 通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下匹配 branch 名或功能的 PRD/spec 文件。
4. 若均未找到，询问用户 spec 位置。若用户表示没有，**spec** 子 agent 跳过并报告"无可用 spec"。

### 3. 识别标准来源

搜索仓库中所有记录代码编写规范的文件。`CODING_STANDARDS.md` 与 `CONTRIBUTING.md` 若存在，必须列入标准来源清单。

除仓库文档外，标准轴始终携带以下**代码异味基线** — 一组固定的 Fowler 代码异味（《重构》第 3 章），即使仓库无文档也适用。两条规则约束它：

- **仓库优先。** 仓库记录的标准始终优先；当仓库认可了基线会标记的内容时，抑制该异味。
- **始终是酌情判断。** 每个异味是启发式标记（"可能的特性嫉妒"），绝非硬性违规 — 与此处的任何标准一样，跳过工具已强制执行的内容。

每个异味的格式为*它是什么* → _如何修复_；与 diff 匹配：

- **Mysterious Name（神秘命名）** — 函数、变量或类型的名称无法揭示其功能或内容。→ 重命名；若找不到贴切的名字，说明设计意图模糊。
- **Duplicated Code（重复代码）** — 相同的逻辑结构出现在本次变更中的多个代码块或文件中。→ 提取共享逻辑，从两处调用。
- **Feature Envy（特性嫉妒）** — 方法更多地访问另一个对象的数据而非自身数据。→ 将方法移到它嫉妒的数据所属的对象上。
- **Data Clumps（数据泥团）** — 相同的几个字段或参数总是一起出现（一个等待诞生的类型）。→ 将它们打包为一个类型，传递该类型。
- **Primitive Obsession（原始类型偏执）** — 用原始类型或字符串代替值得拥有独立类型的领域概念。→ 给概念自己的小类型。
- **Repeated Switches（重复 switch）** — 相同的 `switch`/`if` 级联在同一类型上于本次变更范围内反复出现。→ 用多态替换，或让两处调用点共享一个 map。
- **Shotgun Surgery（散弹式修改）** — 一个逻辑变更迫使在 diff 中的多个文件中散布编辑。→ 将一起变更的内容聚合到一个模块中。
- **Divergent Change（发散式变更）** — 一个文件或模块因多个不相关的原因被编辑。→ 拆分，使每个模块只因一个原因变更。
- **Speculative Generality（投机性泛化）** — 为 spec 中不存在的需求添加的抽象、参数或 hooks。→ 删除；内联回去直到有真实需求出现。
- **Message Chains（消息链）** — 长的 `a.b().c().d()` 导航，调用者不应依赖。→ 在第一个对象上用一个方法隐藏遍历。
- **Middle Man（中间人）** — 主要只是转发委托的类或函数。→ 删除它，直接调用真实目标。
- **Refused Bequest（被拒绝的遗赠）** — 忽略或覆盖大部分继承内容的子类或实现者。→ 放弃继承，使用组合。

### 4. 并行启动两个子 agent

用你所在 harness 的子 agent 机制并行派发两者——harness 支持时，在一条消息中发出两个调用。两者都选用最通用的 agent 类型：每个子 agent 都必须能读文件、跑 `git`，只能搜索的 agent 太窄。

**标准子 agent 提示** — 包含：

- diff 文件路径（`/.temp/code-review-<timestamp>.diff`），子 agent 自行读取。
- commit 列表。
- 步骤 3 中找到的标准源文件列表，**加上步骤 3 的异味基线全文粘贴** — 子 agent 没有其他途径访问它。
- 简报："读取 diff 文件，按文件/hunk（代码块，在相关处）报告：(a) diff 中违反已记录标准的每一处：引用标准（文件 + 规则）；(b) 发现的任何基线异味：命名并引用代码块。区分硬性违规和酌情判断 — 已记录标准违规可以是硬性的，但基线异味始终是酌情判断，仓库已记录标准优先于基线。跳过工具已强制执行的内容。400 words / 400 词以内。"

**spec 子 agent 提示** — 包含：

- diff 文件路径（`/.temp/code-review-<timestamp>.diff`），子 agent 自行读取。
- commit 列表。
- spec 的路径或已获取的内容。
- 步骤 0b 的取证坐标（仓 + 分支 + SHA + `文件:行`）——若本变更消费了外部契约，必须随提示下发，并要求子 agent 逐条核对「本仓断言 ↔ 对方真源实现」；缺取证的契约断言按发现项报告。
- 步骤 0c 的要求：**输出逐 AC 判定表**，列 `AC 编号 / 类别 / 判定 / 证据`；判定只取 `met` / `partial` / `missing`，证据必须是自己跑出的命令 + 输出摘要或 `文件:行`，**不得**引用执行者的勾选与自述；`partial` / `missing` 一律发现项（功能缺失 High）。无 AC 可核对时首行写「未审：无验收点可核对」并注明属生产侧缺陷。
- 简报："读取 diff 文件，报告：(a) 逐 AC 判定表（按上面要求）；(b) spec 要求但缺失或不完整的需求；(c) diff 中未被要求的行为（scope creep / 范围蔓延）；(d) 看似已实现但实现看起来有误的需求。为每个发现引用 spec 行。400 words / 400 词以内。"

若 spec 缺失，跳过 spec 子 agent 并在最终报告中注明。

### 5. 汇总

先给 `## AC 覆盖` 小节（两种模式都出，不可省），再在 `## 标准` 和 `## spec` 标题下呈现报告（委托模式再加 `## 规则`），逐字或轻度整理。**不要**合并或重新排序发现 — 各维度刻意分离（见*为什么分维度*）。

`## AC 覆盖` 的格式：

| AC 编号 | 类别 | 判定 | 证据坐标 |
| --- | --- | --- | --- |
| AC-1 | 主路径 | met | `pnpm test tests/list.test.ts::pagination` → 3 passed |
| AC-5 | 错误路径 | missing | `git grep -n 'InvalidCursor' -- src/` → 无命中 |

表下一行统计：`met N · partial N · missing N`。无 AC 可核对时本小节只写「未审：无验收点可核对」+ 生产侧缺陷说明（步骤 0c 第 5 条）。

以一行总结结尾：每个维度的发现总数，以及每个维度内最严重的问题（如有）。不要跨维度选出一个最严重问题 — 那正是分离所防止的重新排序。

### 6. 更新工单状态

若本审查针对某个实现型工单（工单 `Status:` 为 `pending-review` 待审查）：

- **置 `done` 的前置**：`## AC 覆盖` 表**非空**且无 `partial` / `missing`。无 AC 可核对时必须报「未审」，不得放行。有任一条 `partial` / `missing` 即不得置 `done`，先返工重审（`missing` 属功能缺失，不许用「用户认可」跳过）。
- **审查者只复核与报告，不代置 `done`**：本步骤产出结论（通过 / 发现项 + AC 覆盖表），`Status:` 由执行者在审查通过后置（`/jxx-implement` 完成步骤第三节）。
- 审查**有发现项且用户选择修复**时，工单保持在 `pending-review`，待修复并重新审查通过后由执行者置 `done`。

**服务器对齐（v1.2.0 起默认；v1.4.0 起走写腿）**：项目已接入服务器工单（repo_key 在 `jxx_tickets` 中出现）时，状态置变不再手改 md 再推——项目内有 `tools/ticket-flow.mjs` 且工单在 `.scratch/<NN>-<slug>/` 下时，一条写腿命令完成「改本地 md + 推服务器」：`node tools/ticket-flow.mjs --root <仓库根> --file <单条工单md> --set status=<本地词表> [--comment "<审查结论 / 返工要求>"]`。exit 0 收敛；exit 2 = 评论撞上「服务器版本已前进」，按条目自带 `server`/`local`/`resolution` 裁决后重跑；exit 3 = 本地已还原或未变（`rolled_back:true` = 已回滚），按错误文案处置。**项目没有该 CLI 时回退 MCP 双写**：先改本地 md → `get` 拿最新 `version` 作 `base_version` → `jxx_ticket_call update`（409 先对账再推，不盲目重试；工具面见项目内 `agents/skills/jxx-ticket-router/SKILL.md`，项目技能、`read` 加载）。服务器不可达时只写本地（离线降级），回连后 `jxx_ticket_sync` 收口。

工单状态流转见 `docs/agents/issue-tracker.md` 的「工单状态与生命周期」节。

## 为什么分维度（2 或 3）

一个变更可能通过某些维度而未通过另一些：

- 代码遵循了每个标准但实现了错误的东西 → **标准通过，spec 失败。**
- 代码完全按照 issue 要求做了但违反了项目约定 → **spec 通过，标准失败。**
- 代码满足了需求与项目约定，却引入了 NPE / SQL 注入 / 线程安全等具体缺陷 → **标准与 spec 通过，规则失败。**

分开报告防止一个维度掩盖另一个。

第三个「规则」维度**仅在委托模式下存在** —— 它把 OCR 解析出的具体规则作为独立清单，避免这类可定位的缺陷被前两个维度的讨论淹没。没有 `ocr` 时该维度缺失，审查降级为 2 维度，仍然有效，只是少了一层自动规则覆盖。
