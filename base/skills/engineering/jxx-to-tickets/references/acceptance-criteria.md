# 验收点规范（Acceptance Criteria）

**地位：验收点的唯一权威源。** 生产工单（`jxx-to-spec` / `jxx-to-tickets`）、执行工单（`jxx-implement` / `jxx-implement-spec`）、审查工单（`jxx-code-review`）、看板终审（`jxx-ticket-board`）四处**引用**本文件，**不复制**内容——复制必漂移。质量铁律见 `docs/agents/quality-charter.md`。

## 为什么

LLM 实现有三类失效，全部源于「验收点没写清」：

| 失效 | 机制 | 下游症状 |
|---|---|---|
| **少做** | 需求只散在 PRD 正文，没落成验收点 | 实现时看不见 → 漏功能，或只做主路径 |
| **假做** | 验收点写成「支持 X / 实现 X 功能」 | 写个桩、硬编码就能勾上 |
| **劣化** | 工单只说「加 X」，没说「别弄坏 Y」 | 顺手改公共行为、放宽断言，测试仍全绿 |

验收点是唯一**实现前可评审、实现后可机械核对**的载体。写不满，后面四道工序全部放空。

## 一 · 覆盖清单（生产工单时逐类过）

对每张工单**逐类**扫描，每类二选一：产出 ≥1 条 AC，或在 `**AC 覆盖声明：**` 块里逐条写 `- <类别>：不适用——<理由>`（脚本按这个格式逐类解析，写在别处不算）。既不写 AC 也不声明不适用 = 缺项，**不得发布**。

| # | 类别 | 何时必须写 | 写法要点 |
|---|---|---|---|
| 1 | 主路径 | 总是 | 每个用户可见动作 ≥1 条 |
| 2 | 空态 | 有列表 / 查询 / 可选数据 | 零条数据时返回什么、界面显示什么 |
| 3 | 边界值 | 有数量、长度、时间、分页、金额 | 0、1、最大、越界各一条 |
| 4 | 错误路径 | 每个可能失败的外部调用 / 非法输入 | 每个失败面一条；含超时、不可达、非法参数 |
| 5 | 权限与鉴权 | 有身份、角色、资源归属 | 越权被拒（状态码 + 错误码），不只写「有权限校验」 |
| 6 | 状态转移 | 有实体状态机 | 合法转移逐条 + 非法转移被拒 |
| 7 | 并发与幂等 | 写操作、重试、回调、按钮 | 重复提交只生效一次；并发两次的最终状态 |
| 8 | 持久化与恢复 | 落库、落盘、队列、缓存 | 半途失败不留脏数据；重启后状态可读 |
| 9 | 兼容与迁移 | 改 schema、改接口、改配置键 | 旧数据 / 旧调用方 / 旧配置仍可用 |
| 10 | 性能与时延 | 有列表、批量、循环、外部调用 | 给定规模与阈值（1000 条 < 300ms），不是「优化性能」 |
| 11 | 安全 | 有鉴权、输入、日志、导出 | 注入被拒 / 敏感字段不落日志、不明文回显 / 越权读不到 |
| 12 | 回归 | **改代码的工单必须写** | 点明本单触及的既有行为「保持原样」 |
| 13 | 负向 | **改代码的工单必须写** | 明确禁止出现的行为（新增依赖、改签名、吞异常、放宽校验） |
| 14 | 可观测性 | 有错误码、审计、日志要求 | 错误码 / 日志行 / 审计记录的精确取值 |

**覆盖矩阵**：PRD 每条用户故事必须映射 ≥1 条 AC。矩阵写在 `.scratch/<NN>-<slug>/map.md` 的 `## AC 覆盖矩阵` 节（用户故事编号 ↔ 工单编号 ↔ AC 编号）。任一用户故事无 AC ⇒ 漏项，工单未发布。

## 二 · 单条 AC 的写法

格式（机械可解析，脚本依赖它）：

```
- [ ] AC-<n> [<类别>] 当 <前置条件 / 输入> 时，<动作>，则 <可观测结果> —— 验证:机器 <用例名|命令>
- [ ] AC-<n> [<类别>] 当 <前置条件 / 输入> 时，<动作>，则 <可观测结果> —— 验证:人工 <HUMAN-CHECK 第 n 条>
```

铁律：

1. **一条 AC 一个断言。** 出现「并且 / 以及 / 同时」串起两个可独立失败的要求 ⇒ 拆条。拆不动的，说明这是两条需求。
2. **结果必须可观测**：退出码 / 用例名 / 响应字段与取值 / 文件内容 / 日志行 / 状态名 / UI 元素。不落在这些上的不算 AC。
3. **禁词**（出现即缺陷）：正确、正常、合理、良好、完整、友好、稳定、健壮、优化、改进、完善、支持、兼容、等等、若干、适当、尽可能、必要时、按需。
   - 判的是断言正文，**类别标签不参与检查**（`[兼容与迁移]` 合法）；
   - 「支持 X」「兼容 Y」这类**肯定式短语**判缺陷——写成「调用 X 时返回 Y」；「不支持 X 时返回 400」是合法断言。
4. **照抄真源**：数字、错误码、字段名、路由、状态名、表名列名，逐字取自 spec / 接口文档 / 相邻工单，不许同义改写（改写后审查无从核对）。
5. **验证方式必须带载荷**：`验证:机器 <用例名或命令>` / `验证:人工 <HUMAN-CHECK 条目>`，光写「验证:机器」不算（脚本按 `验证:机器` 后必须跟非空内容判）。二选一的理由见质量宪章二：说不清为什么不能程序断言的，一律按机器验。
6. **AC 编号工单内唯一、从 1 连续**，跨工单不复用——打卡、审查、返工都靠它定位。开工后的「**AC 勾选区：**」是引用打卡，允许与原编号重复（脚本不重复计）。

## 三 · 防少做（漏实现）

- AC 是工单的**验收闭包**：实现时逐条勾选并附证据，未逐条闭环不得置 `done`（详见 `jxx-implement` 完成步骤）。
- 反模式（判为不合格）：
  - 只写主路径——最典型的漏：错误路径、边界、权限、空态全缺；
  - 「实现 X 功能」「接入 Y」「优化 Z」当 AC——无断言，勾选无意义；
  - AC 条数少于用户故事数——必漏；
  - 一条 AC 里塞 5 个行为——只要一个没做，其余四个也会被勾成完成。

## 四 · 防劣化（弄坏既有）

改代码的工单**必须同时**含 `[回归]` 与 `[负向]` AC——缺任一类，验收就不防劣化（脚本按 AND 判）。

- 回归 AC 例：`当跑既有全量测试时，全部通过`；`GET /api/a 的响应仍含字段 b，类型不变`；`配置键 old_key 仍被识别（缺省回退）`。
- 负向 AC 例：`本次 diff 不得新增第三方依赖`；`公共函数 f 的签名不得改变`；`不得新增 skip / only / as any / ! 断言绕过`；`不得捕获后吞掉异常而不记录`。

**劣化门禁**（实现者与审查者**各自独立跑**，不采信对方结论；判据 = 五条，命令见各技能）：

1. 既有全量测试全绿——不是只跑新增用例；
2. 公共符号 diff：无未声明的删除与签名变更（导出函数 / 接口 / 配置键 / 错误码）；
3. 断言放宽扫描：diff 内无新增 `skip` / `todo` / `only` / `as any` / `!` / 放宽的阈值与超时；
4. 依赖与配置：lock 文件无未授权新增；
5. 行为基线：工单点明的命令 / 接口，改动前后输出一致。

## 五 · 审查判定（机械，逐条）

对每条 AC 输出三选一 + **自己取的证据**（命令 + 输出摘要，不引用执行者文本）：

| 判定 | 含义 | 处理 |
|---|---|---|
| `met` | 自己跑过，结果符合 | 记证据坐标 |
| `partial` | 只实现一半 / 只在主路径成立 / 靠硬编码或桩通过 | 发现项，功能缺失按 **High** |
| `missing` | 完全没实现 / 找不到对应代码与用例 | 发现项，**High** |

- 「AC 勾了但代码是桩、硬编码、TODO、空实现」⇒ **假实现**，High，单独成条。
- 覆盖声明写「不适用」而审查认为适用 ⇒ 发现项（生产侧漏项）。
- 审查不得因「AC 太模糊无法判定」而放过——模糊本身即发现项，回退给生产侧。
- 无 AC 可核对（工单缺失 / 无验收段）⇒ 报「未审」，**不得放行**（质量宪章二）。

## 六 · 反模式速查（照抄即错）

| 错写法 | 为什么错 | 改成 |
|---|---|---|
| `- [ ] 支持分页` | 无断言，桩也能过 | `AC-3 [主路径] 当 page_size=20 请求列表时，返回 ≤20 条且 total 为全量条数 —— 验证:机器 tests/list.test.ts::pagination` |
| `- [ ] 错误处理正确` | 禁词 + 无具体失败面 | 逐个失败面各一条，带状态码与错误码 |
| `- [ ] 实现登录功能` | 需求复述，非验收 | 按覆盖清单拆出主路径 / 空态 / 边界 / 错误 / 权限 |
| `- [ ] 不破坏现有功能` | 无法核对 | `AC-7 [回归] 当跑 pnpm test 时，既有 132 个用例全部通过 —— 验证:机器 pnpm test` |
| `- [ ] 性能优化` | 无基线、无阈值 | `当 1000 条数据列表时，响应 < 300ms —— 验证:机器 bench/list.bench.ts` |
| `- [ ] 代码质量良好` | 不可判定 | 删除；质量由审查维度负责，不进 AC |
| 一条 AC 写 5 个行为 | 部分完成也全勾 | 拆成 5 条 |
| 只写「成功后返回 200」 | 漏负向与失败分支 | 补 401 / 403 / 400 / 404 / 500 各自一条 |

## 七 · 机械校验

```bash
node <jxx-to-tickets 技能目录>/scripts/ac-audit.mjs <工单目录或文件>       # 人读报告
node <jxx-to-tickets 技能目录>/scripts/ac-audit.mjs <目录> --strict      # 额外校验覆盖矩阵
```

**查**：AC 编号连续唯一（勾选区不计）、每条带类别与带载荷的验证方式、禁词命中、类别覆盖 ≥3 类、`[回归]` 与 `[负向]` 两类齐备（或按格式声明不适用）、`map.md` 覆盖矩阵存在且行内出现 AC 编号；`--strict` 另查 `## 覆盖闸` 节（见 §八）——节存在、每行判定取 §8.2 四种之一、未处置 `gap` 行数为 0。

**退出码**：`0` 过 · `1` 有硬问题 · `2` 没有工单类文件（PRD 阶段纯用户故事、AC 全交给工单层时的预期 defer）· `3` 用法错误或路径不存在。调用方（`jxx-to-spec` 生产闸）只能把 `2` 当 defer，`3` 一律视为调用错误。

**特殊处理**（都是「不为难合法写法、也不给违规留后门」）：

- 文件名 `PRD.md`：验收点按草案对待——覆盖类与标注类问题降为软问题；但 PRD 已有验收点节却零 AC 行 = 硬问题（新 PRD 必须给草案）。
- `**AC 勾选区：**` 之下的 AC 行是开工引用打卡：不参与编号唯一性与类别统计，只查「是否已勾选 + 是否附证据」。
- 跳过 `reviews/`、`.jxx-tickets/` 目录与 `map.md` / `MILESTONES.md` / `HUMAN-CHECK.md`——审查报告里的 AC 行不算工单；`.jxx-tickets/` 是服务器投影（pull 覆盖写入），不是创作面，AC 只在源 md 补。

**脚本只查形式，判内容仍是人或审查 agent 的事。**

## 八 · 覆盖闸（生产后自检：诉求 / 决策 / PRD 全覆盖）

§七 的脚本查**形式**，覆盖闸查**漏没漏**。工单写完、发布之前，生成者回头把三样东西逐条对到工单的 AC 上；对不上就补工单或补 AC，**不得改判**。这是「少做」与「降低标准」的唯一出口——形式全绿的工单仍可能漏掉用户说过的一句话。

### 8.1 三个源，分开枚举

| 源 | 取处 | 粒度 |
|---|---|---|
| 用户诉求 | 本次对话里用户的原始表述：初始请求、追问中追加的要求、纠正与抱怨 | 一条诉求一行，**原文摘录**，不改写 |
| 决策 | 讨论中敲定的取舍、ADR、`CONTEXT.md`、既有决策文档；**明确不做的事同样是一行**（反向诉求） | 一个决策一行 |
| PRD | `.scratch/<NN>-<slug>/PRD.md`：每条用户故事 + 每条约束 / 非功能 / 边界 / 明确排除项 | 按条目逐行，不按章节概括 |

三源分开，**不许合并去重**：同一件事出现在两个源里是两份证据，合并就丢了一份。

源为空写空，不编造：没有 PRD（直接从对话拆单）⇒ PRD 源不出现；本次没有敲定任何取舍 ⇒ 决策源不出现。诉求源永远在——一张工单也要过闸。

### 8.2 每条一个判定，只有四种

| 判定 | 成立条件 | 必须填 |
|---|---|---|
| `covered` | 某张工单的某条 AC **独立关闭**这一条 | 工单编号 + AC 编号 |
| `gap→已补` | 初检是缺口，已补工单或补 AC | 补后的工单 + AC；评论留「补了什么」 |
| `rejected` | 用户明确表示不做 | 用户确认原话 + 轮次 |
| `defer` | 明确划到后续里程碑或另一份 PRD | 去向文件 / 里程碑编号 |

- **「独立关闭」**＝只做这条 AC，这一条就算做完了。只**相关**、只覆盖主路径、只是前置条件，一律判 `gap`。
- 没有第五种判定。`隐含覆盖`、`由他条代表`、`实现时会自然有` 都不是判定，写进表里即判不合格。
- `rejected` 只能由用户给——生产者自判「不做」⇒ 不合格；`defer` 无去向 ⇒ 无效，按 `gap` 计。

### 8.3 落盘：`map.md` 的 `## 覆盖闸` 节

```md
## 覆盖闸

| 源 | 条目（原文摘录） | 工单 | AC | 判定 |
|---|---|---|---|---|
| 诉求 | 「导出要能选时间范围」 | 03 | AC-2 | covered |
| 决策 | 「不做增量导出，只做全量」 | — | — | rejected（用户第 4 轮确认） |
| PRD | 用户故事 2：用户可撤销上一次导入 | 04 | AC-1 | gap→已补 |
```

- PRD 源的行**就是** §一 覆盖矩阵的行：矩阵已齐则原样搬来，不写第二份；矩阵缺则在此补齐（`--strict` 两处都查）。
- 原文摘录是防作弊锚：摘录与诉求对不上，一眼能看出来。

### 8.4 防降低标准（出现即不合格）

- 把两条诉求并进一条 AC 凑覆盖；
- 把诉求改写成更弱的说法再判 `covered`；
- 用 `**AC 覆盖声明：**` 的「不适用」顶替覆盖判定（那是类别豁免，不是需求覆盖）；
- 缺口靠改判消除，而不是补工单 / 补 AC；
- 覆盖闸全绿却零条 `gap→已补`、且无初检记录——初检没做，按不合格处理。

### 8.5 收口

1. 未处置 `gap` 行数 = 0（每行落在 `covered` / `gap→已补` / 有确认的 `rejected` / 有去向的 `defer`）；
2. 补过工单 ⇒ 重跑 `ac-audit.mjs <功能目录> --strict`，退出码回到 0；
3. gap 清单与补法在发布前给用户过目——自检不能自过：判定由生成者做，`rejected` 只能由用户给。
