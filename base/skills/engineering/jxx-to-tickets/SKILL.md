# 转化工单

将计划、规格文档或对话拆解为一组**工单**——追踪弹式（tracer-bullet）垂直切片（vertical slice），每个声明**阻塞它的**工单。

issue tracker 和 triage 标签词汇表应该已提供给你——如果没有，运行 `/jxx-setup-skills`。

**验收点规则是硬约束**：本技能产出的每张工单，验收标准（AC）必须满足 `references/acceptance-criteria.md`（同目录，随技能分发）——那是验收点的唯一权威源，格式、覆盖清单、禁词、判定口径全在里面。本文件只写怎么落地，不复制规则正文。

## 流程

### 1. 收集上下文

从对话上下文中已有的内容出发。如果用户传入引用（规格文档路径、issue 编号或 URL）作为参数，获取并阅读其完整内容和评论。

### 2. 探索代码库（可选）

若尚未探索代码库，先了解代码当前状态。工单标题和描述应使用项目的领域词汇表，并遵守相关区域的 ADR。

寻找预重构机会以简化实现。"先让变更变容易，再做容易的变更。"

### 3. 起草垂直切片

将工作拆解为**追踪弹**工单。

<vertical-slice-rules>

- 每个切片切出一条狭窄但完整的路径，贯穿每一层（schema、API、UI、测试）——垂直切片，不是单层的水平切片
- 完成的切片可独立演示或验证
- 每个切片的大小适合单个新上下文窗口
- 任何预重构应优先完成

</vertical-slice-rules>

为每个工单设定其**阻塞边**——必须在它之前完成的其他工单。没有阻塞的工单可以立即开始。

<ac-closure-rules>

**每张工单的验收点是闭包，不是摘要**（判据正文只在 `references/acceptance-criteria.md`，此处只留动作）：

- 逐类过覆盖清单（14 类，见规范 §一）；不放 AC 的类写进工单 `**AC 覆盖声明：**` 并给理由。
- 每条 AC 带类别与带载荷的验证方式（`验证:机器 <用例名|命令>` / `验证:人工 <HUMAN-CHECK 条目>`）。
- 改代码的工单**必须**同时有 `[回归]` 与 `[负向]`（规范 §四）。
- AC 编号工单内唯一、从 1 连续，跨工单不复用。
- 覆盖矩阵落 `map.md` 的 `## AC 覆盖矩阵`（规范 §一）。
- **含 UI 的工单**：第 4 步必须问用户「是否需要 agent 代做 UI 验收」。**默认不需要**——UI 类 AC 写成机器可断言形态（组件测试断 DOM / 文案 / 状态、e2e 用例、接口字段），剩下来的体验项落 `.scratch/<NN>-<slug>/HUMAN-CHECK.md` 等真人；agent 不主动开浏览器取证（规范 §二之一）。

</ac-closure-rules>

**广泛重构是垂直切片的例外。** **广泛重构**是一种机械性变更——重命名列、重新类型化共享符号——其**影响半径（blast radius）**遍及整个代码库，单次编辑同时破坏数千个调用点，没有任何垂直切片能保持绿色。不要强塞进追踪弹；按**扩展-收缩（expand-contract）**顺序排列。先扩展：在旧形式旁添加新形式，不破坏任何东西。然后按影响半径分批迁移调用点（按包、按目录），每批是独立工单，阻塞于扩展工单，由于旧形式仍然存在，每批之间 CI 保持绿色。最后收缩：一旦没有调用者剩余，删除旧形式，此工单阻塞于所有迁移批。当连批次都无法单独保持绿色时，保持顺序但让它们共享一个集成分支，它们都阻塞最终的集成验证工单——绿色只在那个工单上承诺。

### 4. 询问用户

以编号列表形式呈现提议的拆解。对每个工单，展示：

- **标题**：简短描述性名称
- **阻塞于**：哪些其他工单（如有）必须先完成
- **交付内容**：此工单使什么端到端行为可用
- **验收点覆盖**：AC 条数、类别分布（哪些类已覆盖、哪些写「不适用 + 理由」）、回归与负向各几条

询问用户：

- 粒度是否合适？（太粗 / 太细）
- 阻塞边是否正确——每个工单是否只依赖于真正阻塞它的工单？
- 是否有工单应合并或进一步拆分？
- 验收点是否够严：每条 AC 能不能被人一眼判成「做了 / 没做」？抽 2–3 条念给用户，问他「这样写，桩能过吗」。
- 覆盖闸有没有空洞：用户说过的话、敲定的决策、PRD 条目，有没有哪条没落到任何 AC？（判据见规范 §八）
- **涉及 UI 的工单：要不要 agent 代做 UI 验收？** 默认不要——agent 不主动开浏览器、不截图取证，UI 体验项进 `HUMAN-CHECK.md` 等真人；你要的话，对应 AC 记 `验证:人工 <HUMAN-CHECK 第 n 条>` 并写明「用户授权 agent 代验」（规范 §二之一）。

迭代直到用户批准拆解。

### 4b. 覆盖闸（发布前硬闸，不可跳）

草稿定稿后、落盘之前，**自己回头核对生成物**有没有完全覆盖三样东西——用户诉求、已敲定决策、PRD。判据、判定取值、落盘格式全在 `references/acceptance-criteria.md` §八，此处只留动作：

- 三源**分开**逐条枚举成行：诉求引用户原话，决策含「明确不做的事」，PRD 按条目（不按章节概括）——写进 `map.md` 的 `## 覆盖闸`；
- 每行四选一：`covered`（填工单 + AC）/ `gap→已补` / `rejected`（须用户确认原话）/ `defer`（须有去向）；
- 判不出的**按 `gap` 处理**：补工单或补 AC，不补判；不得把两条诉求并进一条 AC 凑覆盖，也不得把诉求改写得更弱再判 covered；
- 未处置 gap 归零后，把 gap 清单与补法并入第 4 步的询问，让用户过目（`rejected` 只能由用户给）；
- 补过工单 ⇒ 回到第 5 步重跑 `ac-audit --strict`。

### 5. 将工单发布到本地跟踪器

发布前先跑形式自检（硬闸，不可跳）：

```bash
node <本技能目录>/scripts/ac-audit.mjs "<仓库绝对路径>/.scratch/<NN>-<slug>" --strict
```

退出码非 0 ⇒ 先修工单再发布。它查形式（编号断号 / 缺验证标注 / 类别不足 / 缺回归或负向 / 缺覆盖矩阵 / 缺覆盖闸或存在未处置 gap），内容严不严仍由第 4 步的人点头。

将已批准的工单发布到本地 issue 跟踪器——在仓库根目录的 `.scratch/<NN>-<工作简称-slug>/issues/` 下为每个工单创建独立文件 `<NN>-<slug>.md`（从 `01` 编号，按依赖顺序放置，阻塞者在前）。功能目录的 `<NN>` 为从 `01` 起的全局递增顺序号，按创建先后排列。每个文件顶部附近含 `Status: ready-for-agent` 行（triage 词汇见 `triage-labels.md`）；工单发布后由 `/jxx-implement` 推进至 `pending-review`（待审查）、由 `/jxx-code-review` 推进至 `done`（结束）——完整生命周期见 `docs/agents/issue-tracker.md` 的「工单状态与生命周期」节；阻塞边以 `Blocked by: NN, NN` 文本行表示（列出它依赖的工单编号，无阻塞则写"无——可立即开始"）。评论与对话历史追加到文件底部 `## 评论` 标题下。使用下方本地工单文件模板。

<local-issue-file-template>

# <工单标题>

**Status:** ready-for-agent

**Blocked by:** 01, 02   （列出此工单依赖的工单编号；无阻塞则省略此行，或写"无——可立即开始"）

**构建内容：** 此工单使什么端到端行为可用，从用户视角——不是逐层的实现列表。

**验收标准：**

- [ ] AC-1 [主路径] 当 <输入 / 前置> 时，<动作>，则 <可观测结果> —— 验证:机器 <用例名 | 命令>
- [ ] AC-2 [错误路径] 当 <非法输入 / 失败面> 时，<动作>，则 <状态码 + 错误码> —— 验证:机器 <用例名 | 命令>
- [ ] AC-3 [回归] 当跑既有全量测试时，全部通过 —— 验证:机器 <命令>
- [ ] AC-4 [负向] 本次 diff 不得 <禁止行为：新增依赖 / 改公共签名 / 放宽断言 / 吞异常> —— 验证:机器 <检查命令>

**AC 覆盖声明：**（未产出 AC 的类别逐条写「<类别>：不适用——<理由>」；覆盖清单（14 类，见规范 §一）全覆盖则写「无缺口——14 类已覆盖」）

**处理步骤：**（开工时由 `/jxx-implement` 填写；AC 勾选区紧随其后）

## 评论

（评论与对话历史追加于此，新内容置于最前。）

</local-issue-file-template>

> 本地工单存放于 `.scratch/<NN>-<工作简称-slug>/issues/`，每个工单一个独立文件。目录与文件如不存在则创建。功能目录的 `<NN>` 为从 `01` 起的全局递增顺序号；工单编号从 `01` 起，文件名为 `<NN>-<slug>.md`（例如 `01-add-schema.md`、`02-wire-api.md`）。上下文指针与所做决策可汇总到 `.scratch/<NN>-<工作简称-slug>/map.md`。

### 服务器上行与本地落盘同属发布动作（默认纪律 · v1.3.0，非可选项）

工单本地落盘的**同一步**内必须同步上行服务器工单系统（jxx-ticket）——不存在「先本地、服务器以后再说」：项目已接入服务器工单（repo_key 在 `jxx_tickets` 中出现）时，工单上行是发布动作的一部分，未经上行的工单视为发布未完成。工具面与参数契约见项目内 `agents/skills/jxx-ticket-router/SKILL.md`（项目技能，`read` 加载；项目未提供该文件时以 MCP `tools/list` 自披露 schema 为准），`jxx_ticket_push` / `jxx_ticket_call`；配套 CLI 仓可直接 `node tools/ticket-uplink.mjs --root <仓库根>`，幂等按 repo_key+title 判重：

- **新建（本技能第 5 步的组成部分）**：全部工单落盘后立即批量上行（labels 带 `prd:<NN>-<slug>` 归组；type=ticket、status 按实体状态机映射），把服务器回写的 ticket_no + id + version 记入各工单评论与 PRD 映射表留痕；PRD 本体尚未上行的，同批上行；
- **后续修订（v1.6.0 起走写腿）**：项目内有 `tools/ticket-flow.mjs` 时——**状态 / 标题 / 标签 / 认领**用一条写腿完成「改本地 md + 推服务器」：`node tools/ticket-flow.mjs --root <仓库根> --file <单条工单md> --set status=<本地词表> [--set labels=a,b]`；**打卡 / 评论**附 `--comment "<一句话>"`（写腿不 create、也不改自由正文）；**验收点 / 正文段落修订**改完 md 后跑只读腿 `node tools/ticket-flow.mjs --root <仓库根> --file <单条工单md>` 收敛（内部 get 最新版，`version_conflict` 自动重拉重试一次）。退出码：0 收敛 / 2 评论撞上「服务器版本已前进」按条目 `server`/`local`/`resolution` 裁决后重跑 / 3 本地已还原或未变。**不要先手改状态或标签再手工 update。**项目没有该 CLI 时回退 MCP 双写：`get` 拿最新 `version` 作 `base_version` → `jxx_ticket_call update`（409 冲突先对账再推，不盲目重试）；
- **批量安全**：批量 push 的 id 必须从当次 `list` 实测逐条核对，不得凭表格手抄——串位会把正文写进邻居工单（2026-10-15 实测事故：T131–T135 四条错位，靠标签过滤 `list` + 乐观锁拒绝才发现并修复）；
- **离线降级**：仅当服务器不可达时才允许只写本地，回连后 `jxx_ticket_sync`（给投影根）对账收口；
- **删除**：服务器无 delete——本地删单时服务器对应单走 `update { status: "archived" }` 软删，两侧一致。

### 6. 里程碑交付（可选）

工单发布后，若工单多、改动大、涉及广泛重构或需要分批上线/断点续传，可询问用户是否按里程碑交付——运行 `/jxx-to-milestones`：把工单归组为**可独立上线**的里程碑，生成 `.scratch/<NN>-<工作简称-slug>/MILESTONES.md` 并按里程碑逐个交付。此环节**非必需**——仅在上述场景顺带询问；其余情况不主动提，用户要求时再运行。里程碑文件格式由 `/jxx-to-milestones` 负责，本技能不自行生成另一套格式。

> 确定性环节可调用脚本（零依赖）：`node <本技能目录>/scripts/ac-audit.mjs <工单目录> [--strict]`（验收点形式校验）、`node <本技能目录>/scripts/issue-flow.mjs to-tickets --dir "<仓库绝对路径>/.scratch/<NN>-<slug>" --slug <name> --root "<仓库绝对路径>/.scratch"` / `node <本技能目录>/scripts/issue-flow.mjs resolve-block --dir "<仓库绝对路径>/.scratch/<NN>-<slug>"`。
>
> **路径一律用绝对路径。** 脚本会在任意 cwd 下被调用，相对路径按 cwd 解析——cwd 一旦不是目标仓库（例如停在技能安装目录），产出就会落到错误位置。
>
> 根目录解析：不给 `--root` 时，脚本从 **cwd 向上**寻找含 `.git` / `.scratch` 的仓库，再取该仓库的 `.scratch`。因此**必须在目标仓库目录内执行**。三种情况脚本直接报错退出，绝不静默写错目录：① 不在任何仓库内；② cwd 落在工具安装目录（`~/.workbuddy`、`~/.codebuddy` 等）内；③ `--dir` 传相对路径且 cwd 位于工具安装目录内。
>
> 落盘前先 `--dry-run` 打印目标路径，确认它在目标仓库内再正式执行。
>
> 维护：`issue-flow.mjs` 有三份同步副本（本源 `base/scripts/issue-flow.mjs`）。改完本源执行 `node base/scripts/check-copies.mjs --fix` 同步全部副本（`check-copies.mjs` 不带参数即校验）。
>
> **改完必须再跑 `node base/scripts/ship.mjs install` 刷新各平台已安装副本**——安装副本不会随仓库改动自动更新，而过期的安装副本会让上述全部防护失效（这正是 1.2.3 修的历史事故）。
