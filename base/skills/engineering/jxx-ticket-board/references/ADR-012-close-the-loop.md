# ADR-012：收口是四段闭环（合并预演 + 回收可机检）

- 状态：已接受（用户指令：工单完成后要审查、合入主分支、**回收工作空间**，并处理合并冲突）
- 关联：ADR-005（合并即卡——「解决冲突产生新 diff ⇒ 原审查失效」是本 ADR 分诊的依据）、ADR-011（默认回合 main，本 ADR 补上它缺的第四段与冲突可判定性）、ADR-007（协议单源，§3/§3.1/§5.4/§5.5 的落点）
- 替换：ADR-005 与 ADR-011 正文里的**主观词「机械可解」**由本 ADR 的可判定分诊取代（`merge-check` 的 `·机械候选` / `✗非机械`）；那两篇是历史决策记录，正文句保留不改写，执行以本 ADR 与 PROTOCOL §3 为准。
- 说明：本 ADR 属 **jxx-ticket-board 技能系列**（`references/ADR-00N`），与权威仓 `docs/adr/` 的产品 ADR 编号无关，别混引。

## 背景

ADR-011 把合并流改成「默认回合 main」，并写下第四段「回收 worktree/分支」——但**只写成散文，没给判据**。三个后果在 2026-10 实测到：

1. **回收没发生，且无人报**。判据只覆盖未收口的三个位（`待领` / `在办` / `待审`），`done/` 与 `archived/` 一条闸门都没有 ⇒「合入后不回收」是恒绿路径。实测某项目：**105 个 `ticket/*` 分支对 13 个 worktree、11 张 `done` 卡里 6 张仍挂着 worktree**；`rm-wt` 的 `--delete-branch` 是可选开关，没人按。
2. **冲突不可判定**。「rebase 冲突超出机械可解 ⇒ 交回开发组」里的「机械可解」是主观词，且**判定方式本身有害**：只能在真工作树上试 rebase 才知道，试错会留下半途现场，而一旦解决冲突就产生新 diff ⇒ 按 ADR-005 严格意义上使原审查失效。合并专员既拿不到冲突面，也不知道解完该不该重审。
3. **「第四段没做」在 auto 模式下无人核对**。编排者只看到 merge 卡 `done`，看不到 `wt/` 与分支还在。

## 决策

1. **收口的定义 = 四段，缺一不算收口**：定点复核 → **合入前预演冲突面** → 合入 main → **回收工作空间**。四段写进 PROTOCOL §3，并成为 §3.1（PRD 收口）与 §5.4（auto 合并专员）的共同口径。§3.1 的「收口」由两件事扩为三件事（清暂存 + 置 PRD done + **回收本 PRD 全残留现场**）。
2. **预演先于触碰：新增 `board.mjs merge-check`**。用 `git merge-tree --write-tree` 在**内存里**做三方合并——不改 index、不动 HEAD、不建 commit，预演任意次不污染任何工作区。输出四个 VERDICT：`already-merged` / `merge-clean` / `conflict` / `merge-failed`。
3. **冲突分诊改为可判定，判定结果直接决定去向**：
   - `·机械候选`（内容类 `[content]`）⇒ 逐 hunk 保留双方意图自解（`jxx-resolving-merge-conflicts`，绝不 `--abort`）；**解完 diff 已变 ⇒ 必须重跑 `/jxx-code-review` 再合**（ADR-005 的原始约束，此前只记在 ADR 里、没进协议动作）。
   - `✗非机械`（`binary` / `modify-delete` / `rename` 类）⇒ **不许合并专员拍板**：没有可逐 hunk 保留的「双方意图」，收场必然要发明行为 ⇒ 交回开发组。
   - **二进制的报法有坑**：git 对它同样报 `CONFLICT (content)`，真正信号是另一行 `warning: Cannot merge binary files: <file>`（实测确认）。只读括号里的类型会把二进制误判成「机械候选」——正是最该拦住的一类。`merge-check` 已把这条分辨固化。
4. **回收 = 工作树 + 分支两件，且分支去留由合入实况裁定**。`rm-wt` 数 `origin/main..ticket/<卡id>`：零领先（已全部合入）才自动删分支；仍有领先 ⇒ **默认保留并报明领先数**（未合入的活不能删），`--delete-branch` 强删、`--keep-branch` 保留。**受阻暂存（PRD 分支）时明确不回收现场**——活还没上 main。
5. **新增回收对账闸门（`verify`）**：已收口（`done`/`archived`）的卡若还挂着 `wt/<id>`，或零领先的 `ticket/<id>` 分支 ⇒ `MISMATCH` 点名并给出可照做的 `rm-wt` 命令；**领先 main 的分支只报 `INFO`**（那是暂存活，盲删等于丢活——判据必须区分「孤儿」与「暂存」，否则闸门会教人删掉未合入的活）。
6. **auto 模式补核对动作**：编排者每卡收口后跑 `verify`，出现未回收就按提示补 `rm-wt`（**一次一卡**）。这是 auto 模式下编排者唯一允许碰 worktree 的动作，且仍受 §7 红线约束（不得交给子代理做批量回收）。

## 后果

- 「合入后不回收」从**恒绿**变成**红灯**，且报错自带修法；孤儿 worktree / 分支开始有确定的收敛路径。
- 冲突在碰工作树之前就已知，且分诊结果直接映射到「谁来解决」——合并专员不再需要在真现场试错，ADR-005 的「解决即重审」也第一次进了协议动作序列。
- 「机械候选 / 非机械」这两个词成为可检索句柄：报错（`merge-check` 输出）与协议用同一套词，agent 拿到输出即可照做。
- 代价：`rm-wt` 多一次 `rev-list`、`verify` 多一轮已收口卡的遍历（数量级 = done/archived 卡数）。收口位默认是历史面、不再参与日常判定，这个代价换「第四段有闸门」是值的。
- 不改历史账本与既有卡面（`verify` 的回收对账只看实况，不要求任何迁移）；旧卡无 `- 合入目标:` 行照旧。
- 边界（有意不覆盖）：`verify` 只报不收——**闸门绝不代替人动手**（一次事故的教训就是自动化批量删除）；孤儿分支的清理仍是一次一卡、逐条确认。

## 首轮独立复审揪出的缺陷（本 ADR 定稿前的修正，留痕以免重蹈）

第一版实现通过了它自己的 144 条断言，但**核心安全属性有两处根本性失效**，全部由独立复审（干净视角）实测揪出，方向都是**报绿**：

1. **冲突文件名解析错**（决策 3 的一半失效）：`CONFLICT (modify/delete)` 与 `rename/*` 的消息里文件名后面紧跟句中的 `in`（`del.txt deleted in feat and modified in main`），「找第一个 `in`/文件名」的正则把捕获起点甩到句子中段 ⇒ `types` 的键匹配不上真文件名 ⇒ 类型退化成 `unknown` ⇒ **这两类被判成「机械候选」放行**。修法：**以 `--name-only` 的 `conflicted` 列表为权威键集**，反过来判断「这条消息说的是不是它」；并把 `unknown` 由「默认机械候选」改为 **fail-closed（不默认机械候选，列为需人工裁决）**。
2. **带空格的二进制文件名解析错**（决策 3 的另一半失效，与上条相互独立）：`warning: Cannot merge binary files: (\S+)` 遇空格即停，`my blob.bin` 被截成 `my` ⇒ 该文件进不了 `binaryFiles`、类型又是 `content` 被过滤 ⇒ 干净的「机械候选」。修法：按 ` (<ref> vs. <ref>)` 后缀切分并以 `conflicted` 校验文件名。

另外三处**闸门静默失效**（都违背本 ADR「给判据」的立论）：`verify` 回收对账在卡面带 `- 分支:` 时只判卡面那一支（规范名 `ticket/<id>` 的零领先孤儿静默通过）；三处 `origin/main` 硬编码使**非 main 基准的仓库上回收对账与预演全部失效且报绿**（`init --branch master` 即触发）；`merge-check` 把「基准 ref 不存在」这类配置错误报成 `VERDICT merge-failed 属异常`（与它自己的 `--base` 校验自相矛盾）。

**教训（对 144 条绿灯的重新解读）**：断言全绿不等于判据有效——首轮的二进制断言走的正是 `warning:` 那条 `continue` 分支，**从未进入有缺陷的正则**；`already-merged` 断言传 `--branch origin/main`（拿基准跟自己比），**任何实现都会通过**；`--branch` 正例只看输出文本不看退出码，**失败路径也能匹配**。三条都是「断言写在实现旁边」的自证型盲区。修法已随之落地：**权威键集反向匹配、fail-closed 兜底、反例必须能证伪、断言带 `r.code` 与「确有其事」判据**。
