# ADR-011：完成工单默认回合 main（修订 ADR-009 合并流）

- 状态：已接受（用户指令，口径确认：全部工单默认直合 main；技术受阻才降级暂存，且必须向用户汇报不能回合的原因，汇报渠道 = 会话内显式回报 + merge 卡流转段 + 领导者账本）
- 修订：ADR-009 决策 2「统一合并流 = 卡面合入目标」——本 ADR 取代其「PRD 工单先合 PRD 分支」的默认；ADR-009 的 in-project 布局（决策 1）与三技能同流水线（决策 3）继续有效
- 被修订：决策 1 的「回收 worktree/分支」一句由 **ADR-012** 接手——那一句当时只是散文、没有判据，实测导致第四段恒不执行；ADR-012 把收口定成四段闭环并给回收加可机检闸门（`merge-check` 预演 + `rm-wt` 分支回收 + `verify` 回收对账）。本 ADR 决策 1/2 的合并流向不变。
- 关联：ADR-005（合并即卡）、ADR-007（协议单源，§3/§3.1 已改写）、ADR-009（被修订方）、ADR-012（收口闭环，接手本 ADR 的回收句）
- 说明：本 ADR 属 **jxx-ticket-board 技能系列**（`references/ADR-00N`），与权威仓 `docs/adr/` 的产品 ADR 编号无关，别混引。

## 背景

ADR-009 的合并流是「PRD 工单 ⇒ 先合 PRD 分支，PRD 收口或用户要求才合 main」。运行后用户反馈：完成工单后应默认回合主分支——半成品长期挂在 PRD 分支上，主干迟迟拿不到已审查的代码；「能不能合 main」这件事也没有显式结论交回用户。

## 决策

1. **合入目标一律默认 `main`（含 PRD 工单）**。工单完成审查后，合并专员默认执行：fetch → 把 `ticket/<卡id>` rebase 到最新 `origin/main` → 确认没影响（diff 面限于工单声明范围、本地门禁/测试绿、无越界夹带）→ 合入 main 并 push。
2. **不能回合 main ⇒ 降级 + 汇报（硬性）**。技术受阻时分级处理，且**必须当场向用户显式汇报不能回合的原因**（冲突面 / 哪个门禁红 / 卡在哪张依赖），同时落 merge 卡「流转追加段」与领导者账本：
   - rebase 冲突不可机械解 → 交回开发组按 `jxx-resolving-merge-conflicts` 处理（原冲突红线不变）。**注**：本句原文用「超出机械可解」这一**主观词**，ADR-012 已把它替换为可判定的冲突分诊（`merge-check` 的 `·机械候选` / `✗非机械`），执行以 ADR-012 与 PROTOCOL §3 为准；此历史句保留以免改写决策留痕；
   - rebase 干净但门禁/测试红，或本分支携带未上 main 的兄弟工单提交（典型 = 同 PRD 依赖序未到）→ 工单属 PRD ⇒ 暂存降级：合入 PRD 分支 `ticket/<NN>-<slug>`（**不存在则先从 `origin/main` 建**，惰性创建，不再预建）等收口清入；散工单 ⇒ `blocked` 等人工。
3. **PRD 分支从「集成分支」退化为「暂存道」**：不再预建（`add-wt` 一律从 `origin/main` 拉，PRD 工单同此）；只在首次暂存降级时创建。§3.1「PRD 收口」语义改为「清暂存 + 状态收口」：全部工单 done/wontfix 或用户要求时，把暂存分支上未上 main 的工单清入 main（无暂存则跳过），并把 `PRD.md` 的 `**Status:**` 置 `done`。
4. **卡面「合入目标」行恒为 `main`**：`mergeTargetOf()` 不再按 PRD.md 推导 PRD 分支；受阻暂存分支由合并专员按 PRD 指针现场推导，不上卡面。旧卡面残留的 PRD 分支值由 `card-read` 标注为旧值、协议按新流执行；`verify` 假交付闸门基准从「合入目标」改回 `origin/main`。

## 后果

- 已审查代码尽快上主干，PRD 半成品不再阻塞主干获取已完成工单；PRD 分支仅在真正出现跨工单依赖阻塞时起作用。
- 降级路径必须留痕（会话汇报 + 卡 + 账本），「悄悄停在 PRD 分支」不再合规。
- selftest 对应断言改写：合入目标恒 main、add-wt 一律从 origin/main、PRD 分支不再预建（128 项断言仍全绿）。
