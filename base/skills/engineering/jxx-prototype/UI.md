# UI Prototype

在单个路由上生成**多个截然不同的 UI 变体**，通过浮动底栏切换。用户在浏览器中翻看变体，选择一个（或从各变体中取其精华），然后丢弃其余的。

如果问题是关于逻辑/状态而非外观——走错分支了。使用 [LOGIC.md](LOGIC.md)。

## 何时使用此形状

- "这个页面应该长什么样？"
- "我想在确定前看几个仪表盘方案。"
- "试试设置页面的不同布局。"
- 任何用户否则会在脑海中花一天时间在三个模糊 prototype 之间犹豫的场景。

## 两种子形状——强烈优先选择子形状 A

UI prototype 在与应用的其余部分**紧密贴合**时更容易评判——真实的头部、真实的侧边栏、真实的数据、真实的密度。一个独立的一次性路由是真空环境：每个变体在隔离状态下都看起来不错。只要有合理的现有页面可以承载变体，就默认使用子形状 A。只有当 prototype 确实没有附近的归属时才使用子形状 B。

### 子形状 A——对现有页面的调整（优先）

路由已经存在。变体在**同一路由**上渲染，由 `?variant=` URL 搜索参数控制。现有的数据获取、参数和认证都保留——只有渲染部分切换。这是默认选择；除非有特定理由，否则选它。

如果 prototype 针对的东西还没有页面但*自然会存在于某个页面内*（仪表盘的新区域、设置页面的新卡片、现有流程的新步骤）——那仍然是子形状 A。将变体挂载在宿主页面内。

### 子形状 B——新页面（最后手段）

仅当被 prototype 化的东西确实没有现有页面可以嵌入时使用——例如全新的顶层界面，或无法嵌入任何合理位置的流程。

按照项目已有的路由约定创建**一次性路由**——不要发明新的顶层结构。命名要明显是 prototype（例如在路径或文件名中包含 `prototype`）。同样的 `?variant=` 模式。

在决定使用子形状 B 之前，先做合理性检查：真的没有现有页面可以嵌入吗？空路由会隐藏有内容路由会暴露的设计问题。

两种子形状的浮动底栏是相同的。

## 流程

### 1. 陈述问题并选择 N

默认**3 个变体**。超过 5 个就不再是截然不同，而是噪音——封顶在 5。

用一行写下计划，放在 prototype 位置或文件顶部注释中：

> "设置页面的三个变体，通过 `?variant=` 切换，在现有 `/settings` 路由上。"

无论用户是否在场可以反驳，这都适用。

### 2. 生成截然不同的变体

起草每个变体。每个变体需满足：

- 页面的目的和它可访问的数据。
- 项目的组件库/样式系统（TailwindCSS、shadcn、MUI、纯 CSS 等）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须是**结构不同的**——不同的布局、不同的信息层级、不同的主要交互方式，而不仅仅是不同的颜色。三个微调过的卡片网格不是 UI prototype，是壁纸。如果两个草稿太相似，用明确的"不要使用卡片网格"指导重做其中一个。

### 3. 将它们连接在一起

在路由上创建一个切换器组件：

```tsx
// 伪代码——适配项目的框架
const variant = searchParams.get("variant") ?? "A";
return (
  <>
    {variant === "A" && <VariantA {...data} />}
    {variant === "B" && <VariantB {...data} />}
    {variant === "C" && <VariantC {...data} />}
    <PrototypeSwitcher variants={["A", "B", "C"]} current={variant} />
  </>
);
```

子形状 A（现有页面）：保留切换器上方的所有现有数据获取；每个变体只改变渲染的子树。

子形状 B（新页面）：`/jxx-prototype/<name>` 下的一次性路由挂载相同的切换器。

### 4. 构建浮动切换器

屏幕底部中央的小型固定定位栏，包含三个部分：

- **左箭头**——循环到上一个变体（环绕）。
- **变体标签**——显示当前变体键，如果变体导出了名称也显示该名称。例如 `B — 侧边栏布局`。
- **右箭头**——循环到下一个变体（环绕）。

行为：

- 点击箭头更新 URL 搜索参数（使用框架的路由器——Next 用 `router.replace`，React Router 用 `navigate` 等），使变体可分享且刷新稳定。
- 键盘：`←` 和 `→` 箭头键也可循环。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时不要拦截箭头键。
- 视觉上与页面区分（例如高对比度胶囊、微妙阴影），使其明显不是被评估设计的一部分。
- 在生产构建中隐藏——用 `process.env.NODE_ENV !== 'production'` 或等效检查做门控，防止意外合并将栏发布给用户。

将切换器放在单个共享组件中，以便两种子形状都能复用。放在项目中共享 UI 所在的位置。

### 5. 交付

展示 URL（和 `?variant=` 键）。用户会在方便时翻看。有趣的反馈通常是**"我想要 B 的头部加上 C 的侧边栏"**——那就是他们真正想要的设计。

### 6. 记录答案并清理

一旦某个变体胜出，记录是哪个以及原因（commit 消息、ADR、issue，或 prototype 旁边的 `NOTES.md`，如果你在 AFK 且用户尚未回复）。然后：

- **子形状 A**——删除失败的变体和切换器；将胜出者融入现有页面。
- **子形状 B**——将胜出变体提升为真实路由，删除一次性路由和切换器。

不要留下变体组件或切换器。它们很快就会腐烂并困惑下一个读者。

## 反模式

- **仅在颜色或文案上不同的变体。** 那是微调，不是 prototype。真正的变体在结构上存在分歧。
- **变体之间共享过多代码。** 共享一个 `<Header>` 可以；共享一个 `<Layout>` 就违背了初衷。每个变体应该能自由抛弃布局。
- **将变体连接到真实的数据变更操作。** 只读 prototype 没问题。如果变体需要变更，指向一个桩——问题是"这应该长什么样"，不是"后端能不能工作"。
- **直接将 prototype 提升到生产环境。** 变体代码是在 prototype 约束下编写的（无测试、最少的错误处理）。融入时请正确重写。
