# ADR 格式

ADR 存放在 `docs/adr/` 中，使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

惰性创建 `docs/adr/` 目录 — 只在第一个 ADR 需要时才创建。

## 目标仓已有契约时优先

目标仓库已定义 ADR 的 H1、字段行与固定小节顺序时，以目标仓契约为准；本文件只补内容要求。把「真实备选」写入其「替代方案」节，把「取舍与后果」写入其「后果」节。目标仓无 ADR 结构契约时才使用下面的完整模板。

## 模板

```md
# {决策的简短标题}

状态：{提议（proposed） | 已接受（accepted）}
上下文：{迫使做决策的事实与约束。}
决策：{当前选择。}
真实备选：{实际考虑过的其他方案。}
取舍与后果：{各方案的选择/拒绝理由；所选方案的收益、代价与下游影响。}
```

仍是一项决策一个 Markdown 文件，可以压缩成短段落，但**真实备选、取舍与后果不可省略**。没有真实备选就不满足 SKILL.md 的 ADR 三条件；不得编造陪跑选项，此时不建 ADR。

## 状态与当前现实

- **提议（proposed）**：决策尚未被采用。
- **已接受（accepted）**：决策是当前实际执行的现实，不是未来计划或历史愿望。代码与决策不一致时先核实；决策已变就按「弃用与取代」处理。
- **被 ADR-NNNN 完全/部分取代**：保留历史，同时明确哪些内容不再有效；部分取代时注明其余仍为 accepted 的范围。

## 编号

扫描 `docs/adr/` 获取最高现有编号并加一。

## 弃用与取代

新建 ADR 前，搜索根目录与相关上下文的 `docs/adr/` 并读取同主题旧 ADR。无替代决策的弃用写明原因；改变旧决策时：

1. 在新 ADR 中用相对链接引用旧 ADR，明确**完全取代**或**部分取代**及原因。
2. 部分取代必须写清失效范围与仍有效范围，不能只写“部分”而不给边界。
3. 把旧 ADR 顶部的状态行替换为：用相对链接回指新 ADR，标记相同的取代类型与范围；部分取代在同一状态行写清其余仍为 accepted 的范围。不要保留旧的 `accepted` 状态行，避免同一 ADR 同时声明两种当前状态。
4. 不删除旧 ADR，不另建归档或状态副本；历史推理留在原文件。

完全取代示例：

```md
# 0004-改用 CQRS 分离读写模型

状态：已接受（accepted）
上下文：订单量增长导致读写竞争加剧。
决策：读模型投影到 Elasticsearch，写模型保持事件溯源。
真实备选：保留 ADR-0001 的单体读写方案，但无法满足当前的独立扩展需求。
取舍与后果：CQRS 支持读写独立扩展；代价是新增投影与最终一致性，调用方不得假设读模型即时更新。
取代：完全取代 [ADR-0001](0001-event-sourced-orders.md)。
```

然后把 `0001-event-sourced-orders.md` 顶部的状态行替换为：

```md
状态：被 [ADR-0004](0004-cqrs-read-write.md) 完全取代
```

部分取代示例（编号仅示意，与其他代码块无承接关系）：旧 ADR-0010 决定支付回调用订单状态检查去重并做签名校验；新 ADR-0011 只把去重改为幂等键。新 ADR 写 `取代：部分取代 [ADR-0010](0010-payment-callback.md) — 仅替换回调去重，签名校验不变`；旧 ADR 写 `状态：部分被 [ADR-0011](0011-idempotency-key.md) 取代 — 回调去重失效，签名校验仍为 accepted`。两条记录由此形成双向链接。

## 多上下文归属

- **系统级决策**（影响多个上下文）：放在根 `docs/adr/`
- **上下文特定决策**（只影响一个上下文）：放在该上下文的 `docs/adr/`

判断标准：如果撤销该决策需要修改多个上下文的代码，它是系统级的。

## 何时提供 ADR

三条件判断规则见 SKILL.md「谨慎提供 ADR」。此处补充**什么符合条件**的具体示例：

### 什么符合条件

- **架构形状。** "我们使用 monorepo。""写模型是事件溯源的，读模型投影到 Postgres。"
- **上下文之间的集成模式。** "订购和计费通过领域事件通信，而非同步 HTTP。"
- **带有锁定的技术选择。** 数据库、消息总线、认证提供者、部署目标。不是每个库 — 只是那些换掉需要一个季度的。
- **边界和范围决策。** "客户数据由客户上下文拥有；其他上下文仅通过 ID 引用。" 明确的否定和肯定一样有价值。
- **对显而易见路径的有意偏离。** "我们使用手动 SQL 而非 ORM，因为 X。" 任何合理读者会假设相反的地方。这些阻止下一个工程师"修复"有意为之的东西。
- **代码中不可见的约束。** "因为合规要求我们不能使用 AWS。""响应时间必须在 200ms 以下，因为合作伙伴 API 合同。"
- **拒绝不显而易见的替代方案时。** 如果你考虑了 GraphQL 并因微妙原因选了 REST，记录它 — 否则六个月后会有人再建议 GraphQL。

### 中文领域示例

以下示例展示在中文业务场景中如何撰写 ADR。示例编号仅示意格式，与其他示例没有承接关系；真实编号按 `docs/adr/` 现有最大值递增。

```md
# 0001-订单状态机采用显式状态模式

状态：已接受（accepted）
上下文：订单流转涉及多个状态（待支付、已支付、已发货、已完成、已取消），状态转换有严格的先后约束。
决策：采用显式状态机管理订单状态与转换。
真实备选：使用布尔标志组合；该方案容易产生"已取消且已发货"等非法组合，因此不采用。
取舍与后果：显式状态机能阻止非法转换；代价是需要显式定义状态与转换，后续新增状态必须修改状态机。
```

```md
# 0002-会员等级由独立服务计算而非订单服务内联

状态：已接受（accepted）
上下文：会员等级计算依赖多源数据（消费金额、活跃天数、邀请人数）。
决策：独立为会员服务，通过事件异步触发重算。
真实备选：在订单服务内联计算；该方案会导致职责膨胀和循环依赖，因此不采用。
取舍与后果：独立服务隔离了会员等级职责；代价是引入服务间通信与最终一致性，调用方不能假设重算即时完成。
```

```md
# 0003-支付回调采用幂等键而非状态检查

状态：已接受（accepted）
上下文：支付渠道可能重复发送回调。
决策：采用幂等键去重，由数据库唯一约束保证并发安全。
真实备选：通过检查订单状态去重；该方案在并发场景下存在竞态条件，因此不采用。
取舍与后果：幂等键能避免重复处理；代价是维护幂等键存储与唯一约束，重复回调必须返回首次处理结果。
```
