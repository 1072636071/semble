# 语义方案审查（门下省）

独立审阅已固化的 GOAL.md 契约，判断该方案是否值得进入执行循环。不审形式（否决门已审），审**内容**。

## 定位

```
goal-contract（契约固化 + 否决门自检）→ plan-review（语义审查）→ goal-execute（执行循环）
                                          ↓ 封驳
                                       打回 goal-contract 修正
```

- 否决门审的是：Goal 说"怎么做"了吗？Acceptance 有绑定验证命令吗？
- 本技能审的是：方案真的可行吗？切片的依赖顺序对吗？预算够吗？有遗漏的边界场景吗？

**两者互补，不可互相替代。** 否决门通过不代表方案正确，语义审查通过不代表形式无懈。

## 前提

- `.goals/{name}/GOAL.md` 已存在且已通过 goal-contract 的否决门（V1-V10）
- 若契约只有草稿、未固化，先退回 goal-contract 完成固化
- plan-review 不修改 GOAL.md——只审，不改。修正由 goal-contract 负责

## 审查维度

逐维度审阅，每维度输出通过/问题，有问题的给出具体封驳理由。

### D1 — 覆盖完整性

检查契约是否覆盖了目标所有关键维度，是否有遗漏的边界场景或无声明假设。

审什么：
- Goal 的范围边界是否清晰？有没有"没说要做但读者默认会做"的隐式期望？
- Acceptance 集合是否覆盖了目标的所有关键交付物形态？有没有漏掉某个输出类型（如只验证了代码但没验证文档，只验证了功能但没验证错误处理）？
- 有无关键用户流程或边界场景未被任何 Acceptance 捕获？
- 无声明假设：契约依赖了哪些外部条件但未写入 Constraints？（如"假设数据库已启动""假设用户有管理员权限"）

封驳条件：
- 存在明显遗漏的交付物形态（如 Goal 提到"报告+工具"，Acceptance 只覆盖了工具）
- 关键边界场景未覆盖（如"空输入""并发""权限不足""断网"对目标场景致命但未提及）
- 存在无声明假设且该假设可能不成立

### D2 — 可行性

检查方案在技术上是否可行，子任务拆解方向是否合理。

审什么：
- Goal 描述的交付物在当前技术栈约束下是否可实现？有没有已知的技术障碍？
- 如果有子任务或切片拆解（在 PROGRESS.md 中），拆解方向是否合理？依赖顺序是否正确？
- 关键路径上是否有单点阻塞风险？（某一处失败会导致整个目标无法推进）
- 是否有"先有鸡还是先有蛋"的循环依赖？（切片 A 依赖 B 的输出，B 又依赖 A 的输出）

封驳条件：
- 发现了明确的技术不可行点（如 Constraints 要求的技术栈不支持 Goal 的核心需求）
- 切片依赖顺序有逻辑错误（如先验证后实现）
- 存在循环依赖或单点阻塞且无应对策略

### D3 — 约束一致性

检查 Constraints 内部是否矛盾，Constraints 与 Goal 是否冲突。

审什么：
- Constraints 之间是否互斥？（如"只用标准库"和"使用 Redis Streams"同时出现）
- Constraints 是否与 Goal 冲突？（如 Goal 要求"跨平台桌面应用"，Constraints 限定"纯 Web 前端"）
- 保护性约束是否足以覆盖目标的风险面？
- Budget 上限是否与 Goal 的复杂度匹配？（如"写出一个操作系统"配"最大轮数：3"）

封驳条件：
- Constraints 内部互斥
- Constraints 与 Goal 核心需求直接冲突
- Budget 明显不匹配目标复杂度（差距 ≥ 一个数量级）

### D4 — 审计就绪性

检查契约是否具备进入执行循环的审计条件。

审什么：
- 每条 Acceptance 的验证命令是否真实可执行？（不是占位符、不是伪代码、在当前环境中可运行）
- 验证命令的输出是否可判定通过/失败？（不应输出模糊的、需要人解释的结果）
- Pause Conditions 是否覆盖了目标场景的高风险项？（至少覆盖：凭证/支付/生产数据/版权/发布）
- Pause Conditions 是否过于宽泛导致执行循环频繁中断？（如"任何不确定时暂停"——整个执行过程充满了不确定性）

封驳条件：
- 存在验证命令无法在当前环境中执行（如引用了不存在的工具、路径、API）
- 验证命令输出无明确通过/失败信号（如只输出日志不返回退出码）
- 高风险场景（凭证、支付、生产数据、版权、发布）未出现在 Pause Conditions 中
- Pause Conditions 过于宽泛，估算会导致每轮都中断

### D5 — 可恢复性

检查契约是否支持断点恢复（goal-execute 的核心需求）。

审什么：
- 目标命名是否稳定？（不会在执行中途改名称导致 PROGRESS.md 断裂）
- 切片拆解是否足够细粒度？（一个切片失败不会导致大量工作白做）
- 是否有明确的"最小可交付"？（即使预算耗尽，也有部分成果可用，而非全有或全无）

封驳条件：
- 切片粒度过粗（一个切片涵盖整个 Acceptance，等同于没有拆解）
- 目标名称包含动态部分（日期、版本号等可能在执行中变化的值）

## 审查流程

### 步骤 1 — 收集上下文

读取 `.goals/{name}/GOAL.md` 全文。如果 PROGRESS.md 已存在（含切片拆解），同时读取。读取 `_index.md` 了解是否有其他并行目标。

**不读取**：goal-contract 的否决门自检日志、用户原始对话上下文、生成过程——这些会污染审查独立性，导致"合理化"已生成的方案。

### 步骤 2 — 逐维度审查

按 D1 到 D5 顺序审查。每个维度输出：

- ✅ 通过 —— 该维度无问题
- ⚠️ 建议 —— 有改进空间但不阻塞执行
- ❌ 封驳 —— 必须修正后才能进入执行

封驳时必须给出具体的修正方向，而非"请重新设计"——让 goal-contract 知道改什么。

### 步骤 3 — 综合判定

| 各维度结果 | 综合判定 |
|-----------|---------|
| 全部 ✅ | **准奏** — 直接进入 goal-execute |
| 有 ⚠️ 无 ❌ | **附条件准奏** — 进入执行但 PROGRESS.md 记录警告，执行中关注对应维度 |
| 有 ❌ | **封驳** — 列出所有封驳项，打回 goal-contract 修正 |

### 步骤 4 — 输出审查结果

#### 准奏格式

```
门下省审议结果：准奏

目标：{name}
审查维度：D1 ✅ | D2 ✅ | D3 ✅ | D4 ✅ | D5 ✅

方案可行，建议进入执行。
```

#### 附条件准奏格式

```
门下省审议结果：附条件准奏

目标：{name}
审查维度：D1 ✅ | D2 ✅ | D3 ⚠️ | D4 ✅ | D5 ✅

⚠️ 建议（不阻塞执行，执行中关注）：
- D3：<具体建议>

方案整体可行，建议进入执行，执行中关注上述建议。
```

#### 封驳格式

```
门下省审议结果：封驳

目标：{name}
审查维度：D1 ❌ | D2 ✅ | D3 ✅ | D4 ❌ | D5 ✅

❌ 必须修正：
- D1：<具体问题 + 修正方向>
- D4：<具体问题 + 修正方向>

修正后重新提交审议。修正建议已写入 .goals/{name}/REVIEW.md。
```

### 步骤 5 — 记录审查结果

将审查结论写入 `.goals/{name}/REVIEW.md`：

```markdown
# 语义审查记录

- 审查时间：{时间}
- 审查结果：准奏 / 附条件准奏 / 封驳
- D1 覆盖完整性：✅ / ⚠️ / ❌ + 具体说明
- D2 可行性：✅ / ⚠️ / ❌ + 具体说明
- D3 约束一致性：✅ / ⚠️ / ❌ + 具体说明
- D4 审计就绪性：✅ / ⚠️ / ❌ + 具体说明
- D5 可恢复性：✅ / ⚠️ / ❌ + 具体说明
- 综合判定：<准奏/附条件准奏/封驳>
```

封驳时 REVIEW.md 的修正建议部分即为 goal-contract 的修正指引。

> 确定性环节可调用脚本：`node base/scripts/goal.mjs review-write --goal-dir <dir> [--d1..--d5 pass|suggest|reject]`（零依赖）

## 异常处理

| 场景 | 处理方式 |
|------|---------|
| GOAL.md 不存在 | 提示先运行 goal-contract |
| GOAL.md 未通过否决门（无固化日志） | 提示先完成否决门检查 |
| PROGRESS.md 已存在且有执行记录 | 该目标已进入执行，审查无意义——直接放行，注明"已在执行中，跳过审查" |
| PROGRESS.md 含切片但 GOAL.md 无对应 Acceptance | 数据不一致，标记 D2 封驳，要求 goal-contract 重新对齐 |
| 多目标并行且目标间有依赖 | 在 D2 中额外检查跨目标依赖是否循环 |
| subagent 不可用（审查仍需完成） | 降级为"换视角自检"——抛开生成过程，以第三方姿态仅凭 GOAL.md 原文逐维度审查，在 REVIEW.md 记录"独立审查降级为换视角自检" |

## 与上下游的契约

| 上游 | 关系 |
|------|------|
| `jxx-goal-mode` | 路由器在 goal-contract 完成后、goal-execute 启动前调用本技能 |
| `jxx-goal-contract` | 封驳时本技能将修正方向写入 REVIEW.md，goal-contract 读取后修正 |

| 下游 | 关系 |
|------|------|
| `jxx-goal-execute` | 准奏或附条件准奏后启动；启动前检查 REVIEW.md 确认审查已通过（准奏/附条件准奏） |

## 反模式

- **审形式不审内容**——重复否决门的工作，如检查"Acceptance 有没有 3 条"。否决门已审过，本技能审语义。
- **提模糊建议**——"方案不够好"不如"D2：切片 2 依赖切片 3 的输出，但切片 3 声明依赖切片 2——循环依赖"。
- **过度审查**——对低风险小目标逐维度深挖。根据目标复杂度调整审查深度：深度调研/多人协作/高风险目标 → 全维度深审；单文件脚本/一次性工具 → D1+D4 即可。
- **阻塞合理方案**——吹毛求疵，对无伤大雅的细节封驳。建议（⚠️）和封驳（❌）的区分标准：是否会导致执行循环失败或交付物不可用。
- **泄露上下文**——引用了 goal-contract 生成过程中的信息（"你在生成时假设了 X"）。只以 GOAL.md 原文为证据来源。

## 与 jxx-code-review 的分工

两个审查在管线中互补，不重叠：

| 维度 | plan-review | jxx-code-review |
|------|------------|-----------------|
| 审什么 | 方案（GOAL.md 契约） | 代码（git diff） |
| 时机 | 开工前（contract 之后、execute 之前） | 收工后（代码已写出） |
| 核心问题 | 方案可行吗？有遗漏吗？预算够吗？ | 代码干净吗？匹配 spec 吗？有 bug 吗？ |
| 失败后果 | 封驳打回 contract 修正 | 修改代码后重新审查 |
| 不审什么 | 不审代码风格、不审实现细节 | 不审方案合理性、不审目标定义 |

两者不互相替代。一个方案可能通过 plan-review 但写出烂代码（需 code-review 拦截），一段干净代码可能实现错误方案（需 plan-review 拦截）。
