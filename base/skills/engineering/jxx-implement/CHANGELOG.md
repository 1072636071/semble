# Changelog

## 1.8.1 — 2026-10-21

文档侧收敛：勾选区行格式定为 `- [x] AC-<n> | 证据：…`（不复抄类别与验证方式）；门禁小节删掉与规范 §四重复的判据表，只留 5 条名称 + 命令块；选项 B 不可绕过 `partial` / `missing` 与假实现；明确 `done` 只由执行者置。原因：判据只在权威规范里存一份。

## 1.8.0 — 2026-10-21

**验收点闭环 + 防劣化门禁（硬出口）**：AC 从「写在工单里」变成「实现时逐条勾选并附证据」，同时给出防劣化的可执行门禁，堵住少做、假做、劣化三类失效。判定口径 pointer 到 `jxx-to-tickets/references/acceptance-criteria.md`（唯一权威源，不复制正文）。要点：

- 新增「验收点闭环」节（置于「步骤打卡与断线续接」之后、「完成步骤」之前）：开工把工单 AC 原样抄进「**AC 勾选区：**」；工单无 AC ⇒ 停手补 AC 或退回生产侧，不得先写代码；每完成一条勾选并同行附证据；AC 全勾且带证据才是 `pending-review` 的前置。
- 「完成步骤」三步各自补 AC 前置：置 `pending-review` 前 AC 全勾带证据；审查须按 AC 逐条判 `met` / `partial` / `missing`；置 `done` 前 `ac-audit.mjs <工单文件>` 退出码 0。
- 新增「防劣化门禁（独立执行，不采信他人结论）」小节：规范第四节 5 条门禁（全量测试 / 公共符号 diff / 断言放宽扫描 / 依赖与配置 / 行为基线）逐条给 yes/no 判据与命令示例，diff 范围 `origin/main`。
- 「审查发现问题时的处理流程」补第 6 条：报告里 `partial` / `missing` 的 AC 必须逐条回 AC 勾选区返工（取消勾选 → 改 → 重勾并重写证据），只改代码不补证据视为返工未完成。
- 版本回填说明：frontmatter 长期停在 1.6.0，而 1.7.0（双写改调 `ticket-flow` 一条命令）已于 2026-10-18 落盘却未回填 frontmatter，故本次统一回填版本线，新内容记入 1.8.0——避免同一版本号出现两条 CHANGELOG 条目。

## 1.7.0 — 2026-10-18

**双写段改调 `ticket-flow` 一条命令**（PRD 127 · 服务器 T166）：「服务器优先」节的逐条 MCP 双写纪律（改本地 md → get → update → 冲突重试）改为一条 `node tools/ticket-flow.mjs --root <仓库根> [--file <单条md>]`——命令内部完成匹配、create/update、乐观锁重试与 state 刷新，幂等可重跑、`--dry-run` 零写入预演。**MCP 四把工具（`jxx_ticket_call` / `get` / `list` / `push`）降级为 exit 2 兜底路径**（仅当项目未接该 CLI 或命令不可用时才回退）。「步骤打卡与断线续接」节的续接入口同步改用 `--dry-run` 预演看差异（兜底仍可 `jxx_ticket_call get`）。口径与 `jxx-ticket-router` 技能「快速通道」节一致。

## 1.6.0 — 2026-10-15

**步骤打卡与断线续接（默认纪律）**：开工前列 `**处理步骤：**` 清单进工单文件，每完成一步就地打卡（+日期+执行事实）并双写服务器；续接从打卡现场直接恢复，不重做已完成步骤；续接入口 = 工单打卡区 + 评论时间线 + 服务器副本三方对齐（不一致以服务器为准）。完成三步硬出口并入步骤清单。

## 1.5.0 — 2026-10-15

「服务器优先」双写范围从状态流转扩到**正文与评论**：实现过程中追加的工单评论、修订的验收点，先改本地 md 再按服务器最新 `version` 作 `base_version` 推送。新增「批量 push 的 id 必须实测核对」条款（2026-10-15 T131–T135 串位事故教训：凭表格手抄 id 批量 push，四条正文错进邻居工单，靠乐观锁 409 + 标签过滤对账才发现）。

## 1.4.0 — 收口四段闭环（随 jxx-ticket-board v0.15.0 / ADR-012）

工单完成后不只在「审查 → 合入 main」收尾——新增「交付之后：收口是四段闭环」节，把开发组需要知道的四件事写实：① **现场不归你管**（合并专员合入后 `rm-wt` 回收工作树与已合入分支，别自己删、也别假设现场永远在）；② **冲突在碰工作树之前就已知**（合并专员先 `merge-check` 内存预演；判为非机械 binary / modify-delete / rename 的会交回你）；③ **解冲突 = 改 diff = 原审查失效**，必须重跑 `/jxx-code-review` 再交（ADR-005）；④ **受阻暂存不回收现场**（活还没上 main）。README 的「相关技能」补齐合并冲突处置入口。
## 1.3.0 — 默认回合 main（随 jxx-ticket-board v0.14.0 / ADR-011）

完成工单后默认回合主分支（含 PRD 工单）：投卡「合入目标」一律 main；`add-wt` 一律从 origin/main 拉（PRD 分支不再预建，降为受阻暂存道）；代码审查 diff 基准 = origin/main；合并归合并专员，技术受阻才暂存 PRD 分支或 blocked，且必须向用户汇报不能回合 main 的原因（PROTOCOL §3/§3.1）。

## 1.1.0 — 2026-10-01

三技能统一改造（jxx-ticket-board v0.12.0 / ADR-009）：新增「硬前置」——一切开发在项目内的工单 worktree（`wt/<卡id>`）中进行并走统一看板卡位流转（看板 init → 投卡 → 领卡 → add-wt，基分支按合入目标自动推导）；「完成步骤」commit 目标明确为工单分支，diff 基准 = 合入目标；新增「交付」步（移卡 review 位）；合并归合并专员按统一合并流（PRD → PRD 分支，散工单 → main）。
