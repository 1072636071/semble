# AI 友好架构

代码的第一读者是 AI agent。每条准则背后都是机制：注意力在长 context 中衰减、AI 通过 token 理解语义、RAG 按路径索引、Transformer 按顺序预测。理解机制，准则可以变通；不理解，准则只是清单。

本技能是 jxx 系列的基石：它对**项目**提基线要求（可索引、有规则文件、一键运行），也规定 **agent** 的工作方式（索引优先检索、按模块拆子 agent 并行审查）。其他 jxx 技能假设这些基线成立。

## 两种模式

**设计** — 用户要新系统、新模块、目录结构或拆分方案。按准则产出：模块划分（每个模块单一职责、独立可测试）、扁平目录树、显式接口签名、Schema 定义、护栏配置（linter / 测试建议）。结尾过一遍设计自检。

**审查** — 用户要评估现有结构。**索引优先**：有代码索引 MCP（如 codebase-memory：`search_graph` 找定义、`trace_path` 追调用链、`get_architecture` 看全局分层）时，用索引定位模块与依赖，抽样读文件验证；无索引再退化为目录扫描。覆盖面大时按模块拆子 agent 并行审查，本技能汇总。按准则逐条核对，按审查输出格式报告。

用户未指明时从措辞判断：「设计 / 规划 / 搭建」→ 设计；「审查 / 评估 / 检查」→ 审查。拿不准就问。

## 准则

### 1. 文件与模块：小而美

- **单一职责**：一个文件只做一件事。超过 300-500 行的「上帝文件」要拆。
- **扁平目录**：避免深嵌套（`src/app/modules/user/services/auth/`）。AI 检索长路径易出错，扁平结构利于 RAG 索引。
- **独立可测试**：每个模块能独立运行或测试。功能单一的函数才能形成「生成-验证」闭环。

### 2. 函数：显式优于隐式

- **纯函数优先**：输入确定则输出确定，无副作用。AI 推理纯函数的准确率远高于复杂状态管理。
- **参数显式化**：不用 `*args`/`**kwargs` 或全局配置对象传参。
  - ❌ `process(data, config)` — AI 不知道 config 里有什么
  - ✅ `process(data: str, timeout: int, retry_count: int)`
- **类型注解必须**：类型签名是 AI 最重要的提示词 — 既约束生成，又充当文档。
- **控制流线性化**：用 Early Return、Guard Clauses、Pipeline 替代深层嵌套。线性代码流符合顺序预测特性。

### 3. 命名与注释：语义密度最大化

- **自描述命名**：名字包含业务含义和数据类型。
  - ❌ `list` `data` `temp` `handle`
  - ✅ `user_email_list` `raw_order_json` `retry_counter`
- **Docstring 即 Prompt**：不只写「做什么」，写「为什么」和「边界条件」（参数约束、返回值、异常）。AI 会按 Docstring 生成实现。
- **TODO/FIXME 标准化**：统一格式标记待办，方便 agent 扫描并作为任务入口。

### 4. 架构模式：AI 可预测

选社区主流、训练数据丰富的模式，避免冷门或高度自定义的抽象。

- **经典分层**：MVC / Clean Architecture / Hexagonal。AI 知道 Controller 不该写 SQL、Repository 不该处理 HTTP。
- **依赖注入**：显式依赖让 AI 能追踪调用链。避免服务定位器模式和隐式全局单例。
- **配置与代码分离**：环境变量、常量抽到独立文件。改逻辑不碰配置，反之亦然。
- **Schema 驱动**：用 Pydantic / Zod / Protobuf 定义数据结构。Schema 本身就是最强上下文 — AI 可基于它生成序列化、校验、API 文档。
- **符号友好**：少用 `eval`、`getattr` 动态分发、运行时元类。代码知识图谱和静态检索按符号索引 — 动态特性让 AI 只能暴力 grep。用代码生成代替运行时元编程。

### 5. 工程护栏

- **Linter & Formatter 强制统一**（ESLint/Prettier/Ruff，进 CI 和 pre-commit）：AI 生成代码风格与项目一致，统一风格也提高补全准确率。
- **测试即规格**：测试用例是最好的活文档。先读测试再生成实现，或生成后跑测试验证 — TDD 的红-绿循环是 AI 的纠错器，没有测试的代码对 AI 不可信。
- **一键可运行**：`make dev` / `docker compose up` 一条命令起环境。AI 需要频繁运行代码验证假设；环境搭建要人工干预，AI 效率归零。
- **代码索引**：项目应可被符号级索引（代码知识图谱 MCP，如 codebase-memory；至少 LSP 可解析）。索引是 AI 的检索基建 — 有索引查依赖走图谱，没索引只能暴力 grep。审查发现项目无法被索引（过度动态、缺类型），记为发现。
- **脚本语言约束**：项目脚本优先 TypeScript（统一语言栈，类型即文档，AI 生成质量更高）。审查时检查此约束是否存在（AGENTS.md / package.json / tsconfig）；没有则**询问用户是否加上**，而不是静默绕过。
- **清晰包边界**：多模块项目中每个包有独立 README 和类型导出。跨模块协作需要明确的接口契约 — 也决定任务能否拆给多个子 agent 并行。

### 6. 反模式（AI 开发杀手）

| 反模式 | 为什么对 AI 有害 | 改进方案 |
| --- | --- | --- |
| 过度抽象 / 元编程 | AI 无法展开宏或动态类，丢失上下文 | 适度具体化，保留静态分析能力 |
| 全局可变状态 | AI 无法追踪状态变化，产生幻觉 | 显式传参，不可变数据结构 |
| 巨型配置文件 | YAML/JSON 过长时易截断或格式错误 | 拆分为模块化配置，或用代码定义配置 |
| 注释掉的旧代码 | 干扰 AI 判断当前有效逻辑 | 删除死代码，靠 Git 历史追溯 |
| 非标准 DSL | 训练数据少，几乎无法正确使用 | 通用语言 + 库，或提供完整 DSL 文档 |
| 自然语言需求直转代码（Vibe Coding） | 无规格约束，债务随轮次累积 | Spec-First：需求 → 规格 → 代码，PRD/ADR 版本化 |

### 7. 文档即操作系统（DDAD）

文档不是附属品，是 AI 的运行环境。审查时缺这些要记为发现；设计时要把它们产出来。

- **规则文件**：仓库根部的 `CLAUDE.md` / `AGENTS.md` 是给 AI 的 system prompt — 代码风格、禁止事项、测试命令、架构约束。保持一句陈述 + 指针，不写散文。
- **Spec-First**：先让 AI 生成或确认结构化规格，再按规格写代码。两步走比直接生成代码的错误率低一个数量级；规格版本化，可追溯。
- **ADR**：`docs/adr/` 记录「为什么当初选这个方案」。AI 无法从代码反推动机 — 没有 ADR，重构时必然破坏设计意图。

## 设计自检

设计模式产出方案后逐条确认：

- [ ] 每个模块能用一句话说清职责？
- [ ] 最深目录 ≤ 3-4 层？
- [ ] 每个公开函数有完整类型签名？
- [ ] 没有全局可变状态？
- [ ] 数据结构有 Schema 定义？
- [ ] 每个模块能独立测试？
- [ ] 选的模式是社区主流而非自造？
- [ ] 有规则文件（AGENTS.md/CLAUDE.md）和 ADR 的落点？
- [ ] 环境能一键运行（一条命令起服务/跑测试）？

## 审查输出格式

```markdown
# 架构审查报告
## 总评
一段话：结构对 AI 的友好程度 + 最大的问题。
## 发现
按准则分组。每条：[严重度] 文件路径:行 — 问题 — 改进建议
严重度：违规（明确违反准则）/ 风险（当前临界，随规模恶化）/ 建议（优化项）
## 优先处理
最多 3 条，按投入产出比排序。
```

## 判断原则

- **启发式非硬性**。300-500 行、目录深度是经验阈值不是红线 — 判断趋势，不数行数。
- **仓库约定优先**。仓库已有文档化的架构约定时约定覆盖准则；准则只填补空白。
- **说机制不说教**。每个发现附「为什么对 AI 有害」，让用户能自己权衡。
