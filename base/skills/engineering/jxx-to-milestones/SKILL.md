# 里程碑交付

把一批工单归组为**里程碑**——每个里程碑结束时代码库都处于**可发布状态**：CI 绿、无半成品、可单独上线、可单独回滚——然后按里程碑逐个交付。

**核心不变量：任何一个里程碑结束时，代码库都能直接上线给用户，而不需要等后面的里程碑。**

## 输入

- 一批已发布的工单：优先 `.scratch/<NN>-<slug>/issues/` 下的工单文件，每个用 `Blocked by:` 行声明依赖。
- 工单不存在时：先运行 `/jxx-to-tickets` 生成，再回到本技能。
- 用户也可直接指定工单目录路径，或给出一份工单编号清单。

## 流程

> 所有 `--dir` **一律传绝对路径**（`<仓库>/.scratch/<NN>-<slug>`）。相对路径按 cwd 解析，而脚本会在任意 cwd 下被调用——cwd 一旦不是目标仓库（例如停在技能安装目录），脚本就会读错工单、把 `MILESTONES.md` 写进无关目录。

### 1. 扫描工单

```bash
node <本技能目录>/scripts/milestones.mjs scan --dir <dir>
```

读取每个工单的编号、标题、`Status:`、`Blocked by:`。确认工单集完整：若某工单依赖的编号不在集合内，确认它是外部已完成的工作，否则先补齐工单。

### 2. 归组为里程碑

先拿脚本的默认建议——它按**依赖层**归组（彼此无依赖的工单同层，被依赖的工单必在更早的层），再贪心合并相邻层到 `--target` 大小：

```bash
node <本技能目录>/scripts/milestones.mjs plan --dir <dir> --target 4 --max 6
```

脚本只懂依赖，不懂语义。拿到建议后按下面的硬规则做语义调整：

<grouping-rules>

- **依赖闭合**：一个工单的所有依赖，必须在同一里程碑且排在其前，或在更早的里程碑。**跨里程碑回头依赖是被禁止的**——那意味着前一个里程碑上线时带着半成品。
- **边界可发布**：里程碑结束时不得存在"做了一半"的用户可见行为。涉及 schema/API 形状变更时按**扩展-收缩**：扩展（加新形式，旧形式保留）与迁移批次可与新功能同里程碑；**收缩（删掉旧形式）必须单独成里程碑**，且排在所有迁移批之后。
- **破坏性变更与数据迁移隔离**：破坏性契约变更、不可逆数据迁移，不与新功能混装，单独成里程碑并写明回滚代价。
- **里程碑内可并行**：同里程碑内若无依赖，工单可并行推进；有依赖则按组内顺序串行——脚本会算出这个顺序并写进文件。
- **回滚方式先定**：每个里程碑动工前就要有明确的回滚手段（功能开关 / 迁移可逆 / 仅新增无破坏 / 直接 revert）。想不出回滚方式的分组，就是分错了。

</grouping-rules>

调整后校验——**退出码非 0 必须修正后才能继续**：

```bash
node <本技能目录>/scripts/milestones.mjs check --dir <dir> --groups "01,02|03,04|05"
```

脚本判定的是可机械检查的部分（循环依赖、依赖是否落在更晚里程碑、工单遗漏/重复/空组/超限）。**可发布性、半成品、回滚这些语义判据脚本判不了**——它们由你在下一步显式写进文件，并在上线门禁时逐条核对。

### 3. 询问用户

以编号列表呈现里程碑划分。对每个里程碑展示：**所含工单**、**用户视角的交付结果**、**为什么它能独立上线**、**回滚方式**。

询问：

- 这个划分下，每个里程碑单独上线时用户看到的是什么？有没有哪个里程碑上线后会出现半成品？
- 粒度是否合适？（里程碑太多 = 上线仪式成本过高；太少 = 单次变更面过大、回滚困难）
- 有没有该拆出去单独成里程碑的破坏性变更或数据迁移？

迭代直到用户批准。

### 4. 生成 MILESTONES.md

```bash
node <本技能目录>/scripts/milestones.mjs render --dir <dir> --groups "01,02|03,04" --title "<功能名>"
```

产出 `<dir>/MILESTONES.md`。脚本只搭骨架，**每个里程碑的四个占位段必须由你补全**——这些是判读性内容，脚本不生成：

- **用户视角交付**：此里程碑上线后用户能看到的端到端变化；若外部行为不变，就写"外部行为不变"并说明它在为什么做准备。
- **可独立上线判据**：为什么这批工单合起来是一个可发布整体。
- **回滚方式**：功能开关 / 迁移可逆 / 仅新增无破坏 / 直接 revert——选一个并写清操作步骤。
- **验收信号**：可观测、可勾选的一条条信号，不是"代码写完了"这种不可观测的描述。

### 5. 按里程碑交付

里程碑之间**严格串行**，里程碑内按组内顺序推进：

1. 取当前里程碑：`node <本技能目录>/scripts/milestones.mjs status --dir <dir>`
2. 置 `in-progress`，逐工单调用 `/jxx-implement`，工单之间清理上下文
3. 全部工单走完 `pending-review` → `/jxx-code-review` → `done`
4. 跑**上线门禁**（见 `references/delivery-loop.md`）：全员工单 `done` + 验收信号全勾选 + CI 绿 + 回滚方式已验证
5. 门禁通过：勾选验收信号、置 `shipped`、提交代码，再进入下一里程碑
6. 门禁未过：就地修复；若发现分组有误（出现跨里程碑依赖），回到步骤 2 重新划分，而不是硬上

```bash
node <本技能目录>/scripts/milestones.mjs set-status --dir <dir> --milestone M1 --status shipped
```

**中断续接**：重新运行 `status` 即可从各里程碑的 `**状态：**` 行恢复进度，不重做已 `shipped` 的里程碑。里程碑文件是进度的唯一真相源。

## 参考

- `references/milestone-rules.md` — 独立上线的完整硬规则、反例、扩展-收缩与破坏性变更处理、粒度指引。**划分时拿不准就读它。**
- `references/delivery-loop.md` — 交付循环细节、上线门禁清单、偏差与重新划分的处理。**进入交付阶段时读它。**
