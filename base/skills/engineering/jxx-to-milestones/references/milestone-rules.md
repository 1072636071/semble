## 不变量

**任何一个里程碑结束时，代码库都能直接上线给用户，而不需要等后面的里程碑。**

推论：

- 不允许"上线到一半的功能"——要么完整可交付，要么完全不可见（开关关闭 / 仅内部通道）。
- 不允许"数据库已迁移但代码没跟上"或反之——两者要么同里程碑，要么用新旧并存过渡。
- 不允许"删了旧的实现，新的还没接完"——删除永远排在最后。

## 规则一：依赖闭合

一个工单的所有依赖，必须在**同一里程碑且排在其前**，或在**更早的里程碑**。

违反形态：M1 里的工单 03 依赖 M2 里的工单 05。M1 上线时 03 无法完成，M1 就带着半成品上线了。脚本会报 `E-FWD-DEP`。

处理办法（按顺序尝试）：

1. 把被依赖的工单**前移**到依赖者所在里程碑或更早。
2. 若前移会让里程碑过大，把依赖者**后移**到下一里程碑。
3. 若依赖其实是"最好有"而非"必须有"，回到 `/jxx-to-tickets` 修正 `Blocked by`——不要靠里程碑划分去掩盖错误的依赖声明。

同里程碑内的依赖是允许的（脚本报 `W-INTRA-DEP` 提示），但组内必须按拓扑序串行执行，脚本会把这个顺序写进 `**组内顺序：**`。

## 规则二：边界可发布

里程碑边界上不得存在半成品。判据是**从用户视角看**，不是从代码视角看：

| 场景 | 判据 |
|------|------|
| 新功能 | 用户能完整走完一条端到端路径，或功能完全不可见（开关关闭） |
| 重构 | 外部行为完全不变，且已验证（测试/灰度/对比） |
| schema 变更 | 新旧形式并存且都可用（扩展阶段），或已全部切到新形式（收缩后） |
| API 变更 | 旧契约仍可用，或所有调用方已在同里程碑内迁移完毕 |
| UI 改动 | 不出现"点了按钮没反应"的中间态 |

**"CI 绿"不等于"可上线"。** CI 绿只说明没破坏已有测试；可上线要求新引入的东西要么完整、要么不可见。

## 规则三：扩展-收缩的里程碑切法

广泛重构（重命名列、重新类型化共享符号、改公共接口签名）的影响半径遍及全代码库，任何垂直切片都装不下。按扩展-收缩切：

- **扩展里程碑**：在旧形式旁添加新形式，**不破坏任何东西**。这个里程碑自身可上线——因为它什么都没改变。
- **迁移里程碑**：按影响半径分批迁移调用点（按包、按目录），每批一个工单，全部阻塞于扩展工单。旧形式仍在，所以每批之后 CI 保持绿色。批次可按依赖层并入同一里程碑。
- **收缩里程碑**：确认无调用者后删除旧形式。**单独成里程碑**，阻塞于所有迁移批。删除后无法靠"切回旧形式"回滚，所以要单独验证、单独回滚。

关键约束：**扩展与收缩不能落在同一里程碑**。同里程碑内做完扩展又删除旧形式，等于把"迁移所有调用点"压缩成一次原子变更——一旦漏掉一个调用点，就是线上事故，且回滚需要同时回退新旧两侧。

当连批次都无法单独保持绿色时：保持顺序，让它们共享一个集成分支，全部阻塞于最终的集成验证工单——绿色只在那个工单上承诺，整条链算一个里程碑。

## 规则四：破坏性变更与数据迁移隔离

破坏性契约变更（删字段、改语义、收紧校验）和不可逆数据迁移，**不与新功能混装**：

- 单独成里程碑，排在依赖它的新功能之后（或让新功能依赖它，从而自然被前移）。
- 在文件里写明回滚代价：可逆（有反向迁移）、可容忍（数据可重建）、不可逆（需停机/需备份恢复）。
- 不可逆的迁移里程碑之前，先有一个"备份/双写/影子校验"的里程碑。

判据：如果这个里程碑上线后需要回滚，回滚能不能在不丢数据的前提下完成？不能，就要再加一个前置的保障里程碑。

## 规则五：回滚方式先定

每个里程碑动工前就要确定回滚手段，写进 `**回滚方式：**`：

| 手段 | 适用 | 说明 |
|------|------|------|
| 功能开关 | 新功能 | 关开关即回到旧行为，无需发版 |
| 迁移可逆 | schema/数据变更 | 写出反向迁移并演练过 |
| 仅新增无破坏 | 扩展阶段 | 旧路径未被触动，revert 即可 |
| 直接 revert | 小改动、纯新增 | 整里程碑一个提交/一个 PR，一条命令回退 |

想不出回滚方式的分组 = 分错了。此时应重新划分，而不是在回滚栏写"无"。

## 规则六：里程碑内并行，里程碑间串行

- 里程碑内无依赖的工单**可以并行推进**（不同 agent 会话、不同分支），有依赖的按 `**组内顺序：**` 串行。
- 里程碑之间**严格串行**——上一里程碑 `shipped` 并验证后，才开工下一里程碑。并行推进多个里程碑会让"哪个状态是线上状态"变得不可判定，直接破坏不变量。
- 例外：纯准备工作（写测试、补文档、加脚手架）可与前一里程碑并行，但它自己必须是一个可独立上线的里程碑（外部行为不变）。

## 粒度指引

| 维度 | 建议 |
|------|------|
| 工单数 | 3–6 个/里程碑（脚本默认 target 4 / max 6） |
| 上下文 | 一个里程碑能在一两个上下文窗口内推进完 |
| 上线仪式 | 每多一个里程碑就多一次上线与验证成本；里程碑太碎会让成本超过收益 |
| 变更面 | 一个里程碑的回滚范围应当是一个人能在十分钟内判断清楚的 |

工单链很长（如 01→02→03→04 串行四层）时，脚本会切成四个里程碑。这是**正确的**——链上每一环都是一个可发布状态。若觉得太碎，检查依赖是否真实：`Blocked by` 声明过严会让里程碑无谓膨胀，回到 `/jxx-to-tickets` 修正比在这里合并更好。

## 反例集

| 反例 | 为什么错 | 正解 |
|------|----------|------|
| M1 建表 + 写新 API，M2 接前端 | M1 上线后 API 无人调用、数据无来源，是半成品 | 把 API 与前端合进同一里程碑，或用开关让 API 在 M1 不可见 |
| 扩展与删除旧列同里程碑 | 迁移调用点被压缩成原子变更，漏一个就是事故 | 扩展+迁移一批，收缩单独下一里程碑 |
| 数据迁移与新功能同里程碑，回滚方式写"revert" | revert 代码不会回滚已迁移的数据 | 迁移单独成里程碑，写明反向迁移 |
| M1 依赖 M2 的工单 | M1 带着无法完成的工作上线 | 前移被依赖工单，或后移依赖者 |
| 里程碑内既有前端改动又有后端改动，但声明"可并行" | 两者共享契约，实际有隐式依赖 | 把隐式依赖显式写成 `Blocked by`，或拆到不同里程碑 |
| 五个里程碑同时开工 | 无法判定当前线上状态 | 严格串行，重新回到单一当前里程碑 |

## 划分检查清单

对每个里程碑逐条过：

- [ ] 它依赖的工单全部在本里程碑（排在其前）或更早里程碑
- [ ] 上线后用户看到的是完整功能，或完全看不到变化
- [ ] 没有"删了旧的、新的还没接完"的情况
- [ ] 破坏性变更/不可逆迁移不在其中，或已单独隔离并写明回滚代价
- [ ] 回滚方式已写明且可操作
- [ ] 验收信号可观测（不是"代码写完了"）
- [ ] 工单数在 3–6 之间；超出有明确理由
