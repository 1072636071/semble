## 状态机

里程碑状态写在 `MILESTONES.md` 各里程碑节的 `**状态：**` 行，四选一：

| 状态 | 含义 |
|------|------|
| `pending` | 未开工 |
| `in-progress` | 正在推进其下的工单 |
| `shipped` | 已通过上线门禁、已提交、可独立发布 |
| `blocked` | 被外部因素阻塞（等依赖、等信息、等决策） |

流转：`pending → in-progress → shipped`，任意状态可转 `blocked`，`blocked` 解除后回到原状态。

文件头部的 `**状态：**` 为总体状态，由 `set-status` 自动重算：全部 `shipped` → `shipped`；有 `in-progress` 或 `shipped` → `in-progress`；否则 `pending`。

工单状态走既有生命周期：`ready-for-agent → pending-review → done`（见 `docs/agents/issue-tracker.md`）。

## 交付循环

```
status  →  取当前里程碑（第一个非 shipped）
  ↓
set-status in-progress
  ↓
按 组内顺序 逐工单：/jxx-implement → pending-review → /jxx-code-review → done
  ↓
上线门禁（见下）
  ├─ 未过 → 就地修复；若发现分组有误 → 回到 SKILL.md 步骤 2 重新划分
  └─ 通过 → 勾选验收信号 → set-status shipped → 提交/发 PR
  ↓
回到 status，进入下一里程碑
```

要点：

- **一次只推进一个里程碑。** 当前里程碑 `shipped` 之前不开工下一个——这是"可独立上线"不变量的运行时保障。
- **工单之间清理上下文。** 逐工单用 `/jxx-implement`，每个工单独立会话，避免上下文污染。
- **里程碑内可并行的工单**（无依赖关系）可分给不同会话，但合并与上线门禁仍以里程碑为单位整体做。
- **每个里程碑一个提交或一个 PR。** 回滚粒度 = 里程碑粒度，这是"可单独回滚"的落地方式。

## 上线门禁清单

在里程碑末尾逐条核对，全部通过才置 `shipped`：

1. **工单全绿** — 该里程碑所有工单 `Status: done`（`pending-review` 不算，必须过 `/jxx-code-review`）。
2. **验收信号全勾选** — `**验收信号：**` 下每个 `- [ ]` 都已改为 `- [x]`，且每条都被真实观测过，不是照抄。
3. **CI 绿** — 类型检查、单测、lint 全过。
4. **可发布性复核** — 回到该里程碑的 `**可独立上线判据：**`，确认仍然成立：没有半成品、没有未完成的迁移、旧契约仍可用或已全部迁移。
5. **回滚方式已验证** — 不只是"写了"，要确认真的能执行：开关关得掉、反向迁移跑得通、revert 后 CI 仍绿。
6. **范围无溢出** — 该里程碑的改动只包含其声明的工单，没有顺手带上属于后续里程碑的变更。

脚本能帮你核对 1、2 两项（可读部分）：

```bash
node <本技能目录>/scripts/milestones.mjs status --dir <dir>
```

输出形如 `M2 [in-progress] 工单 3/4 · 验收 2/2 · 门禁未过`，并把未 `done` 的工单逐条列出。3–6 项需要你实际执行验证。

## 断点续传

`MILESTONES.md` 是进度的唯一真相源。中断后：

```bash
node <本技能目录>/scripts/milestones.mjs status --dir <dir> --json
```

- 从 `current` 字段拿到当前里程碑。
- 已 `shipped` 的里程碑**不重做**。
- 中途工单状态停在 `pending-review` 的，先走 `/jxx-code-review` 再继续。
- 交付过程中出现的阻塞、决策与偏差，追加到文件末尾 `## 评论` 下（新内容置于最前），让续接的人（或下一个会话）有完整上下文。

## 偏差处理

| 情况 | 处理 |
|------|------|
| 工单实现中发现需要额外工单 | 新建工单，归入**当前或后续**里程碑（不得回头塞进已 `shipped` 的里程碑），重跑 `check` |
| 发现跨里程碑依赖（M1 的工单实际需要 M2 的东西） | 停止推进，回到 SKILL.md 步骤 2 重新划分并重新 `check`，而不是硬上 |
| 某里程碑上线后发现问题 | 执行该文件里写明的回滚方式，把里程碑状态从 `shipped` 退回 `in-progress`，修复后重新过门禁 |
| 工单被判定 `wontfix` 或取消 | 从里程碑的 `**工单：**` 行移除，重跑 `check` 确认依赖仍然闭合 |
| 里程碑推进中发现原划分粒度过粗 | 拆成两个里程碑，重跑 `check`，已完成的工单留在前一个并置 `shipped` |
| 外部依赖阻塞（等第三方、等决策） | 置 `blocked`，在 `## 评论` 里记录阻塞原因与解除条件；不要跳过它去推进后续里程碑 |

## 反模式

- **并行推进多个里程碑** — 破坏"哪个状态是线上状态"的可判定性。
- **把门禁当形式** — 验收信号没被真实观测就勾选，等于没有门禁。
- **里程碑内做完又拆回工单粒度提交** — 回滚粒度变细，里程碑的"可单独回滚"承诺失效。
- **跨越已 shipped 的里程碑回头改** — 已上线的状态不允许隐式变更；需要改就新开工单、归入后续里程碑。
- **用里程碑划分掩盖错误的依赖声明** — 依赖声明错了就去改 `Blocked by`，不要让里程碑划分去将就它。
