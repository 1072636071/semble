# Grill with Docs

通过 grill 会话打磨计划或设计，**同时**同步创建领域文档（`CONTEXT.md` 词汇表 + `docs/adr/` 架构决策记录）。

## 核心约束

1. **文档先行，代码后行** — 在 grill 会话期间，只做追问和文档创建/更新。禁止在 grill 会话未结束前修改任何代码文件。
2. **即时记录** — 每当一个术语被确定或一个决策被做出，立即更新 `CONTEXT.md` 或创建 ADR，不要攒着批量处理。
3. **grill 未结束 = 不动手** — 只有当用户明确表示"可以了""开始实施"或类似退出信号时，grill 会话才算结束。在此之前，只提问和写文档。

## 工作流

### 阶段 1：初始化

1. 读取根目录的 `CONTEXT.md`（若存在），了解现有词汇表
2. 读取 `docs/adr/` 目录（若存在），了解已有架构决策
3. 若两者均不存在，在第一个术语被确定时创建

### 阶段 2：Grill 循环

交替执行以下两个子流程：

**追问（grilling）** — 对计划的每个方面穷追不舍地盘问：

- 逐一提问，等待每个问题的反馈后再继续
- 如果某个*事实*可以通过探索代码库查到，自己去查而不是问用户
- 但*决策*是用户的 — 每个决策都要交给用户决定，等待回答
- 对每个问题，提供你推荐的答案

**领域建模（domain modeling）** — 每当追问中产生术语或决策时：

- 识别模糊、过载或未定义的术语 → 提出精确的规范术语
- 发明边界场景压测概念之间的边界
- 对照代码检查一致性（若存在代码库）
- 术语确定 → 立即更新 `CONTEXT.md`
- 决策确定且满足 ADR 条件 → 立即创建 ADR

### 阶段 3：收尾

当用户发出退出信号时（"可以了""开始实施""够了"等）：

1. 总结本次会话新增/变更的术语和决策
2. 列出已创建/更新的文档清单
3. **此时才可以**进入代码实施阶段

## ADR 创建条件

仅当以下三个条件**全部满足**时才创建 ADR：

1. 难以逆转 — 后来改变想法的成本不可忽略
2. 没有上下文会令人惊讶 — 未来读者会想知道"为什么这样做"
3. 真实权衡的结果 — 有真正的替代方案被否决

## 反模式

- **grill 期间修改代码** — 绝对禁止。grill 是设计阶段，不是实施阶段
- **批量更新词汇表** — 术语确定后立即更新，延迟记录会导致后续讨论基于过时定义
- **把 CONTEXT.md 当 spec 写** — 它是词汇表，不是功能规格或设计文档
- **记录显而易见的决策** — "我们用 REST API" 不需要 ADR
- **同时问多个问题** — 逐一提问，等待反馈后再继续
