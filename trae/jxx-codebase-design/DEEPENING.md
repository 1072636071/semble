# 深化

如何在给定依赖的情况下安全地深化一组浅模块。假设 [SKILL.md](SKILL.md) 中的词汇 — **模块**、**接口**、**接缝**、**适配器**。

## 依赖类别

评估深化候选者时，对其依赖分类。类别决定了深化模块如何跨接缝（seam）测试。

### 1. 进程内

纯计算、内存状态、无 I/O。始终可深化 — 合并模块并直接通过新接口测试。不需要适配器（adapter）。

### 2. 本地可替代

有本地测试替身的依赖（Postgres 用 PGLite、内存文件系统）。替身存在则可深化。深化模块用测试套件中运行的替身测试。接缝是内部的；模块外部接口处没有端口。

### 3. 远程但自有（端口与适配器 / Ports and Adapters）

跨网络边界的你自己的服务（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深模块拥有逻辑；传输作为**适配器**注入。测试使用内存适配器。生产使用 HTTP/gRPC/队列适配器。

推荐措辞：_"在接缝处定义端口，为生产实现 HTTP 适配器、为测试实现内存适配器，使逻辑集中在一个深模块中，即使它跨网络部署。"_

### 4. 真正外部（Mock）

你无法控制的第三方服务（Stripe、Twilio 等）。深化模块将外部依赖作为注入端口接收；测试提供 mock 适配器。

## 接缝纪律

- **一个适配器意味着假想的接缝。两个适配器意味着真正的接缝。** 除非至少有两个适配器有合理依据（通常是生产 + 测试），否则不要引入端口。单适配器接缝只是间接层。
- **内部接缝 vs 外部接缝。** 深模块可以有内部接缝（私有于实现，仅供自身测试使用）以及接口处的外部接缝。不要仅因测试使用了内部接缝就通过接口暴露它们。

## 测试策略：替换，不要分层

- 一旦深化模块接口处的测试就位，浅模块上的旧单元测试即成废料 — 删除它们。
- 在深化模块的接口处编写新测试。**接口是测试面**。
- 测试通过接口断言可观察的结果，而非内部状态。
- 测试应在内部重构后存活 — 它们描述行为，而非实现。如果实现变更时测试必须变更，说明它测试的是越过接口的内容。
