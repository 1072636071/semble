### 2026-09-13 10:16 · 第 8 问（待答）· 「漏需求」是哪一类

### 2026-09-13 10:18 · 第 9 问（待答）· 验收框证据化怎么落地

针对 A 类漏需求（也是「A 没信号」的解药）：

- A. **框后强制附证据（格式约定 + 脚本校验）** —— 每条 `- [x]` 后必须跟 `→ 证据：<命令 / 用例名 / 文件:行>`，脚本校验格式合规。
  - 优点：机器可判定格式；复用既有 grep 核验路子（工单 11 已是 grep 派）。
  - 缺点：**证据可造假**（写个不存在的用例名也能过），只校验格式不校验真伪。
- B. **证据必须可复现（校验器真去跑/真去查）** —— 用例名要能被 grep 到、命令要 `exit 0`。
  - 优点：**证据真伪可机器验证** —— 这是真硬闸，与决策 1 完全一致。
  - 缺点：校验成本高（要执行命令）；部分需求无法用单条命令验证。
- C. **双 agent 交叉验证** —— 一个写，另一个独立按验收框逐条复核且必须自己跑命令。
  - 优点：抓得住「假证据」。缺点：成本翻倍，且两 agent 可能同源出错。

主 agent 倾向 **A + B 分层**：格式强制（A）+ 可执行项要求真跑（B）；无法执行的项降级为「人工确认项」并显式标注（不许混在 `- [x]` 里）。

### 决策 9 · 验证职责分界 + 分流判据（2026-09-13 10:25，用户给定）

> 「尽可能 agent 验证，agent 验证不了的，还有 UI 交互，让人工验证。人工关注功能是否好用、体验是否舒适。AI 关注功能是否能用、是否有这个功能。」

**这是本次 memorial 最重要的语义约定，直接改写第 11 问的前提**：

| 维度 | 归属 | 判据 |
|---|---|---|
| **功能是否存在 / 是否能用** | **AI / 机器** | 可写成程序断言（存在性 + 功能性） |
| **是否好用 / 体验是否舒适** | **人** | 不可程序化（主观质量） |
| **UI 交互** | **人** | 用户显式点名划归人工 |

**⇒ 分流判据（取代第 11 问的白名单思路）**：不是按文件类型分，而是按**验证目标的性质**分 ——
**「这个验收点能不能写成一条程序断言？」**
- **能** ⇒ 机器验证（附可复现证据，决策 6）。
- **不能**（主观体验 / 视觉 / 手感 / 交互流畅度）⇒ 进人工验证清单（决策 8）。

**两条配套纪律**：

1. **举证责任在 agent**：默认**必须**给机器验证 —— 只有当 agent 能说明「此点无法程序断言」时才允许进人工清单（防逃逸，比白名单更本质）。
2. **白名单收缩到只剩 UI 一类**：脚本交叉检查仅需覆盖「diff 触及 UI/前端交互层却无人工清单条目」⇒ 校验失败。维护面从「全类型白名单」缩到「一类」，符合「从轻」约束。
