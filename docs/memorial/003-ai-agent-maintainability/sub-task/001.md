### 3. Top 5 缺口（按「最阻碍 agent 自主改动」排序）

**缺口 1 · MemoryCore 完全无类型检查（353 文件 / 占全仓源码 49%）**
- 表现：包根无 `tsconfig.json`；现存 7 个 tsconfig 无一覆盖 `src/` 主源码；无 `typecheck` script；`tsdown.config.ts` 设 `dts: false`；CI 的 MemoryCore 只做 `npm install` + `npm pack` + `npm pack --dry-run`，**从不跑 `npm test`**。
- 为什么阻碍：agent 改一个函数签名、改一个接口字段类型、删一个导出，在 MemoryCore 里**没有任何一条命令会报错**，只能等 109 个 vitest 用例里恰好命中——而类型错误通常不表现为断言失败，会一路带到运行时。这是全仓最大的「改完不知道对不对」的黑洞，且它偏偏是最大的包。

**缺口 2 · 全仓后端零静态检查（6/7 包无任何 linter）**
- 表现：根目录无 eslint/biome/oxlint/prettier 配置；7 个一级包中只有 `MemoryPanel/web/` 有 `.eslintrc.cjs` + `.prettierrc` 并接进 scripts；其余 6 包约 719 个 src 文件无任何 linter，也无 `lint` script。
- 为什么阻碍：未使用变量/导入、误用 `await`、错误的错误处理、`any` 扩散、格式漂移——这类问题本可由 `eslint --fix` 一秒机器化，现在只能靠人 review。同时**没有统一 formatter，agent 每次改动都会产生大量无关 diff**，污染后续 review 与 diff 判定。

**缺口 3 · CI 只覆盖 2/7 包，agent 改动无机器拦截**
- 表现：`.github/workflows/pr-ci.yml` 共 7 个 job，全部只覆盖 MemoryCore（install / pack / size / isolation）与 MemoryKnowledge（typecheck + test + build）。**MemoryPanel / MemoryGateway / MemoryMCP / MemoryProxy / MemoryAdmin 5 个包完全不在 CI 中**；MemoryCore 在 CI 中也只 `npm pack`，不跑测试。
- 为什么阻碍：这 5 个包的「通过」完全依赖 agent 自己记得 `cd <包> && npm run typecheck && npm test`。而根 `AGENTS.md` 里一条命令都没写（见缺口 5），agent 大概率不跑 → 错误在无人拦截的情况下合入，且**没有任何历史信号可供 agent 学习「怎样算通过」**。

**缺口 4 · MemoryCore 多个 script 指向不存在的文件（命令即失败）**
- 表现：
  - `build:seed-v2` = `tsc --project scripts/seed-v2/tsconfig.json` → `MemoryCore/scripts/` 下**无 `seed-v2` 目录**；而 `build` = `build:plugin && build:scripts`，`build:scripts` 串联了 `build:seed-v2` → **`npm run build` 必然失败**。
  - `test:oss` = `vitest run -c vitest.oss.config.ts` → `vitest.oss.config.ts` **不存在**。
  - `test:standalone:memory/skill/conv` 指向 `__tests__/standalone/*.sh`、`test:standalone:all` 指向 `scripts/e2e-standalone.sh` → `MemoryCore/__tests__` 目录**整体不存在**（`scripts/` 下也无 `e2e-standalone.sh`）。
  - `vitest.config.ts` 的 `include` 含 `__tests__/**/*.test.ts`，该目录不存在。
- 为什么阻碍：agent 的常规动作是「读 package.json → 跑 scripts」。在这里它跑一条坏一条，**无法区分「我的改动错了」还是「脚本本来就是坏的」**，反馈闭环从第一步就断了；更糟的是 agent 可能为了「让命令变绿」去臆造这些文件。

**缺口 5 · 跨包依赖无声明 + 包级导航文档缺失**
- 表现：
  - MemoryGateway 8 处 `../../MemoryMCP/src/*.js` 相对 import（含测试文件 `src/tools.test.ts:14`），`package.json` 的 `dependencies` 里没有任何 MemoryMCP 条目，也无 `workspace:` / `file:` 协议；全仓无根 `package.json`、无 workspace 包声明。
  - 跨服务耦合全部落在硬编码端口与 env 上：`127.0.0.1:8421`（Knowledge，4 个包引用）、`127.0.0.1:8123`（Admin）、`127.0.0.1:8096`（Panel）+ `KNOWLEDGE_API_URL` / `DEFAULT_KNOWLEDGE_URL` / `TDAI_MCP_URL` 等。
  - **7 个包无一有 `AGENTS.md` / `CONTEXT.md`；MemoryGateway 与 MemoryAdmin 连 `README.md` 都没有**；根 `AGENTS.md`（70 行）零验证命令。
- 为什么阻碍：agent 改 MemoryMCP 的一个导出，**没有任何机器手段告诉它 MemoryGateway 会一起炸**（无依赖声明、无 CI 矩阵、无类型层面的包边界）；改 8421 端口的接口契约，Panel/Gateway/Admin 三处静默失效。同时 agent 打开一个包根目录时，没有任何文档告诉它「这条命令跑通 = 我改对了」，只能靠摸索或猜。

（备选第 6：MemoryProxy **无 `build` 脚本**，无法验证「能否产出可运行产物」；MemoryMCP 仅 2 个测试覆盖 6 个源文件，「测试通过」几乎不构成正确性信号。）

### 4. 一句话改造靶心

`MemoryCore 补根 tsconfig + typecheck 脚本` → `全仓加一个根级 linter/formatter 并接进 scripts` → `CI 扩展到 7 个包` → `修掉 MemoryCore 的僵尸 script` → `MemoryGateway/MemoryMCP 依赖显式化 + 每包补 AGENTS.md（含验证命令）`。
