**「两个 agent 各起一套会具体怎么炸」——三个层次，按危险度升序**

1. **同 cwd 起两套 ⇒ 启动即失败（最安全）**：`8421` 已被占用 ⇒ 第二个 KS `EADDRINUSE` 退出。**这是唯一「吵得响」的失败**，agent 能看见。

3. **SQLite 文件锁 + WAL（最隐蔽）**：`knowledge.db` / `codegraph.db` / `hits.sqlite` 均为 SQLite。两个进程同时开同一 DB ⇒ SQLite 用 `-shm`/`-wal` 做跨进程锁：读可并发，**写会 `SQLITE_BUSY` 或长事务互斥**；若一方以默认 `journal_mode` 挂起再做 checkpoint，另一方可能读到**半合并的 WAL**。⇒ 表现为**间歇性「数据库被锁」/「disk I/O error」/查到的数据时有时无**——最难归因的一类故障。

### 3. 一句话结论（第一因）

**当前「只能一个 agent 改代码」的第一因不是 git 文件冲突，而是「本机共享单例资源」——具体地，是第 1+2 项的组合：三个硬编码端口（8421/8123/8096）各自的默认 URL 指向固定端口，叠加以 `./data` 相对路径落盘的活 SQLite 热库（`knowledge.db` 带 482KB 未合并 WAL、`codegraph.db` 带 927KB WAL）。两个 agent 各起一套服务时，最坏情况不是「启动报错」（那还好），而是「第二个 agent 静默地把数据写进第一个 agent 的库」——这类故障机器不可检测、症状间歇、无法归因，因此用户被迫退回串行以换取可预测性。**

按严重度排序：**① 端口+默认URL（静默错库）> ② SQLite 热库并发（静默错乱/间歇锁）> ③ node_modules 4.1GB（隔离成本高，非正确性问题）> ④ .scratch/ADR 编号撞车（merge 冲突，痛但可见且可解）> ⑤ 跨包耦合（编译半成品）**。

### 4. 隔离方案的成本量级

- **「每 worktree 独立装依赖」= 每个 ~4.1GB（首次），且必须 hoisted 平铺 + 重装 `better-sqlite3` 原生 binding（需系统 node 24 + `--use-system-ca`）。**
  - 各包拆开看：MemoryCore 单靠一个就 2.6GB（占 63%）；Knowledge 639MB；Proxy 371MB。
  - 若「一个 agent 一个 worktree、且只装自己负责的包」⇒ **133MB（MCP）～2.6GB（Core）**，中位数 ~370MB。
  - 若「每 worktree 全量装」⇒ **4.1GB/个**，2 个 agent 即 **8.2GB**，3 个即 12.3GB。**这是量级判断：GB 级，不是百 MB 级。**
- **「不独立装、共用 node_modules」——不可行**，三条硬理由：
  1. **物理不可共享**：`node_modules` 是 per-package 实体目录（7 份独立），git worktree 会给每个工作树新建空目录；要共用只能做 symlink/junction。
  2. **symlink 正是本仓库已踩且已放弃的坑**：`MEMORY.md:24` 明记「reparse point 任何进程解析不了 ⇒ pnpm 链接式 node_modules 全废」，7 个包**现已全部是 real dir（实测）**——说明团队已用「放弃共享、全部平铺」换取了可运行性。**走回头路 = 复活已知必炸的坑。**
  3. **`better-sqlite3` 原生 binding 与 node ABI/路径绑定**：共用会在 Node 版本切换（Knowledge 用 node 24 / knowledge-web 用 node 22）时直接 `NODE_MODULE_VERSION` 崩溃。
- **可行的折中（成本递减）**：
  1. **不新建 worktree，改为「进程级隔离」**：env 套件错开端口组（8421→18421 等）+ 绝对路径 `KNOWLEDGE_DATA_DIR`/`baseDir` 指向 `.temp/agent-<id>/data`。成本 ≈ 0（复用唯一一份 node_modules），但**要求全链路端口/env 成套替换**，且 `.temp` 下的库仍会各自复制一份数据（小，仅 KB 级起）。
  2. **worktree 只给「必须真跑服务」的 agent**，纯代码改写（文档/类型/重构）继续共用主工作树 —— 因为代码级并发其实只有 A.2 那几个编号/单文件冲突。
  3. **优先级更高的是先修「编号分配」与「AGENTS/CODEBUDDY 单源」**：这两项是**纯 git 层、零成本**，却直接解锁「多 agent 并行改代码」的大部分场景（因为绝大多数改动不碰端口与服务）。

⇒ **对改造方案的建议：不要先上 git worktree（4.1GB/份、复活 symlink 坑）；应先做「端口组 + 数据目录 env 化 + 编号分配去竞争」这三件零/低成本事，把「并行」的边界从「整机单例」收缩到「进程参数」。**
