# ADR-0003 · 不可机器验证项必须显式入「人工验证清单」

状态：已接受（memorial 020 内部）
日期：2026-09-13

## 背景

ADR-0001 禁止「勾了完事」，ADR-0002 定下分流判据。剩下的问题是：**被分流到人工的那部分，落到哪里、怎么保证不被遗忘。**

用户提出（2026-09-13 原话）：

> 「每次改动就记录一个需要人工验证的点或者流程。本地放在一个独立的清单，如果使用本项目的 task 管理能力的话，就新增一个 task。」

现状问题：`.scratch/27-board-quickwins/issues/01-comment-kernel-api.md` 里，「缺用例」这件事被写在 `## 评论` 的散文里 —— **不是可勾选的条目，不进任何清单，无人跟踪**。信息在，但不可执行。

## 决策

**不可机器验证的验收点，必须转为「人工验证清单」条目；双落点：本地清单 + 本项目 AgentTask。**

- **触发时机**：`jxx-implement` 硬出口 —— 第一轮功能开发完成、置 `pending-review` 之前，逐条给验收框分流。
- **本地落点**：`.scratch/<NN>-<effort>/HUMAN-CHECK.md`（工单域内，随工单归档、可跨会话）。
  - **禁止用 `.temp/`** —— 该目录被 `.gitignore` 且语义是临时；人工验证清单需要留存。
- **线上落点**：本项目 AgentTask（任务通道）新增 `task_type=human_verify`，payload 含：来源工单 / 验证步骤 / 预期结果 / 关联 commit。
  - **按工单聚合一张卡**（复用 CONTEXT.md 既有「待抽取待办卡」的防刷屏模式），而非一条一卡。
- **条目字段**：验证点 · 操作步骤 · 预期结果 · 未验证的后果 · 由哪条验收框降级而来。
- **闭环**：人工验证完成后勾选（本地）/ 任务状态流转（线上）。人的入口已具备（CONTEXT.md「通道三分」已定义 `actor=user|agent`）。

## 理由

- **把「不可验证」显式化，而不是让它消失**。这是「漏需求」的直接解药：过去它消失在评论区，现在它是一条待办。
- **双落点各有分工**：本地清单随 git 走、可离线、与工单同生命周期；AgentTask 让待办进入既有的任务看板与通知矩阵，人不会漏看。
- **复用既有机制而非新建**：AgentTask 已是本项目唯一任务通道（`AgentTask` 是唯一任务通道，旧看板已下线），`human_verify` 只是新增 `task_type`（该字段本就自由扩展、不设白名单）。符合「从轻」。
- **自举**：用本项目自己的能力管理本项目的改造。

## 被否决的替代方案

- **写进工单 `## 评论` 散文** —— 现状做法，不可勾选、无人跟踪，已被证明会漏。
- **放 `.temp/`** —— 会被清理、不进版本库，跨会话即丢。
- **每条验证点一张 AgentTask 卡** —— 刷屏，与既有「按知识库聚合一张待抽取卡」的既定反刷屏模式冲突。
- **新建独立系统（专门的验证清单服务/表）** —— 与「不要特别重」冲突，且与 AgentTask 功能重叠。

## 影响

- `jxx-implement` skill 需新增分流步骤与清单模板。
- MemoryCore 侧新增 `task_type=human_verify` 的使用约定（无需新表，`task_type` 自由扩展）。
- `issue-tracker.md` 的 done 硬闸需增加一条：**存在未勾选的人工验证项时不得置 `done`**（或显式标注为待人工验证并保留 `pending-review`）。
