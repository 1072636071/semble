# ADR-0002 · 验证职责分界：机器管「有没有 / 能不能用」，人管「好不好用 / 体验」

状态：已接受（memorial 020 内部）
日期：2026-09-13

## 背景

ADR-0001 要求「每条验收框必须二选一：机器验证 或 人工验证」。但**分流的判据**若不明确，agent 可以把该机器验的推给人工以逃避（回到自述问题）。

用户给出了职责分界（2026-09-13 原话）：

> 「尽可能 agent 验证，agent 验证不了的，还有 UI 交互，让人工验证。人工关注功能是否好用、体验是否舒适。AI 关注功能是否能用、是否有这个功能。」

## 决策

**按验证目标的性质分流，不按文件类型分流。判据 = 「这个验收点能不能写成一条程序断言？」**

| 维度 | 归属 | 判据 |
|---|---|---|
| 功能是否存在 / 是否能用 | **AI / 机器** | 可写成程序断言（存在性 + 功能性） |
| 是否好用 / 体验是否舒适 | **人** | 不可程序化（主观质量） |
| UI 交互 | **人** | 用户显式点名划归人工 |

两条配套纪律：

1. **举证责任在 agent** —— 默认**必须**给机器验证；只有当 agent 能说明「此点无法程序断言」时才允许进人工清单。
2. **白名单收缩到只剩 UI 一类** —— 校验脚本仅需覆盖「diff 触及 UI / 前端交互层却无人工清单条目」⇒ 校验失败。

## 理由

- **比按文件类型分更本质**：同一个文件里可能既有可断言的逻辑，也有只能人看的交互；按目标性质分才不会误判。
- **符合「尽可能 agent 验证」的倾向**：默认交给机器，人工是例外而非常态。
- **白名单只留一类**，维护面最小，符合用户「不要特别重」的约束。
- **人的注意力被引导到真正需要判断的地方**（好不好用），而不是让人去重测机器本该测的东西（有没有这个功能）。

## 被否决的替代方案

- **按文件类型白名单分流（如后端必机器验、前端必人工验）** —— 会把「UI 组件里的纯函数逻辑」也推给人工，判据错位。
- **完全由 agent 自行判断分流** —— 可逃逸，且与 ADR-0001 的根本问题同构。
- **按改动行数 / 文件数阈值分流** —— 与「验证目标能否程序化」无关，是无关变量。

## 影响

- 人工验证清单（ADR-0003）的条目来源被限定为「体验 / 视觉 / 手感 / 交互流畅度」类。
- 校验脚本的 UI 白名单需要一份「UI / 前端交互层」路径清单（本项目 = `MemoryPanel/web/`、`MemoryPanel/knowledge-web/`、各前端组件与样式目录）。
- 「功能存在性」类验收点不允许以「人工验证」名义出逃。
