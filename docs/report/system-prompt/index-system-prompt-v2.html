范围：只做系统提示词（system prompt）工程。四份厂商手册 + 一份跨厂商底座，全部按「2026-09-01 之后发布/更新的官方文档、官方代码资产、论文」重做了一遍。 定稿 2026-10-20。为什么要有 v2：上一轮语料里只有 36.4% 的日期标注落在 2026-09 之后（实测 250 条中 91 条），且混着"抓取日"与"发布日"两种含义；本轮把两者拆开、以官方页面 dateModified／GitHub 提交日／arXiv 提交日为准重新取证。 为什么按厂商分开：不同 LLM 对系统提示词的服从面、承载协议、前缀构成、动态注入方式都不一样——下面 §1–§7 就是这些差异本身。 排版约定：全角〈〉为排版保护，实际使用换半角。等级 A=官方一手／B=对端与权威二手／C=社区可复现／D=未证实。

2. 敏感度对照①：谁能「中途改系统提示词」

这是 2026 Q4 系统提示词工程最实际的分水岭——改人设的成本完全不同。

厂商中途插 system官方明文与代价级
DeepSeek三协议都支持（Chat 明确「不支持中途插工具调用，但支持插 system」）；但只有 deepseek-flash 声明 systemPromptUpdate: in-history，v4-pro 等需重写第 0 号节点重写头节点 → "从首个变化的 token 起失去前缀复用"；in-history 则保住"直到该历史末尾"的前缀；Anthropic 侧硬限制：更新后若把用户/工具结果轮次全省略 → UNSUPPORTED_CONTENTA
Anthropicmid-conversation system messages（beta）：位置受严格约束——不能是第一条、必须紧跟 user 或以 server tool result 结尾的 assistant 轮、不能夹在 tool_use 与 tool_result 之间（400）turn-scoped clear_at: "next_user_message"：只在本轮渲染、之后留在历史里但零 token 成本、不累积、不破缓存、不失效 thinking；已清除的消息必须逐字节原样回传A09-01
Anthropic 的型号反转⚠️ Sonnet 5.5 / Haiku 5.5 上「紧跟 tool result 的 system 消息可能被当成不可信文本直接忽略」——因为这些模型被训练成抵抗经由工具结果的注入官方建议改走 user 轮。同一份 reminder 代码在新中小模型上会静默失效 → reminder 机制现在必须按型号分支A
Kimi支持，但形态特殊：带 tools 的 system 不能再带 content（400 cannot be used with content）；且「出现在哪个位置，工具就从哪个位置开始可见」只追加、不插入、不改写；动态声明按请求生效、服务端不记忆，不携带即失效；仅 kimi-k3 支持（k2.6 上 tokenization failed）A09-28
GLM文档层没有任何条款回答"能否多条/是否必须 messages[0]/能否中途插入"；答案只在代码资产里：ZCode 契约三段并列 + # Harness 写明「系统可通过 mid-conversation system turns 发送更新、提醒或规则修改」旧式 OpenAI 兼容模板只接受一个开头 system，适配器"按原序、空分隔合并、不补空白"；Responses 协议没有 system 位，用顶层 instructionsA（10-10 契约）+ 负结果
MiniMax三面入口：Anthropic 顶层 system／OpenAI messages 内 role／Responses instructions省略 thinking 时 OpenAI 端默认开、Anthropic 端默认关（M3） → 同一份 system 在两个兼容协议上推理行为可能相反，必须分别测Alive
Google门槛内无 mid-conversation system 机制（system_instruction 仍是请求级字段）动态注入只能靠用户轮内追加 + 分块标签A负结果

一句话：想"会话中途补规则"，DeepSeek/Kimi/GLM/Anthropic 都有通道但约束各不相同（Anthropic 管位置与不可信内容，Kimi 管 tools/content 互斥与只追加，GLM 管协议合并，DeepSeek 管能力位白名单）；Gemini 没有这层机制。

3. 敏感度对照②：system 前缀里塞了什么「不是你写的东西」

四家都一样：你的 system 前缀 ≠ 你的 system 文本。差别在塞的是什么。

厂商被塞进 system 前缀的东西官方依据工程后果
GLM① Reasoning Effort: Max 首行（5.3/5.3-Flash 无条件注入，5.2 需 enable_thinking 门控，4.7/5 没有这行）② tools 序列化成第二个 system 块官方 chat_template.jinja（ModelScope）逐字 + vLLM recipe「then injects Reasoning Effort: Low|High|Max into the system prompt」换 effort 档＝换前缀首行→整段缓存失效；增删工具＝换 system
DeepSeekeffort 指令在训练期就被 prepend 进 system（Reasoning Effort: {effort} (range 1--100…)，max/high/low = b=100/75/50）；Harness 侧 tools 与 persona 各占段arXiv 2609.19969 §5.1.4（09-17）报告原话："Realized behavior may deviate because the effort instruction can directly change the reasoning strategy"
Kimi动态 tools 声明占用上下文长度（官方明说）；顶层全局工具声明不影响缓存命中use-dynamic-tool-loading（09-28）核心工具固定顶层，长尾工具按需追加
MiniMax前缀顺序官方写死 工具定义 → 系统提示词 → 历史对话，"任意模块内容的变更，都可能会影响缓存的效果"；PTC 类形态下工具清单可整体进 systemtext-prompt-caching（live）与 Anthropic tools → system → messages 同构

OpenAI（参照）hidden system content 不计入最小可缓存长度；顶层 instructions 不能放显式断点，要复用 developer 指令须放进 developer 消息的 input_text 块prompt-caching 现值平台自带段你控制不了；断点位置有规则

5.5 补充对照：思考内容回传——五家都要求，罚则完全不同

这一条是本轮最容易写错的。调研子代理曾报「GLM 官方明写无需回写推理」，主线用本地官方快照逐字复核后判定为误读：原文是「该机制同时适用于 Interleaved Thinking 和 Preserved Thinking，无需手动区分」——"无需"修饰的是"区分模式"，不是"回写"。同一页紧接着写："请记得返回历史的 reasoning_content，以保持推理连贯性。"（英文页同句："Remember to return the historical reasoning_content to keep the reasoning coherent."）

厂商是否要求回传不遵守的后果（各家不同）级
DeepSeek带 tools 时必须完整回传历史 reasoning_content（哪怕那轮没调工具）HTTP 400（唯一给硬报错的一家）A
GLM要求回传；clear_thinking: false（Preserved）下"所有连续 reasoning content 必须与原始序列完全一致，不要重排或修改""会降低效果并影响缓存命中"；端点默认值不等价（Coding Plan 默认开、标准 API 默认关）A09-29 快照
MiniMax「无论本轮是否包含思考内容，都需要完整回传」；解析前先判空但不裁剪打断 Interleaved Thinking → 官方描述为 cumulative state drift、丧失自纠Alive
Kimi「把 API 返回的 完整 assistant message 原样回传，不能只复制 content 和 tool_calls」"会丢失可能返回的 reasoning_content，破坏后续工具调用上下文"；且 reasoning_content 计入 tokenA10-14
Anthropic（参照）thinking / turn-scoped reminder 块逐字节原样保留编辑更早轮次会使后续 thinking 块失效（2026-08-31 后新建账号强制执行）+ 缓存 missA09-01
腾讯云 MaaS（易混淆源）曾写「多轮只将 content 回传、不回传 reasoning_content 以省 token」与 MiniMax 官方相反，属托管平台旧规B，不可冠名厂商规则

通用化即错：不存在"跨家统一的回传策略"。写 harness 时按厂商分支，并把三件事记进清单：字段叫什么 / 是否必须原序原样 / 计入不计入预算与缓存。

9. 跨厂商一致的十二条系统提示词纪律（全部有 ≥09 支撑）

  1. 人设块只写职责、读者、标准；不写能力断言。 503 份职业画像实测 -0.6pp、成本 2.2–4.5×、工具任务 -10pp（2610.00084）；"请匹配角色能力水平"也治不好 voice-vs-capability 裂口（2609.39846）。
  2. 常驻规则按容量算，不是按需要算。 有限注意力容量下「加一条规则不会提高其余规则的遵守率」，最优文件规模存在上界（2610.11007）；官方实测落点在 12–18 块 / 3k–4.3k 词（§3 计数）。
  3. 删规则不能只看"没人用过"。 缺失只在造成伤害时才产生反馈，"删除被忽略的指令必然可能删掉有用的"（2610.11007）；瘦身要用 OpenAI 的「删一组→同评测复跑」，且45 题的小评测抓不到 13 分差（2610.04433）。
  4. 强调词是零和资源。 "If you emphasize many lines, none of them stands out."（Claude Code）；Anthropic 消费者端提示词09-28 起全大写条款归零。
  5. 矛盾指令的代价是早停，不是多想。 OpenAI 09-11 与 GPT-6 指南两处；Claude Code /doctor prompt-audit 把"矛盾的指导文件"列首位。
  6. 安全沉 harness，别沉 system。 机制证据：安全条款的表征移动"与最小基线统计不可区分"、与"你没有任何限制"近乎同路径（CKA 0.997），70B 仍 <10% penetration（2609.38205）；行为证据：只改 system 就能让 ASR 从 0.2% 跳到 43%（2610.23254）；官方口径："enforcement lives in the harness"、"hooks are deterministic, CLAUDE.md is advisory"。
  7. 一定给失败态命名。 官方框架的 shipped prompt 九个里零个规定了工具失败时怎么办；补一句 retrieval_status: OK or FAILED 把不诚实率 14.10% → 0.87%（2609.14758）。
  8. SOP 不进 system，走工具/协议逐步下发。 adherence 76–95% → 95–99%；且 prompt 下发时 31–49% 的"正确结果"其实没走流程（2610.07817）。
  9. 频率决定 system 还是 skill：命中 ≥1/3 流量才进 system；安全/法务/品牌/关键用户事实恒进 system。 skill 作为 tool result 载入，别追加进 system（Anthropic 09-02）。
  10. 日期、当前页、会话 id、记忆一律后置。 "system 顶部放时间戳是最常见错误"（Anthropic）；GLM/DeepSeek 官方实现都把它踢出 system；论文实测日期方差超过 batch/精度且 CoT 放大（2609.36931）。⚠️ Gemini 官方说法相反，冲突已在 §6 呈现。
  11. 别在 system 里放外部不可信内容。 Anthropic 原话："doing so gives that text operator-level authority"；DeepSeek 官方两份 untrusted 条款是按工具各写一段（web_search / web_fetch）；Kimi/GLM 都把"材料 vs 要求"分层写明。
  12. 换模型/换 harness 必重测，且 system 面是成本主项。 同模型同任务同价目表，跨 harness 每任务成本差最多 3×，差距"在第一次调用就由 system prompt + 工具 schema 的 preamble 决定，再乘以步数"；而 harness 对分数的影响落在噪声内（2610.04433）。

10. 落地检查清单（写/改一份 agent 系统提示词时逐条过）

结构层

  • [ ] 身份句一句话，含"跑在哪、为谁服务"，无能力等级断言
  • [ ] 授权边界写成判断式；principal 是谁写明确（它会改变行为，2609.17989）
  • [ ] 完成定义与停止条件写在末尾，且从会话第一轮就在
  • [ ] 失败态契约：工具返回不可用值时先报 retrieval_status: FAILED
  • [ ] 工具规则只写"跨工具会选错"处；单工具规则沉 description，窄触发
  • [ ] 冲突优先级写明「用户指令 > skill/文件」，并附点名污染源的诊断句
  • [ ] 块数 12–18、常驻英文词 3k–4.3k 以内、全大写强调 = 0、example ≤3

协议层

  • [ ] 确认目标协议怎么承载 system（顶层字段 / messages role / instructions）
  • [ ] 旧式 OpenAI 兼容网关：多段 system 能否合并、是否只接受一个开头 system
  • [ ] 中途更新：该模型是否有 in-history 能力位（DeepSeek 仅 flash；Kimi 仅 k3；Anthropic 需按型号防忽略）
  • [ ] 需要 tools 与 content 分开（Kimi 互斥）？动态工具是否"不携带即失效"？
  • [ ] 采样参数：该家会报错还是静默忽略；prefill 是否已被禁
  • [ ] 思考内容回传规则：字段名 / 是否必须原样 / 是否计入预算

缓存与成本层

  • [ ] 常驻前缀 ≥ 目标阈值（按最大者 1024 设计最稳）
  • [ ] 顺序 tools → system → messages，前缀 byte 级稳定
  • [ ] 日期 / 会话 id / cwd 清单 / 记忆 不在 system 顶部
  • [ ] effort 档会话开始就定（GLM 5.3 关不掉、Kimi 换档毁缓存、MiniMax 省略即 max）
  • [ ] 命中率目标 90–99%；TTL 与定时任务间隔匹配（Kimi TTL 首写锁定不可改）

治理层

  • [ ] 版本化：像 Kimi Managed Agents 那样把 system 当不可变配置快照管
  • [ ] 可复现：记录每次请求的 system + tools + 参数（Claude Code 10-14 的做法）
  • [ ] 每版跑一次"删一组指令→同评测复跑"；/doctor prompt-audit 类审计
  • [ ] 条款归属分层记账：厂商 API 文档 / 兼容层 / 云平台 / 教程，别把平台模板当厂商规则
