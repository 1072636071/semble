# 目标契约（GOAL.md）

`GOAL.md` 是目标模式循环的唯一判停依据。它在契约固化阶段生成，在执行循环每轮被对照，在交付时用于验收。**写入 `.goals/{name}/GOAL.md`**（按目标名称隔离存储），不再写入项目根目录。

> 相关文件：[acceptance-patterns.md](acceptance-patterns.md)（验收标准设计模式）、[constraint-design.md](constraint-design.md)（约束设计）、[grilling-guide.md](grilling-guide.md)（grilling 问题模板与推进策略）

## 存储位置

```
工作区根目录/.goals/
├── _index.md                    # 目标索引
├── {goal-name}/
│   ├── GOAL.md                  # 契约
│   ├── PROGRESS.md              # 执行进度
│   └── EVIDENCE.md              # 交付证据
```

- `{goal-name}` 为 kebab-case，从交付物描述中提取
- 多个目标互不干扰，各自独立目录
- `_index.md` 追踪所有目标状态

## 模板

```markdown
# Goal

<一句话：交付物形态 + 意图。不含"怎么做"。>

# Acceptance

1. <可观测、可独立判定的断言>（验证：`<可执行命令>`）
2. ...
   （每条必须能被外部观察者据此判定通过/失败，且绑定可执行验证命令。≥ 3 条。
    无法命令化的降级为绑定外部产物 + 检查清单，如 `（验证：截图 <路径> + 检查单：<项>）`。）

# Constraints

- <边界：技术栈/风格/范围/不可改动项/伦理>
  （划边界，不写步骤。≥ 3 条：技术栈 + 范围 + 保护性约束。）

# Budget

- 最大轮数：<N>（必须）
- 时间上限：<如 2h>（必须）

# Pause Conditions

- <高风险暂停条件：凭证/付费/生产数据/法律/版权/发布>
  （至少显式声明"无"或列出具体场景。不可留空。）
```

## 深度下限

| 字段             | 下限要求                                                                 |
| ---------------- | ------------------------------------------------------------------------ |
| Goal             | ≥ 1 句，必须包含交付物形态 + 意图                                      |
| Acceptance       | ≥ 3 条，每条必须含独立证据来源 + 绑定验证命令（`（验证：\`<命令>\`）`） |
| Constraints      | ≥ 3 条（技术栈 + 范围 + 至少一条保护性约束）                             |
| Budget           | 最大轮数 + 时间上限，缺一不可                                           |
| Pause Conditions | 至少显式声明"无"或列出具体场景                                          |

## 示例

```markdown
# Goal

一个命令行工具 `linkcheck`，扫描一个 Markdown 目录下的所有本地链接，报告失效链接（指向不存在文件/锚点）的列表。

# Acceptance

1. 运行 `linkcheck ./docs` 能扫描 docs 下所有 .md 文件的本地链接（相对路径 + 锚点）。（验证：`python -m linkcheck ./docs --verbose` 输出覆盖 docs 全部 .md 文件）
2. 对一个含 3 个已知失效链接的 fixture 目录，输出恰好包含这 3 条，无遗漏无多余。（验证：`python -m linkcheck tests/fixtures/broken > /tmp/out.txt; diff /tmp/out.txt tests/fixtures/expected.txt` 无差异）
3. 退出码：发现失效链接返回 1，全部有效返回 0。（验证：`python -m linkcheck tests/fixtures/broken; echo $?` 输出 `1`；`python -m linkcheck tests/fixtures/clean; echo $?` 输出 `0`）
4. `linkcheck --help` 输出用法说明，包含至少一个示例命令。（验证：`python -m linkcheck --help` 退出码 0 且输出含示例命令行）

# Constraints

- 语言：Python 3.11+，仅标准库，不引入第三方依赖。
- 不修改被扫描目录的任何文件（只读）。
- 输出格式为纯文本，一行一条失效链接，格式 `文件路径:行号 -> 失效目标`。

# Budget

- 最大轮数：8
- 时间上限：1.5h

# Pause Conditions

- 需要安装第三方依赖才能完成核心功能时暂停
- 需要修改被扫描目录中的文件时暂停
```

## PROGRESS.md 模板

每个目标目录下必须初始化 PROGRESS.md：

```markdown
# 执行进度

- 目标名称：{name}
- 当前轮数：0
- 状态：契约中

## 每轮必读（执行任何动作前先读完本块）

- 我在跑目标循环，目标名称：{name}
- 当前轮数：0 / 预算上限：<从 GOAL.md Budget 填入>
- 当前切片：待拆解
- 本轮结束必须：跑验证命令 → 更新本文件（轮数 + 切片状态 + 循环日志）→ 对照 GOAL.md Acceptance 检查是否全部通过
- 禁止用"我觉得完成了"作为证据——每条验收的通过证据必须来自其绑定验证命令的实际运行输出
- 凭记忆续跑 = 违规：状态以本文件为准，不以对话记忆为准

## 固化日志

（记录否决门自检/独立检查结果，每轮修正追加）

| 门  | 自检结果 | 独立检查结果 | 修正说明 |
| --- | -------- | ------------ | -------- |
| V1  |          |              |          |
| V2  |          |              |          |
| ... |          |              |          |
| V10 |          |              |          |

## 验收进度

| #   | 验收条件 | 验证命令 | 状态   | 证据 |
| --- | -------- | -------- | ------ | ---- |
| 1   | <验收1>  | `<命令>` | 待验证 | -    |
| 2   | <验收2>  | `<命令>` | 待验证 | -    |

## 切片状态

| #   | 切片 | 状态     | 验证结果       | 备注 |
| --- | ---- | -------- | -------------- | ---- |
| -   | -    | -        | -              | 执行阶段填写 |

## 循环日志

（每轮追加：做了什么 → 验证命令输出 → 所学/调整）

## 阻塞项

- 无
```

## 填写要点

- **Goal 只说"什么"**。出现"用 React""先建数据库"等步骤词，说明混入了 Constraints 或拆解——剥离出去。Goal 必须包含交付物形态（代码/文档/工具/报告）+ 意图（解决什么问题）。
- **Acceptance 来自独立来源，且绑定验证命令**。每条验收的"通过"判定不能依赖 AI 自述——它必须是某条命令的实际运行结果。每条验收末尾以 `（验证：\`<命令>\`）` 绑定验证命令（测试/脚本/退出码/grep 检查）；无法命令化的降级为绑定外部产物 + 检查清单。详见 [acceptance-patterns.md](acceptance-patterns.md)。每条验收必须附证据来源说明。≥ 3 条。
- **Constraints 划边界**。描述"不可逾越的线"，而非"该走的路"。详见 [constraint-design.md](constraint-design.md)。≥ 3 条（技术栈 + 范围 + 保护性约束）。
- **Budget 必填**。没有预算的循环没有终止条件，会陷入"再改一点"。最大轮数和时间上限缺一不可。
- **Pause Conditions 必显式声明**。只放需要人类决策的场景（账号/付费/生产/法律/版权/发布），低风险不确定性写成工作假设放 Constraints。即使无高风险场景，也必须显式声明"无"——留空等于未思考。

## 否决门

契约写入前必须通过全部否决门，详见 SKILL.md 中的"契约否决门"章节（含 V10）。任一否决 = 不可写入。

## 契约一旦固化

契约固化后即冻结。后续如需调整，遵循 SKILL.md 中"契约一旦固化"的规则——不擅自改，先向用户说明并取得确认。
