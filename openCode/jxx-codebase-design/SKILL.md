# 代码库设计

设计深模块：大量行为隐藏在小接口之后，接口置于干净接缝处，且可通过该接口测试。目标是：为调用者提供杠杆（leverage），为维护者提供局部性（locality），为所有人提供可测试性。

## 词汇表

精确使用这些术语——不要替换为"组件"、"服务"、"API"或"边界"。

- **模块（Module）** — 任何具有接口和实现的单元。刻意不限定规模：函数、类、包或跨层切片。避免：unit、component、service。
- **接口（Interface）** — 调用者为正确使用模块必须了解的一切：类型签名，以及不变量、顺序约束、错误模式、所需配置和性能特征。避免：API、signature。
- **实现（Implementation）** — 模块内部，即其代码体。与适配器不同：一个模块可以有小适配器大实现（Postgres 仓库）或大适配器小实现（内存 fake）。
- **深度（Depth）** — 接口处的杠杆：调用者每单位接口学习量所能行使的行为量。大量行为隐藏在小接口之后时模块是深的；接口几乎和实现一样复杂时是浅的。
- **接缝（Seam）** — 无需编辑该处即可改变行为的位置；模块接口所在的位置。接缝放在哪里本身是一个设计决策。避免：boundary。
- **适配器（Adapter）** — 在接缝处满足接口的具体事物。描述角色（填充什么槽位），而非实质。
- **杠杆（Leverage）** — 调用者从深度中获得的收益：每单位接口学习量获得更多能力。
- **局部性（Locality）** — 维护者从深度中获得的收益：变更、bug、知识和验证集中在一处而非分散在调用者中。

## 原则

- 深度是接口的属性，不是实现的。深模块内部可以由小的、可 mock 的、可替换的部分组成——它们只是不属于接口。模块可以有内部接缝（私有于实现）以及接口处的外部接缝。
- 删除检验（deletion test）。想象删除该模块。如果复杂性随之消失，它只是透传。如果复杂性在 N 个调用者中重新出现，说明它物有所值。
- 接口是测试面。调用者和测试穿过同一个接缝。若想测试越过接口，模块的形状可能不对。
- 一个适配器意味着假想的接缝。两个适配器意味着真正的接缝。除非确实有东西在接缝两侧变化，否则不要引入接缝。

## 为可测试性设计

- 接受依赖，不要创建依赖。`function processOrder(order, paymentGateway) {}` 可测试；`function processOrder(order) { const gateway = new StripeGateway(); }` 难以测试。
- 返回结果，不要产生副作用。`function calculateDiscount(cart): Discount {}` 可测试；`function applyDiscount(cart): void { cart.total -= discount; }` 难以测试。
- 小表面积。方法少 = 需要的测试少。参数少 = 测试设置简单。

## 不采用的表述

- 深度为实现行数与接口行数的比率（Ousterhout）：会鼓励堆砌实现代码。使用深度即杠杆。
- "接口"作为 TypeScript `interface` 关键字或类的公共方法：太窄——这里的接口包括调用者必须知道的每个事实。
- "边界"：与 DDD 的限界上下文含义重叠。说接缝或接口。
