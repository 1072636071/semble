# Triage

将项目 issue tracker 上的 issue 推过一个小型 triage 角色状态机。

triage 期间写入 issue 文件的每条评论必须以此免责声明开头：

```
> *This was generated by AI during triage.*
```

## 角色

两个分类角色：`bug`（某些功能损坏）、`enhancement`（新功能或改进）。

五个状态角色：

- `needs-triage` — 维护者需要评估
- `needs-info` — 等待报告者补充信息
- `ready-for-agent` — 已完全定义，可由 AFK agent 接手
- `ready-for-human` — 需要人工实现
- `wontfix` — 不会处理

每个经 triage 的 issue 应恰好携带一个分类角色和一个状态角色。若状态角色冲突，先标记并询问维护者。实际标签字符串可能不同——映射应已提供，若没有运行 `jxx-setup-matt-pocock-skills`。

状态转换：未标记的 issue 通常先进入 `needs-triage`；然后移至 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。`needs-info` 在报告者回复后返回 `needs-triage`。维护者可随时覆盖。

## Guidelines

- 维护者用自然语言描述需求（"给我看需要注意的事项"、"看看 #42"、"将 #42 移到 ready-for-agent"）。解释请求并执行。
- 展示需要注意的事项：查询 issue tracker，按最旧优先展示三个桶——未标记、`needs-triage`、`needs-info` 且报告者在上次 triage 备注后有活动。展示计数和每项一行摘要。
- triage 特定 issue 时：收集上下文（阅读完整 issue、解析之前 triage 备注、探索代码库、检查冗余性和先前拒绝）；推荐分类和状态并等待指示；验证声明（对 bug 按报告者步骤复现）；若需充实同时运行 `jxx-grilling` 和 `jxx-domain-modeling`。
- 应用结果：`ready-for-agent` 发布 agent 简报；`ready-for-human` 同结构但注明为何不能委托；`needs-info` 发布 triage 备注；`wontfix` 关闭（已实现则指向位置不写 `.out-of-scope/`，拒绝 bug 则礼貌说明，拒绝 enhancement 则写入 `.out-of-scope/` 并链接）。
- 快速状态覆盖：若维护者说"将 #42 移到 ready-for-agent"，信任并直接应用角色。确认即将执行的操作后执行。跳过 grill。若无 grill 会话则询问是否要编写 agent 简报。
- 恢复之前的会话：若存在之前 triage 备注，阅读它们，检查报告者是否已回答待决问题，在继续前展示更新后的状况。不要重复已解决的问题。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

将 grill 期间解决的所有内容记录在"established so far"下。问题必须具体且可操作，而非"请提供更多信息"。
