# 测试驱动开发

TDD 就是 红 → 绿 循环。本技能是让该循环产出值得保留的测试的参考指南：什么是好测试、测试放在哪里、反模式、循环规则。每个章节在每次循环都适用——在循环开始前和进行中查阅，而非事后。

## Guidelines

- 阅读代码库的 `CONTEXT.md`（若存在），使测试名称和接口词汇与项目领域语言一致，遵守所涉及区域的 ADR。
- 测试通过公共接口验证行为，而非实现细节。代码可以完全改变；测试不应随之改变。好测试读起来像 spec，能经受重构。
- 只在预先确认的接缝（seam）处测试。编写任何测试之前，写下待测接缝并与用户确认。不在未确认的接缝上写测试。预先确认接缝，让测试投入集中在关键路径和复杂逻辑上，而非每个边缘情况。
- 问："公共接口是什么，我们应该测试哪些接缝？"

## 反模式

- **实现耦合** — mock 内部协作者、测试私有方法、或通过旁路验证（查数据库而非用接口）。特征：重构时行为未变但测试却失败。
- **同义反复（tautology）** — 断言以与代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`），测试按构造就通过，永远不可能与代码不一致。期望值必须来自独立的 source of truth——已知正确的字面量、已验证的演算示例、spec。
- **水平切片（horizontal slice）** — 先写完所有测试，再写所有实现。批量测试验证的是想象中的行为，测试对真实变化变得不敏感。改为以垂直切片工作——一个测试 → 一个实现 → 重复，每个测试是一发 tracer-bullet。

## 循环规则

- 先红后绿。先写失败测试，然后只写足够让它通过的代码。不要预判未来测试或添加推测性功能。
- 每次一个切片。每轮循环一个接缝、一个测试、一个最小实现。
- 重构不是循环的一部分。它属于 review 阶段，而非 红 → 绿 实现循环。
