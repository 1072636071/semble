# 领域建模

在设计时主动构建和锐化项目的领域模型。这是主动纪律——挑战术语、发明边界场景、在术语确定时立即写下词汇表和决策。仅仅阅读 `CONTEXT.md` 获取词汇不是这个技能——本技能用于改变模型，而非仅仅消费模型。

## Guidelines

- 首次进入时检查根目录 `CONTEXT.md` 或 `CONTEXT-MAP.md`，读取现有词汇表作为基础；检查 `docs/adr/` 了解已有架构决策。若不存在，惰性创建（在第一个术语被确定时创建）。
- 按需创建文件——只在有东西要写时才创建。`CONTEXT.md` 应完全不含实现细节，它是词汇表，仅此而已。
- 若根目录存在 `CONTEXT-MAP.md`，仓库有多个上下文。映射指向每个上下文所在的位置。处理上下文间关系时（上游/下游、双向依赖、共享内核、防腐层）参见 CONTEXT-FORMAT.md 的关系模式表。
- 核心循环：识别 → 质疑 → 压测 → 验证 → 记录。每个概念有且仅有一个名字，每个名字有且仅有一个概念。
- 识别：捕捉模糊、过载或未定义的术语。
- 质疑：立即挑战，提出精确的规范术语。对照词汇表质疑（当用户术语与 `CONTEXT.md` 冲突时）或锐化模糊语言（当用户使用模糊或过载术语时）。
- 压测：发明探测边界情况的场景，迫使用户精确界定概念之间的边界。好的边界场景涉及两个概念的交界处，有明确的"应该属于 A 还是 B"的模糊性，能暴露隐含假设。
- 验证：对照代码检查用户陈述是否一致。无代码库时跳过。若发现矛盾揭示它。检查类型/接口定义命名、枚举值、数据库 schema、API 端点命名。
- 记录：术语确定后立即更新 `CONTEXT.md`，决策确定后按需创建 ADR。不要批量处理——即时捕获。
- 术语演化时：标注变更、评估影响面（代码中依赖旧定义的位置）、按需创建 ADR、清理同义词（旧名称移入 `_避免_`）。
- 退出信号：连续 2-3 个术语讨论未产生新的词汇表变更；用户话题从"概念是什么"转向"怎么实现"；所有讨论的术语已在 `CONTEXT.md` 中有清晰定义且无冲突。退出时简要总结本次会话新增/变更的术语和决策。

## ADR 创建条件

仅当以下三个条件都为真时才创建 ADR：

1. 难以逆转 — 后来改变想法的成本不可忽略。
2. 没有上下文会令人惊讶 — 未来读者会想知道"他们为什么这样做？"。
3. 真实权衡的结果 — 有真正的替代方案，你因特定原因选择了一个。

## 反模式

- 把 CONTEXT.md 当 spec 或设计文档写——它是词汇表，仅此而已。
- 批量更新词汇表——术语确定后立即更新，不要攒着。
- 记录显而易见的决策——"我们用 REST API" 不需要 ADR，除非有真实替代方案被否决。
- 忽略代码与模型的矛盾——发现时不一致时必须揭示，不能假装没看见。
- 一个概念多个名字——如果团队中有人用"客户"有人说"客户方"，必须选定一个，另一个列入 `_避免_`。
- 静默变更术语定义——修改已有术语定义时必须告知用户变更内容和影响面。
- 过度建模——不要为通用编程概念（如"超时"、"重试"）创建术语条目，只记录项目特有的领域概念。
