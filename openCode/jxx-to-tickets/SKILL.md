# To Tickets

将计划、规格文档或对话拆解为一组工单——追踪弹式垂直切片，每个声明阻塞它的工单。

issue tracker 和 triage 标签词汇表应已提供——若没有，运行 `jxx-setup-matt-pocock-skills`。

## Guidelines

- 从对话上下文中已有的内容出发。若用户传入引用（规格文档路径、issue 编号或 URL）作为参数，获取并阅读其完整内容和评论。
- 若尚未探索代码库，先了解当前状态。工单标题和描述使用项目的领域词汇表，遵守相关区域的 ADR。寻找预重构机会以简化实现——"先让变更变容易，再做容易的变更"。
- 将工作拆解为追踪弹工单。每个切片切出一条狭窄但完整的路径，贯穿每一层（schema、API、UI、测试）——垂直切片，不是单层水平切片。完成的切片可独立演示或验证。每个切片大小适合单个新上下文窗口。任何预重构应优先完成。
- 为每个工单设定阻塞边——必须在它之前完成的其他工单。没有阻塞的工单可以立即开始。
- 广泛重构是垂直切片的例外。广泛重构是机械性变更（重命名列、重新类型化共享符号），影响半径遍及整个代码库，单次编辑同时破坏数千个调用点。按扩展-收缩顺序排列：先扩展（在旧形式旁添加新形式），然后按影响半径分批迁移调用点（每批是独立工单，阻塞于扩展工单），最后收缩（删除旧形式，阻塞于所有迁移批）。
- 以编号列表形式呈现提议的拆解。对每个工单展示：标题、阻塞于、交付内容。询问用户粒度是否合适、阻塞边是否正确、是否有工单应合并或拆分。迭代直到用户批准。
- 将工单发布到本地跟踪器：在 `.scratch/<NN>-<工作简称-slug>/issues/` 下为每个工单创建独立文件 `<NN>-<slug>.md`（从 `01` 编号，按依赖顺序放置，阻塞者在前）。每个文件顶部含 `Status: ready-for-agent` 行；阻塞边以 `Blocked by: NN, NN` 文本行表示。
- 避免具体文件路径或代码片段——它们很快过时。例外：若 prototype 产出了比文字更精确地编码决策的片段，在此内联并简要注明它来自 prototype。只保留决策密集部分。
- 按前沿逐个工单推进，使用 `jxx-implement`，在工单之间清理上下文。

## 本地工单文件模板

```markdown
# <工单标题>

**Status:** ready-for-agent

**Blocked by:** 01, 02   （列出此工单依赖的工单编号；无阻塞则省略或写"无——可立即开始"）

**构建内容：** 此工单使什么端到端行为可用，从用户视角——不是逐层的实现列表。

**验收标准：**

- [ ] 验收标准 1
- [ ] 验收标准 2

## 评论

（评论与对话历史追加于此，新内容置于最前。）
```
