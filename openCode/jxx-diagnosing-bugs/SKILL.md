# 诊断 Bug

诊断棘手 bug 的纪律。仅在确有理由时跳过阶段。探索代码库时阅读 `CONTEXT.md`（若存在）建立相关模块的心智模型，检查所涉及区域的 ADR。

## 脱敏（Redact）

本技能会让你展示命令、输出和捕获的产物。先脱敏每一个机密——在原位写 `<REDACTED>`。循环要基于环境变量构建，让凭证留在环境中。捕获的产物带有 auth 头：只引用携带信号的行。若脱敏后的输出不足以诊断 bug，明确说明并询问用户。

## 阶段 1 — 构建反馈循环

这就是本技能的全部。如果你有一个针对此 bug 的紧密通过/失败信号——一个能在此 bug 上变红的——你就会找到原因。在此投入超常精力，要激进，要有创意，绝不放弃。

构建方式（大致按此顺序尝试）：会失败的测试、curl/HTTP 脚本、CLI 调用用 fixture 输入、无头浏览器脚本、重放捕获的 trace、一次性测试桩、属性测试/模糊测试循环、二分测试桩、差分循环、HITL bash 脚本（最后手段）。

收紧循环：把循环当作产品。能让它更快吗？能让信号更清晰吗？能让它更确定吗？30 秒的 flaky 循环比没有循环好不了多少；2 秒的确定性循环才是紧密的。

非确定性 bug：目标不是干净复现而是更高复现率。循环触发 100×，并行化，加压力，缩小时间窗口。50% flake 的 bug 可调试；1% 不行。

当你确实无法构建循环时：停下来明确说明，列出尝试了什么。向用户要：(a) 能复现它的环境访问权限，(b) 脱敏后的捕获产物，或 (c) 添加临时生产插桩的许可。不要在没有循环的情况下继续假设。

完成标准：循环紧密且能变红——你能说出一个命令（已至少运行过一次），它驱动实际的 bug 代码路径并断言用户描述的确切症状，确定性，秒级，agent 可运行。没有能变红的命令，就没有阶段 2。

## 阶段 2 — 复现 + 最小化

运行循环，看它变红。确认：循环产生的是用户描述的失败模式；失败在多次运行中可复现；已捕获确切症状。

最小化：将复现缩小到仍然变红的最小场景。逐一削减输入、调用者、配置、数据和步骤，每次削减后重新运行循环——只保留对复现失败不可或缺的。当每个剩余元素都不可或缺时完成。

## 阶段 3 — 假设

在测试任何假设之前生成 3–5 个排好序的假设。单假设生成会锚定在第一个看似合理的想法上。每个假设必须可证伪：陈述它做出的预测（"如果 <X> 是原因，那么 <改变 Y> 会使 bug 消失"）。在测试之前向用户展示排序列表——他们通常有能立即重新排序的领域知识。

## 阶段 4 — 插桩

每个探针必须对应阶段 3 中的特定预测。一次改变一个变量。工具偏好：调试器/REPL 检查（一个断点胜过十条日志）、目标日志在区分假设的边界处。绝不"记录一切然后 grep"。给每条调试日志打标签（如 `[DEBUG-a4f2]`），清理只需一次 grep。

性能问题分支：对于性能 regression，日志通常是错的工具。建立基线测量（计时工具、分析器、查询计划），然后二分。先测量，后修复。

## 阶段 5 — 修复 + regression 测试

在修复之前写 regression 测试——但仅当有正确的接缝时。正确的接缝是测试在调用点执行真实 bug 模式的接缝。如果没有正确的接缝，这本身就是重要发现——记录它，代码库架构阻止了 bug 被锁定。

如果正确的接缝存在：将最小复现转为该接缝处的失败测试，看它失败，应用修复，看它通过，对原始场景重新运行阶段 1 反馈循环。

## 阶段 6 — 清理 + 复盘

声名完成之前必需：原始复现不再复现；regression 测试通过（或接缝缺失已记录）；所有 `[DEBUG-...]` 插桩已移除；一次性 prototype 已删除；被证明正确的假设陈述在 commit/PR 消息中。

然后问：什么本可以防止这个 bug？如果答案涉及架构变更（没有好的测试接缝、纠缠的调用者、隐藏的耦合），将具体信息交接给 `jxx-improve-codebase-architecture`。在修复到位之后而非之前给出推荐。
