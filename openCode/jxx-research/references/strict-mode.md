# 严格模式

触发词：用户说"生成报告""写报告""严格模式""按模板""输出报告"时启用。

按模板生成结构化 Markdown 报告，输出到 `docs/report/`。

## 输出位置

所有报告统一存放在工作区根目录的 `docs/report/` 下。目录不存在时自动创建。

```
工作区根目录/docs/report/
├── tech-xxx.md       # 技术调研报告
├── progress-xxx.md    # 项目进度报告
├── analysis-xxx.md    # 分析报告
└── general-xxx.md     # 通用报告
```

**文件名规则**：`{模板前缀}-{主题slug}.md`。slug 从目标中提取简短英文 kebab-case（如 `react-state-management`、`q2-sprint-review`）。中文主题用拼音或英文翻译。

## 工作流

### 阶段 1 — 明确目标

收到请求后先澄清。如果用户描述已经足够具体，跳过追问直接进入下一阶段。

需确认的维度：

1. **主题** — 报告要回答的核心问题是什么？
2. **受众** — 谁读这份报告？（开发者 / 技术负责人 / 管理层 / 客户）
3. **信息源偏好** — 优先本地代码与文档，还是需要网络搜索？还是两者都做？
4. **深度** — 快速概览（采样关键来源）还是穷尽调研（覆盖所有相关来源）？

模糊时追问，一次一个维度，附推荐答案：

> "受众是开发者还是管理层？我默认按开发者视角写，技术细节可以深一些。"

### 阶段 2 — 选择模板

根据报告类型匹配模板。每个模板独立定义在 `references/templates/` 下：

| 报告类型 | 模板文件 | 适用场景 |
| -------- | -------- | -------- |
| 技术调研 | [tech](templates/tech.md) | 技术选型、工具对比、API 调研、方案评估 |
| 项目进度 | [progress](templates/progress.md) | 项目状态汇报、迭代回顾、里程碑总结 |
| 代码分析 | [analysis](templates/analysis.md) | 架构评估、代码质量、性能分析、安全审查 |
| 通用报告 | [general](templates/general.md) | 不限领域的通用结构，其他类型不适配时的兜底 |

如果所有模板都不完全匹配，以 `general` 为底本灵活增减节。模板是起点，不是牢笼 —— 根据实际情况调整节标题和顺序。

### 阶段 3 — 调研

按目标多源收集信息。信息源优先级：用户指定 > 一手来源（官方文档、源代码） > 可信二手来源（权威博客、技术书籍） > 社区讨论。

**信息源类型**：

| 来源 | 方式 | 适用 |
| ---- | ---- | ---- |
| 本地代码 | 搜索工作区、读取关键文件、分析依赖 | 代码分析报告、架构调研 |
| 本地文档 | 读取 CONTEXT.md、ADR、README、设计文档 | 所有报告类型 |
| 网络搜索 | 官方文档、技术文章、社区讨论 | 技术调研、方案评估 |
| 用户提供 | 用户指定的文档、链接、数据、截图 | 所有报告类型 |

**调研纪律**：

- 每个论断必须**可追溯** —— 标注来源：文件路径、URL、用户输入。
- 区分**事实**（来自来源）和**推断**（你的分析）。推断标注"分析："前缀。
- 调研深度与报告重要性匹配：高风险决策（技术选型、架构变更）→ 穷尽一手来源；快速了解 → 关键来源采样即可。
- 不编造结论。找不到答案时写明"未找到相关证据"，而非推测。

### 阶段 4 — 整理与生成

按选定模板结构，将调研发现填入各节：

1. 每节有明确的小标题和实质性内容 —— 不写只有标题的空节
2. 关键结论附来源引用，格式：`（来源：<文件路径 | URL>）`
3. 一节一段核心观点：每节要有一个读者能带走的关键信息
4. 报告写入 `docs/report/{模板前缀}-{slug}.md`

**冲突处理**：如果目标路径已有文件，**不覆盖**。创建新文件名（加序号后缀如 `-2`、`-3`），生成后告知用户两个文件的差异。

### 阶段 5 — 交付

报告生成后向用户汇报，格式：

```
报告已生成：docs/report/{filename}
- 模板：{模板名称}
- 节数：{N} 节
- 来源数：{N} 个（本地 X / 网络 Y / 用户提供 Z）
- 关键发现：<1-2 句摘要>

需要调整结构或补充内容吗？
```

如果阶段 1 有未确认的假设，在交付时显式列出。

## 完成标准

- [ ] 目标已明确（主题、受众、信息源偏好均已知或已做合理默认假设）
- [ ] 已选择并应用合适的模板（或基于 general 灵活调整）
- [ ] 报告包含模板要求的核心节（非空壳，每节有实质内容）
- [ ] 每个关键论断有可追溯的来源引用
- [ ] 文件已写入 `docs/report/{模板前缀}-{slug}.md`
- [ ] 已向用户交付（汇报关键信息 + 询问是否需要调整）

## 护栏

- **模板不绑架。** 模板是整理框架，遇不适配时灵活增减节，不以牺牲内容完整性为代价强行套模板。
- **冲突不覆盖。** 同名文件存在时创建新文件并告知差异。
- **先澄清再执行。** 目标模糊时不急于动手，追问到可执行再进入调研。

## 反模式

- **跳过澄清直接调研。** 目标不清导致报告答非所问。
- **模板过拟合。** 为套模板砍掉重要发现，或为填模板塞入无关内容。
- **忽略受众。** 用开发者术语写给管理层看，或用商业语言掩盖技术细节。
- **空节占位。** 写了节标题但内容只有"待补充"或一句话敷衍。
