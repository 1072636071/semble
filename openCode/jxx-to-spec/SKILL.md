# To Spec

将当前对话上下文和代码库理解转化为规格文档（PRD）。不要访谈用户——仅综合你已知的内容。

issue tracker 和 triage 标签词汇表应已提供——若没有，运行 `jxx-setup-matt-pocock-skills`。

## Guidelines

- 探索仓库以了解代码库当前状态（若尚未探索）。在整个规格文档中使用项目的领域词汇表，遵守相关区域的 ADR。
- 勾画出测试该功能的 seam。优先使用已有 seam 而非新建；使用尽可能高层的 seam；若需新 seam，在最高可能的位置提出。代码库中 seam 越少越好——理想数量是一。与用户确认这些 seam 是否符合预期。
- 使用下方模板编写规格文档，发布到项目 issue tracker。应用 `ready-for-agent` triage 标签——无需额外 triage。
- 发布路径：在仓库根目录 `.scratch/` 下创建功能目录 `<NN>-<feature-slug>/`，将规格文档写入 `.scratch/<NN>-<feature-slug>/PRD.md`。`<NN>` 为从 `01` 起的全局递增顺序号。

## Spec 模板

```markdown
## 问题陈述

用户面临的问题，从用户视角描述。

## 解决方案

问题的解决方案，从用户视角描述。

## 用户故事

一个长的、编号的用户故事列表。每个采用：

1. 作为 <角色>，我想要 <功能>，以便 <收益>

用户故事列表应极其详尽，覆盖功能的所有方面。

## 实现决策

已做出的实现决策列表。可包括：将要构建/修改的模块、将要修改的模块接口、来自开发者的技术澄清、架构决策、Schema 变更、API 契约、具体交互。

不要包含具体文件路径或代码片段——它们可能很快过时。例外：若 prototype 产出了比文字更精确地编码决策的片段（状态机、reducer、schema、type shape），在相关决策中内联并简要注明它来自 prototype。只保留决策密集部分。

## 测试决策

已做出的测试决策列表。包括：什么样的是好测试的描述（仅测试外部行为，不测实现细节）、哪些模块将被测试、测试的先例（代码库中类似类型的测试）。

## 超出范围

此规格文档范围外的事项描述。

## 补充说明

关于功能的任何进一步说明。
```
