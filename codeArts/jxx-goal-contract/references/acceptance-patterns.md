# 验收标准设计模式

验收标准是目标模式的判停核心。一条好的验收标准让"完成"成为一个客观事实而非主观判断。本文件给出可观测（Observable）、可判定（Decidable）、独立来源（Independent）三条性质，加上绑定验证命令（Verifiable）——通过证据必须是命令的实际运行结果，不接受 AI 陈述。

> 相关文件：[goal-contract.md](goal-contract.md)（契约模板与示例）、[constraint-design.md](constraint-design.md)（约束设计，与验收的边界）、[grilling-guide.md](grilling-guide.md)（grilling 中磨验收的问题模板）

## 三条性质 + 一条绑定

1. **可观测（Observable）**——验收指向一个外部可见的状态或行为，而非内部实现。"数据库表有 user_id 列"不可观测（除非直接查 schema），"GET /users/1 返回 200 且 body 含 user_id"可观测。
2. **可判定（Decidable）**——存在一个明确的通过/失败判定，不留主观空间。"API 响应快"不可判定，"GET /users/1 在 200ms 内返回 200"可判定。
3. **独立来源（Independent）**——通过证据来自 AI 之外的来源——命令输出、测试结果、文件内容、外部检查——而非 AI 的自述。这是最重要的一条。
4. **绑定验证命令（Verifiable）**——每条验收末尾以 `（验证：\`<命令>\`）` 绑定一条可执行命令。执行阶段的"通过"= 该命令的实际运行结果，不接受 AI 陈述。确实无法命令化的（如视觉走查），降级为绑定具体外部产物 + 检查清单，如 `（验证：截图 <路径> + 检查单：<项>）`——"人工看看""我觉得 OK"一律否决。

好/坏对照见下面的示例——注意好对照都带有 `（验证：...）`。

## 好 / 坏对照

### 翻译任务

- ❌ 坏："翻译质量好"——不可判定，不可观测。
- ✅ 好："将 README.md 翻译为中文，保持所有代码块、链接、标题层级不变；原文中所有 Markdown 链接在译文中仍可点击且指向相同目标。"（可通过 diff 译前后的代码块/链接结构、检查标题层级验证）

### 报告任务

- ❌ 坏："写一份全面的行业报告"——"全面"无判定标准。
- ✅ 好："一份 Markdown 报告，覆盖 X 行业的 3 个主要细分市场；每个细分市场含：市场规模（附数据来源链接）、Top 3 玩家、一个代表性风险；总长 2000-3000 字。"（可逐项核对：3 细分？每项三要素？来源链接可访问？字数区间？）

### 代码任务

- ❌ 坏："功能正常工作"——与实现同义，按构造就通过（同义反复反模式）。
- ✅ 好：见 [goal-contract.md](goal-contract.md) 的 linkcheck 示例——用 fixture 输入 + 精确输出断言，每条验收带 `（验证：...）`。

## 反模式

- **同义反复**——验收以与实现相同的方式重算期望值，按构造永远通过。期望值必须来自独立的真实来源（字面量、手工演算、spec）。
- **主观词**——"优雅""全面""高质量""用户友好"——无法判定。替换为可数/可测的具体指标。
- **无独立证据**——"我会确保 X 正确"不构成验收；验收须指明由什么外部检查来确认 X。
- **过细**——验收写成实现步骤（"先建 User 类，再建 save 方法"）。验收描述结果，不描述过程。
- **无命令绑定**——验收只写断言不写 `（验证：...）`，执行阶段只能靠 AI 自评。每个验收末尾必须有命令或外部产物检查单。

## 检验问题

对每条验收，问：

1. 一个不写这段代码的人，能据此判定通过/失败吗？
2. 通过的证据会是什么具体的东西（命令？文件？输出）？
3. 这个证据来源独立于实现本身吗？

三个都答"是"才算合格。
