# ADR 格式

ADR 存放在 `docs/adr/` 中，使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

惰性创建 `docs/adr/` 目录 — 只在第一个 ADR 需要时才创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：上下文是什么，我们决定了什么，为什么。}
```

就这样。ADR 可以只有一段。价值在于记录*做出了*决策以及*为什么* — 而不是填写章节。

## 可选章节

仅在增加真正价值时包含。大多数 ADR 不需要它们。

- **状态**前置元数据（`提议 | 已接受 | 已弃用 | 被 ADR-NNNN 取代`）— 当决策会被重新审视时有用
- **考虑过的选项** — 仅当被拒绝的替代方案值得记住时
- **后果** — 仅当非显而易见的下游影响需要指出时

## 编号

扫描 `docs/adr/` 获取最高现有编号并加一。

## 弃用与取代

当一个 ADR 被新决策取代时：

1. 在旧 ADR 顶部添加状态行：`状态：已弃用 — 被 ADR-NNNN 取代`
2. 在新 ADR 中引用旧 ADR 编号，说明取代原因
3. 不要删除旧 ADR — 它记录了历史决策的推理过程

示例：

```md
# 0004-改用 CQRS 分离读写模型

订单量增长导致读写竞争加剧，我们改用 CQRS 模式将读模型投影到 Elasticsearch，
写模型保持事件溯源。取代 ADR-0001 中的单体读写方案。
```

然后在 `0001-event-sourced-orders.md` 顶部添加：

```md
状态：已弃用 — 被 ADR-0004 取代
```

## 多上下文归属

- **系统级决策**（影响多个上下文）：放在根 `docs/adr/`
- **上下文特定决策**（只影响一个上下文）：放在该上下文的 `docs/adr/`

判断标准：如果撤销该决策需要修改多个上下文的代码，它是系统级的。

## 何时提供 ADR

三条件判断规则见 SKILL.md「谨慎提供 ADR」。此处补充**什么符合条件**的具体示例：

### 什么符合条件

- **架构形状。** "我们使用 monorepo。""写模型是事件溯源的，读模型投影到 Postgres。"
- **上下文之间的集成模式。** "订购和计费通过领域事件通信，而非同步 HTTP。"
- **带有锁定的技术选择。** 数据库、消息总线、认证提供者、部署目标。不是每个库 — 只是那些换掉需要一个季度的。
- **边界和范围决策。** "客户数据由客户上下文拥有；其他上下文仅通过 ID 引用。" 明确的否定和肯定一样有价值。
- **对显而易见路径的有意偏离。** "我们使用手动 SQL 而非 ORM，因为 X。" 任何合理读者会假设相反的地方。这些阻止下一个工程师"修复"有意为之的东西。
- **代码中不可见的约束。** "因为合规要求我们不能使用 AWS。""响应时间必须在 200ms 以下，因为合作伙伴 API 合同。"
- **拒绝不显而易见的替代方案时。** 如果你考虑了 GraphQL 并因微妙原因选了 REST，记录它 — 否则六个月后会有人再建议 GraphQL。

### 中文领域示例

以下示例展示在中文业务场景中如何撰写 ADR：

```md
# 0001-订单状态机采用显式状态模式

订单流转涉及多个状态（待支付、已支付、已发货、已完成、已取消），
我们采用显式状态机而非布尔标志组合，因为状态转换有严格的先后约束，
布尔标志容易产生非法组合（如"已取消且已发货"）。
```

```md
# 0002-会员等级由独立服务计算而非订单服务内联

会员等级计算依赖多源数据（消费金额、活跃天数、邀请人数），
将其放在订单服务内会导致职责膨胀和循环依赖，
因此独立为会员服务，通过事件异步触发重算。
```

```md
# 0003-支付回调采用幂等键而非状态检查

支付渠道可能重复发送回调，我们采用幂等键去重而非检查订单状态，
因为状态检查在并发场景下存在竞态条件，幂等键由数据库唯一约束保证。
```
