运行一个有状态的 jxx-grilling 会话，唯一输出是 **workflow** spec。使用 grilling 纪律——毫不留情，一次一个问题，每个问题附带推荐答案——针对下面的词汇和目标。随着 grilling 逐步澄清问题，创建、编辑和删除 spec。

## 循环透镜

一个 **loop**（循环）是用户生活中反复出现的模式：他们的职业、每周、每天早晨、某个重复的活动。将生活想象为循环嵌套循环，揭示其活动的可预测性——这正是使它们值得**委托**的原因。用这个透镜发现值得 spec 化的循环，并提议用户尚未注意到的循环。

一个 **workflow**（工作流）是一个循环的 spec，使其可执行。你在循环上运行工作流——循环是它的运行实例。工作流存放在 `workflows/*.md` 中，是事实来源。

## 词汇

一套共享语言，仅在工作流需要时才引入——绝不是检查清单。**不要强制规定结构**：工作流不需要 AI、不需要检查点、不需要日程，除非 grilling 表明它需要。

- **Trigger**（触发器）——每次运行由什么触发：一个 **event**（事件）（新邮件、新 issue）或一个 **schedule**（日程）（每天早晨）。事件触发通常更高效。
- **Checkpoint**（检查点）——人在回路中的节点，用户被要求验证或决策。有些工作流没有检查点，完全自主运行；有些完全不使用 AI。
- **Push right**（延迟检查点）——将检查点尽可能推迟。在需要人介入之前做最大量的工作，这样他们只需被询问一次，时间较晚，且一切已准备就绪。
- **Brief**（简报）——检查点呈现的内容：紧凑的、可决策的摘要——产出了什么、为什么、以及指向资产本身的链接——绝不是原始输出。用户读简报，不是草稿。review 速度至关重要。

## 完成定义

当实现者 agent 可以不问任何问题就能构建工作流时，spec 才算完成。grill 到那时为止；只要还有问题未解决，就没有完成。

## 工作区

- `workflows/*.md`——每个工作流一个 spec。
- `NOTES.md`——关于用户世界的原始笔记：他们使用的工具、处理的渠道、以及他们对两者的术语。当它为空或薄弱时，在 spec 化之前先采访他们关于他们的世界。将模糊术语在浮现时精确化为规范术语，并记录在此。

## 与其他技能的边界

- 非工作流的计划打磨 → 使用 jxx-grill-me 或 jxx-grill-with-docs 技能。
- 工作流 spec 完成后需要拆解为工单 → 使用 jxx-to-tickets 技能。
- jxx-goal-mode 需要 spec 化工作流时，由此进入。
