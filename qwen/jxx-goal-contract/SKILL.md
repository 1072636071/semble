# 目标契约固化

将模糊任务收敛为可执行的 `GOAL.md` 契约。契约是目标模式循环的唯一判停依据。

## 目标存储结构

所有目标统一存储在工作区根目录的 `.goals/` 下，按目标名称隔离：

```
工作区根目录/.goals/
├── _index.md                    # 目标索引
├── linkcheck/                   # 目标名称
│   ├── GOAL.md                  # 契约文件
│   ├── PROGRESS.md              # 执行进度
│   └── EVIDENCE.md              # 交付证据
```

### 目标索引（`_index.md`）

索引记录所有目标的状态，格式：

```markdown
# 目标索引

| 名称      | 状态   | 创建时间   | 最后更新   |
| --------- | ------ | ---------- | ---------- |
| linkcheck | 执行中 | 2026-07-12 | 2026-07-12 |
```

状态取值：`契约中` / `执行中` / `已暂停` / `已完成` / `已失败`。

> `.goals/` 中的 PROGRESS.md / EVIDENCE.md 是执行过程产物。新建首个目标时提示用户：如不希望入库留痕，可将 `.goals/` 加入 `.gitignore`。

### 目标名称规则

- 从用户任务的交付物中提取简短英文 kebab-case 名称（如 `linkcheck`、`blog-site`）。
- 名称唯一，不可与已有目标重名（除非是继续/重复操作）。
- 用户未指定名称时，从 Goal 描述中自动提取。

## 目标操作

### 新建目标

1. 确定目标名称（kebab-case）。
2. 创建 `.goals/{name}/` 目录。
3. 走契约固化流程（见"模式选择"）。
4. 契约写入 `.goals/{name}/GOAL.md`。
5. 按 references/goal-contract.md 的完整模板初始化 `.goals/{name}/PROGRESS.md`（含每轮必读块、验证命令列、固化日志；轮数=0，所有验收=待验证）。
6. 更新 `_index.md`，状态=`契约中`。

### 继续目标

继续中断目标**不经过本技能**——由 jxx-goal-mode 技能直接路由到 jxx-goal-execute 技能（断点恢复），契约读取与进度确认由执行器完成。仅当用户要在继续前**修改契约**时，才走本技能的"追加到已有目标"流程。

### 重复目标

当用户说"重复 {name}"或"重做 {name}"时：

1. 读取 `.goals/{name}/GOAL.md` 作为新契约起点。
2. 询问用户：原样重复还是调整契约？
3. 原样重复：复制 GOAL.md，重置 PROGRESS.md，状态改回 `契约中`。
4. 调整：以旧契约为起点走对应模式流程，合并后写入。

### 追加到已有目标

先读取旧契约，以旧契约为起点，仅对新增部分走对应模式流程，合并后写入。

### 异常处理

异常场景（名称冲突、GOAL.md 损坏、PROGRESS.md/`_index.md` 缺失、固化放弃、写入失败等）的完整处理表见 references/error-recovery.md。核心原则：写入序列（GOAL.md → PROGRESS.md → `_index.md`）中途失败时，清理已写入部分回到写入前状态，避免不一致状态残留。

## 依赖关系

| 依赖技能 | 关系 | 说明 |
| --- | --- | --- |
| jxx-goal-mode | 上游 | 路由器，将用户请求分发到本技能 |
| jxx-grill-me | 降级 | 目标模糊时委托 grill 追问收敛目标 |
| jxx-plan-review | 下游 | 语义审查（门下省），契约固化后审方案可行性 |
| jxx-goal-execute | 下游 | 执行器，语义审查准奏后由该技能执行自主循环 |

> 封驳处理：若 jxx-plan-review 技能封驳，修正方向写入 `.goals/{name}/REVIEW.md`。本技能读取 REVIEW.md 中的修正建议，走"追加到已有目标"流程修正契约，修正完成后重新提交 jxx-plan-review 技能审查。

## 契约结构

契约由 5 个字段组成：Goal、Acceptance、Constraints、Budget、Pause Conditions。模板与填写示例见 references/goal-contract.md。

关键设计：**Pause Conditions** 独立于 Constraints——Constraints 划技术边界（不可逾越的线），Pause Conditions 列高风险场景（需要人类决策才能继续）。

## 模式选择

收到任务后先分类再选模式：

| 任务特征 | 模式 | 理由 |
| --- | --- | --- |
| 低风险 + 领域熟悉 | 默认推进 | 不拦用户填表，直接给推荐版 |
| 低风险 + 陌生领域 | 发现优先 | 先调研再实施 |
| 高风险（涉及账号/付费/生产/法律/版权） | Grilling | 必须逐维度确认 |
| 用户要求详细追问 | Grilling | 尊重用户偏好 |

## 默认推进模式

核心理念：低风险不确定性不拦用户填表，直接给最佳默认方案。

### 流程

1. **重述为结果**——把用户请求改写为一个具体交付物，而非活动描述。
2. **选保守默认**——对低风险未知做明确假设，给最佳默认方案。
3. **目标确认门**——把第 1 步重述的目标用一句话反馈给用户确认：
   - 格式：`我理解你的目标是：[一句话目标描述]。这个理解正确吗？`
   - 用户确认正确 → 进入第 4 步。
   - 用户纠正 → 用纠正后的目标重新走第 1-2 步，再次确认，直到用户确认正确。
   - 目标确认门不可跳过——即使任务看起来"很明显"也必须确认。
   - 确认的是**目标本身**（做什么、交付什么），不涉及验收标准、约束、预算等细节。
   - **目标模糊降级**——若无法从用户输入中提炼出清晰的一句话目标（描述过于宽泛、歧义多、缺少关键维度），不强行猜测，委托 jxx-grill-me 技能启动 grill 追问，逐维度帮用户把模糊意图收敛为清晰目标。grill 收敛完成后回到本流程第 1 步重新开始。
4. **生成草稿**——输出一份完整的 GOAL.md 草稿，不留占位符，但此时**不展示给用户**。
5. **自检-修正内循环**——对照否决门（见"契约否决门"）逐条检查草稿：
   - 每条否决门必须显式回答"通过"或"否决+原因"。
   - 存在否决项 → 修正草稿 → 重新自检，直到全部通过。
   - 自检通过后启动独立 task/subagent 执行否决门检查（见"执行-检查上下文隔离"），确保检查在独立上下文中完成。
   - 独立检查也通过 → 进入下一步；否则修正后重新走自检+独立检查。
6. **输出推荐执行版**——展示通过双重检查的 GOAL.md，附默认理由和编号选择题，用户确认或调整后写入 `.goals/{name}/GOAL.md`。
7. **给编号选择题**——只在答案改变成本/风险/所有权/产品方向时才问，用编号选项+默认值。

### 输出格式

```
推荐执行版（目标名称：{name}）：
<完整的 GOAL.md 内容>

默认选择理由：<一句话>

可选调整：
1. <维度A>：A <默认> / B <选项2> / C <选项3>
2. <维度B>：A <默认> / B <选项2>

你可以直接回复：按默认，或回复类似 1B 2A。确认后我将写入 .goals/{name}/GOAL.md。
```

### 模糊词翻译

模糊词（"高级""有质感""专业""像官网"）不删除，翻译为验证条件：

| 模糊词 | 翻译为 |
| --- | --- |
| "高级/有质感" | 截图检查间距/字体/层级 + 最多 3 轮聚焦视觉改进 |
| "专业/像官网" | 对照指定参考站点截图 + 可读性/一致性检查 |
| "全面/完整" | 列出具体覆盖项清单 + 逐项核对 |
| "好用/友好" | 走通核心用户流程 + 操作步骤数 ≤ N |

翻译结果写入 Acceptance 时同样遵守绑定要求：能命令化的绑命令，不能命令化的绑产物 + 检查单。

## 发现优先模式

陌生领域（医疗、金融、合规、复杂专业数据）不假装懂，先调研再实施。

### 流程

1. 在 Goal 中加入"先读取项目文档/样例数据/现有脚本"。
2. 在 Acceptance 中加入"识别并读取权威参考资料"。
3. 在 Constraints 中加入"不编造领域结论/数据语义/合规声明"。
4. 在 Budget 中保持正常设定，但预留 1-2 轮给发现阶段。
5. 在 Pause Conditions 中列出该领域的高风险暂停场景。
6. 在 Goal 或 Acceptance 中注明"先完成发现阶段并列出工作假设，再进入实施"。

## Grilling 模式

高风险任务或用户要求时，逐维度追问直到契约各维度可执行。

### 推进策略

1. **一次只问一个维度**——Goal → Acceptance → Constraints → Budget → Pause Conditions。
2. **每个问题附推荐答案**——降低认知负荷。
3. **最多 3 轮追问**——同一维度超过 3 轮仍模糊，停下来给锐化方向。
4. **识别"够了"信号**——连续两次确认推荐答案且无补充，推进下一维度。

详细问题模板见 references/grilling-guide.md。

### 验收标准设计

每条 Acceptance 必须满足三条性质 + 一条绑定：

1. **可观测**——指向外部可见的状态或行为。
2. **可判定**——存在明确的通过/失败判定。
3. **独立来源**——通过证据来自 AI 之外（命令输出、测试结果、文件内容）。
4. **绑定验证命令**——每条验收末尾以 `（验证：`<命令>`）` 绑定一条可执行命令。执行阶段的"通过" = 该命令的实际运行结果，不接受 AI 陈述。确实无法命令化的（如视觉走查），降级为绑定具体外部产物 + 检查清单——"人工看看""我觉得 OK"一律否决。

好/坏对照见 references/acceptance-patterns.md。

### 约束设计

约束划**边界**（不可逾越的线），不写**步骤**（该走的路）。详见 references/constraint-design.md。

## 暂停条件设计

Pause Conditions 独立于 Constraints，专门列出需要人类决策的高风险场景：凭证/账号/支付、生产数据/破坏性操作、法律/医疗/金融判断、版权素材/官方授权、上架发布/真实部署、所有权或产品方向不清。

低风险不确定性写成工作假设（放在 Constraints 里），不放入暂停条件。

## 契约否决门

契约写入 GOAL.md 前必须通过全部否决门。**任一否决 = 不可写入，必须修正后重新检查。**

### 否决门清单

| 门 | 检查内容 | 否决条件 |
| --- | --- | --- |
| V1 | Goal 只说"什么"不含"怎么做" | 出现动词短语描述步骤 |
| V2 | Goal 包含交付物形态 + 意图 | 缺少形态或意图 |
| V3 | 每条 Acceptance 可观测、可判定、独立来源 | 出现主观词/同义反复/无独立证据来源 |
| V4 | Acceptance ≥ 3 条 | 少于 3 条 |
| V5 | Constraints 只划边界不写步骤 | 出现"先…再…最后…"等过程描述 |
| V6 | Constraints ≥ 3 条（技术栈 + 范围 + 保护性） | 少于 3 条或缺少任一类 |
| V7 | 无执行计划/拆解步骤混入契约 | 出现"阶段""步骤""第一步"等拆解语言 |
| V8 | Budget 有最大轮数 + 时间上限 | 缺少任一 |
| V9 | Pause Conditions 显式声明 | 缺失（即使为"无"也必须显式声明） |
| V10 | 每条 Acceptance 绑定可执行验证命令 | 任一验收缺少绑定，或绑定物是"人工确认/AI 自评" |

### 检查方式

1. **自检**——生成草稿后，主 agent 逐门显式回答"通过"或"否决+原因"。
2. **独立检查**——自检通过后启动独立 task/subagent 执行否决门检查（见"执行-检查上下文隔离"）。
3. **双重通过**——自检 + 独立检查均通过，才可输出推荐执行版。

### 行政检查

否决门通过后还需确认：目标名称 kebab-case 且唯一；契约写入 `.goals/{name}/GOAL.md`；PROGRESS.md 已初始化；`_index.md` 已更新。

如果固化后目标仍然模糊，**不启动循环**——指出模糊点并给出锐化方向。

## 契约深度下限

| 字段 | 下限要求 |
| --- | --- |
| Goal | ≥ 1 句，必须包含交付物形态 + 意图 |
| Acceptance | ≥ 3 条，每条必须含独立证据来源 + 绑定验证命令 |
| Constraints | ≥ 3 条（技术栈 + 范围 + 至少一条保护性约束） |
| Budget | 最大轮数 + 时间上限，缺一不可 |
| Pause Conditions | 至少显式声明"无"或列出具体场景 |

## 执行-检查上下文隔离

契约的"生成"和"检查"必须在**不同上下文**中完成，避免自我检查时"放水"。

### 机制

1. 主 agent 生成契约草稿并完成自检。
2. 自检通过后启动独立 task/subagent 执行否决门检查。检查 agent 只接收：契约草稿原文 + 否决门规则 + 深度下限规则；**不接收**生成过程、自检过程、用户原始请求上下文。
3. 检查 agent 逐门输出"通过"或"否决+原因"。
4. 主 agent 根据检查结果修正草稿，修正后重新走自检 + 独立检查，直到双重通过。

**降级路径**：宿主无 task/subagent 能力时，独立检查降级为换视角复检——抛开生成过程，以"第一次审阅的第三方"姿态仅凭契约原文逐门检查，并在 PROGRESS.md 固化日志中记录"独立检查降级为换视角自检"。降级不豁免任何否决门。

### 为什么必须隔离

同一上下文中 AI 倾向于"自我合理化"；独立上下文的检查 agent 只看到契约原文，像第一次审阅的第三方，更容易发现漏洞。这是"执行者不检查，检查者不执行"原则的落地。

## 契约一旦固化

契约写入 `.goals/{name}/GOAL.md` 后即冻结。后续如需调整，**不擅自改**——停下来向用户说明并取得确认后再改，并在交付时记录改动。

## 反模式

- **模糊目标**——"做好一个网站"。回 grilling 磨清。
- **验收同义反复**——"功能正常工作"。替换为具体可检查的行为。
- **约束过死**——详述"怎么做"，退化回过程模式。
- **占位符**——`[Outcome]`、`TODO`、`待定`出现在推荐执行版中。推荐版必须完整无占位符。
- **模糊词当验收**——"高级""有质感"作为完成标准。翻译为截图/检查/迭代规则。
- **无命令验收**——验收只写断言、不绑定验证命令。每条验收必须绑定 `（验证：...）`。
- **无限循环**——没有预算上限。设上限。
- **目标名称冲突**——新建目标与已有目标同名但不打算继续/重复。改名称或先处理旧目标。
