# Grilling 指南

阶段 0 的 grilling 会话是目标模式成败的关键。本文件给出 grilling 的推进策略、问题模板和常见陷阱。

## 推进策略

1. **一次只问一个维度**——Goal 没磨清前不碰 Acceptance，Acceptance 没磨清前不碰 Constraints。
2. **每个问题附推荐答案**——降低用户认知负荷，用户只需确认或修正，而非从零构造。
3. **识别"够了"信号**——当用户连续两次对推荐答案说"对"且无补充，该维度已够清晰，推进下一维度。
4. **最多 3 轮追问**——同一维度追问超过 3 轮仍模糊，停下来告知用户该维度想不清，给出锐化方向而非继续追问。

## 维度一：Goal

目标是要什么结果，不是怎么做。

### 问题模板

| #   | 问题                                                     | 推荐答案示例                                            |
| --- | -------------------------------------------------------- | ------------------------------------------------------- |
| G1  | 你要的最终交付物是什么形态？（代码/文档/报告/工具/数据） | "一个 CLI 工具" / "一份 Markdown 报告"                  |
| G2  | 这个交付物给谁用？解决什么问题？                         | "给开发者用，检查链接失效" / "给产品经理，了解市场格局" |
| G3  | 用一句话描述：完成时你会拥有什么？                       | "一个能扫描 Markdown 目录并报告失效链接的命令行工具"    |

### 常见问题

- **混入步骤**——"用 React 做一个网站"→ 剥离技术选择到 Constraints，Goal 只留"一个网站"。
- **范围蔓延**——"一个网站加后端加部署"→ 拆为多个独立目标，每次只跑一个循环。
- **无法一句话说清**→ 说明目标太大或太模糊，建议拆分或缩小范围。

## 维度二：Acceptance

验收标准是怎样算完成。每条必须可观测、可判定、独立来源，且绑定验证命令。详见 [acceptance-patterns.md](acceptance-patterns.md)。**至少 3 条，每条必须附独立证据来源说明 + 绑定验证命令（`（验证：`<命令>`）`）。**

### 问题模板

| #   | 问题                                                    | 推荐答案示例                                            |
| --- | ------------------------------------------------------- | ------------------------------------------------------- |
| A1  | 怎么判定这个交付物"做完了"？给我 3-5 条可检查的断言。   | "运行 `linkcheck ./docs` 能扫描所有 .md 文件的本地链接" |
| A2  | 每条断言：一个不写这段代码的人，能据此判定通过/失败吗？ | 如果不能 → 重写为可观测的行为描述                       |
| A3  | 通过的证据会是什么？（命令输出？文件内容？测试结果？）  | "fixture 目录扫描输出恰好包含 3 条失效链接"             |
| A4  | 每条断言绑定的验证命令是什么？（测试/脚本/退出码/grep） | "`python -m linkcheck tests/fixtures/broken` 后 diff 输出与 expected.txt 无差异" |

### 常见问题

- **同义反复**——"功能正常工作"→ 与实现同义，按构造即通过。替换为具体可检查的行为。
- **主观词**——"优雅""高质量"→ 替换为可数/可测的具体指标。
- **过细**——验收写成实现步骤 → 验收描述结果，不描述过程。
- **无命令绑定**——断言没法用命令验证 → 执行阶段只能靠 AI 自评。能命令化的绑命令，不能的降级为绑产物 + 检查单（如"截图 <路径> + 检查单：<项>"）。

## 维度三：Constraints

约束是不能踩的边界。详见 [constraint-design.md](constraint-design.md)。**至少 3 条：技术栈 + 范围 + 保护性约束。**

### 问题模板

| #   | 问题                                              | 推荐答案示例                     |
| --- | ------------------------------------------------- | -------------------------------- |
| C1  | 技术栈有什么限制？（语言、版本、允许/禁止的依赖） | "Python 3.11+，仅标准库"         |
| C2  | 有什么文件或目录绝对不能改？                      | "不修改被扫描目录的任何文件"     |
| C3  | 有什么风格/规范必须遵守？                         | "遵循项目现有的 ESLint 配置"     |
| C4  | 有什么安全/伦理红线？                             | "不收集用户数据，不调用外部 API" |

### 常见问题

- **约束过死**——"先用 os.walk 遍历目录"→ 这是步骤，不是约束。移到拆解阶段。
- **约束过宽**——不写约束 → AI 可能选择与项目惯例冲突的方案。至少声明技术栈和不可改动项。
- **约束与验收混淆**——"输出格式为纯文本"→ 如果是"必须达成什么"放 Acceptance，如果是"不能超出什么"放 Constraints。

## 维度四：Budget

没有预算的循环没有终止条件。**最大轮数和时间上限缺一不可。**

### 问题模板

| #   | 问题                                       | 推荐答案示例 |
| --- | ------------------------------------------ | ------------ |
| B1  | 你愿意让这个循环跑多少轮？（建议 5-10 轮） | "8 轮"       |
| B2  | 时间上限是多少？                           | "1.5 小时"   |

### 常见问题

- **不设预算**→ AI 永远在"再改一点"。必须设上限。
- **预算过紧**→ 1-2 轮不够完成任何有意义的切片。建议至少 5 轮。

## 维度五：Pause Conditions

Pause Conditions 列出需要人类决策的高风险场景，独立于 Constraints。**即使无高风险场景，也必须显式声明"无"——留空等于未思考。**

### 问题模板

| #   | 问题                                   | 推荐答案示例                      |
| --- | -------------------------------------- | --------------------------------- |
| P1  | 这个任务涉及凭证、账号、支付吗？       | "不涉及" / "涉及，需要暂停确认"   |
| P2  | 会接触生产数据或执行破坏性操作吗？     | "不会" / "会，需要暂停确认"       |
| P3  | 涉及法律、医疗、金融判断或版权素材吗？ | "不涉及" / "涉及，需要暂停确认"   |
| P4  | 需要上架发布或真实部署吗？             | "不需要" / "需要，发布前暂停确认" |

### 常见问题

- **Pause Conditions 过宽**——低风险不确定性不应放入暂停条件，写成工作假设放 Constraints。只保留账号/付费/生产/法律/版权/发布等高风险项。
- **与 Constraints 混淆**——Constraints 是技术边界（"不能用第三方库"），Pause Conditions 是决策门槛（"需要付费 API 时暂停等用户确认"）。

## Grilling 会话示例

```
AI: 你要的最终交付物是什么形态？
    推荐答案：一个 CLI 工具 / 一份报告 / 一个库 / ...

用户: 一个命令行工具

AI: 这个工具给谁用？解决什么问题？
    推荐答案：给开发者用，自动化某个检查 / 给数据分析师用，批量处理某个格式 / ...

用户: 给开发者用，检查 Markdown 文件里的失效链接

AI: 用一句话描述：完成时你会拥有什么？
    推荐：一个能扫描 Markdown 目录并报告失效本地链接的命令行工具

用户: 对，就这样

AI: 好，Goal 已锁定。接下来磨验收标准——怎么判定"做完了"？给我 3-5 条可检查的断言。
    推荐答案：
    1. 运行 `linkcheck ./docs` 能扫描所有 .md 文件的本地链接（验证：`python -m linkcheck ./docs --verbose` 输出覆盖全部 .md）
    2. 对含 3 个已知失效链接的 fixture，输出恰好包含这 3 条（验证：扫描输出与 expected.txt diff 无差异）
    3. 退出码：发现失效链接返回 1，全部有效返回 0（验证：分别对 broken/clean fixture 跑 `echo $?`）
    4. `linkcheck --help` 输出用法说明（验证：`--help` 退出码 0 且含示例行）

用户: 这些都行，再加一条：支持 .mdx 文件

AI: 更新第 1 条为"能扫描所有 .md 和 .mdx 文件的本地链接"。其他条目确认？...

[继续 Constraints → Budget → Pause Conditions]

AI: 这个任务涉及凭证、支付或生产数据吗？
    推荐答案：不涉及 / 涉及，需要暂停确认

用户: 不涉及

AI: 有什么需要人类决策才能继续的高风险场景？
    推荐答案：需要安装第三方依赖时暂停 / 需要修改被扫描目录中的文件时暂停

用户: 就这两个

AI: 好，Pause Conditions 已锁定。契约固化完成，写入 GOAL.md。
```
