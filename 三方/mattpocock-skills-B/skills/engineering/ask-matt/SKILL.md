# Ask Matt

你记不住每个技能，所以问。

一个**流程（flow）** 是穿过技能的一条路径。大多数路径沿着一条**主线流程**，两条**入口匝道**汇入其中。其他一切都是独立的，或者是运行在底层的一个词汇层。

## 主线流程：想法 → 交付

大多数工作走的路线。你有一个想法，想把它构建出来。

1. **`/grill-with-docs`** — 通过访谈打磨想法。每当你在**工作目录**中工作时都从这里开始：它是有状态的，把学到的东西保留在 `CONTEXT.md` 和 ADR 中。（没有工作目录？使用 `/grill-me`——见独立章节。两者都运行同一个 `/grilling` 原语；`grill-with-docs` 是留下文字记录的那个，这使得每当有仓库可以留下记录时，它是两者中更好的一个。）
2. **分支——你能在对话中解决所有问题吗？** 如果一个问题需要可运行的答案（状态、业务逻辑、一个你必须看到的 UI），绕道经过原型，两个方向都用 **`/handoff`** 衔接（原型存在于它自己的目录中，这正是 `/handoff` 的用途——见阶段边界）：
   - **`/handoff`** 出去，然后针对该文件打开一个新会话，
   - **`/prototype`** 用一次性代码回答这个问题，
   - **`/handoff`** 把你学到的东西带回来，并在原始想法线程中引用它。
3. **分支——这是一个多会话构建吗？**
   - **是** → **`/to-spec`**（把线程转化为规格），然后 **`/to-tickets`** 把它拆分成曳光弹工单，每个工单声明它的**阻塞边（blocking edges）**。在本地跟踪器上，就是 `.scratch/<feature>/issues/` 下每个工单一个文件，按阻塞者优先手工处理；在真实跟踪器上，这些边变成原生的阻塞链接，因此任何阻塞者已完成的工单都可以被拿起——每个工单发起 **`/implement`**，每个工单之间 **`/clear`** 上下文。每个工单自包含，所以最后一个工单的上下文是可以丢弃的。
   - **否** → 就在同一个上下文窗口中执行 **`/implement`**。

   无论哪种方式，**`/implement`** 通过在内部驱动 **`/tdd`** 来构建每个 issue——一次一个红绿切片——然后在提交前运行 **`/code-review`**（对 diff 的双轴审查：标准 + 规格）收尾。当你只想在测试先行的情况下构建一个具体行为、而不需要完整规格时，单独使用 **`/tdd`**；当你只想针对一个固定点审查分支或 PR 时，单独使用 **`/code-review`**。

### 上下文卫生

让第 1–3 步保持在**一个不间断的上下文窗口**中——在 `/to-tickets` 之前不要压缩或清除——这样访谈、规格和工单都建立在同一个思考之上。然后每个 `/implement` 从工单出发，重新开始。

这方面的限制是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍然清晰推理的窗口（在最先进的模型上约 150k token）。如果会话在 `/to-tickets` 之前接近它，不要在退化状态下硬撑——在最近的阶段边界 **`/compact`** 并继续（见阶段边界）。

## 入口匝道

一个产生工作的起始情况，然后汇入主线流程。

- **bug 和请求堆积** → **`/triage`**。它让 issue 穿过分流角色，产生 agent-ready 的 issue，稍后由 **`/implement`** 接手。

  分流只针对**不是你创建的** issue——bug 报告、进来的功能请求、任何原始到达的东西。`/to-tickets` 产生的工单已经是 agent-ready 的，所以**不要分流它们**。

- **有东西坏了** → **`/diagnosing-bugs`**。针对难缠的情况：第一眼看不出的 bug、间歇性 flake、在两个已知良好状态之间悄悄出现的回归。它拒绝在有一个**紧凑的反馈循环**之前做理论推演——一个已经在这个 bug 上变红的命令——然后用回归测试修复。当真正的发现是"没有好的接缝来锁住这个 bug"时，它的复盘会交接给 **`/improve-codebase-architecture`**。

- **一项巨大而模糊的努力——一个绿地项目或一个大型功能构建，对单个会话来说太大** → **`/wayfinder`**，这里是认知要求最高的流程。当从这里到目的地的路还不可见时，它在 issue 跟踪器上绘制一张**决策工单**的**共享地图**，并一次解决一个——产出**决策，而不是交付物**——直到迷雾被推回、道路清晰。**`/grill-with-docs`** 打磨的是你能在单个会话中容纳的想法，而 wayfinder 是为你不能容纳的想法准备的——而且它更慢更密集，所以只把它留给那种情况，永远不要用于一个范围明确的特性。

  当地图清晰时，**它交接，而不是构建**：在 **`/to-spec`** 汇入主线流程，它把地图的关联决策折叠成一个可构建的计划，然后照常 `/to-tickets` 和 `/implement`。把地图直接循环进 `/implement` 会跳过那个折叠并丢掉关联的细节——只有当努力结果真正很小时才直接去 `/implement`。

## 代码库健康

不是特性工作——是维护。

- **`/improve-codebase-architecture`** — 每当你有空闲时间保持代码库对 agent 的良好运作状态时运行。它浮现**深化机会**；挑选一个*会生成一个想法*，你可以带着它进入主线流程的 `/grill-with-docs`。它是找到候选者的勘察；**`/codebase-design`**（下方）是你设计所选方案的工作台。

## 底层的词汇

两个模型调用的参考，运行在*其他*技能的*底层*——各自是其词汇的单一事实来源。当问题是**词**而不是流程时直接取用它们；或者让上面的技能把它们拉进来。

- **`/domain-modeling`** — 打磨项目的*领域*语言：挑战一个模糊的术语，解决一个过载的词（"account" 干着三份工作），把一个难以逆转的决策记录为 ADR。它是 `/grill-with-docs` 驱动、让 `CONTEXT.md` 保持为一份干净词汇表的活跃纪律。
- **`/codebase-design`** — 深模块词汇（模块、接口、深度、接缝、适配器、杠杆、局部性），用于设计模块的*形态*：大量行为隐藏在干净接缝上的小接口之后。`/tdd` 和 `/improve-codebase-architecture` 都说这种语言。

## 阶段边界

一个**阶段**是会话内的一块工作——访谈、实现、QA。在两者之间的**边界**上你有五个选项，在它们之间选择是整个地图中最模糊的决策：

- **继续** — 留在原地。不花钱，不丢东西。
- **`/clear`** — 清空窗口，当这里没有东西与下一步相关时。
- **`/handoff`** — 写一个可移植的 markdown 文件。范围很窄：只用于**新 harness**、**新目录**、**同事**，或在**阶段中间**分叉一个附带任务。它买到的是可移植性。
- **子 agent** — 把一个范围严格的任务送到它自己的窗口，拿回一份报告。
- **`/compact`** — 压缩这个上下文并用它播种一个新会话。**默认**，位于树的底部而不是首选。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解有序的树——五个问题、每个分支背后的推理，以及为什么首要来源成本使 **继续** 成为第一个被排除的选项。在边界处**做出决定**；在阶段中途，继续或把剩余部分拆成子 agent。

## 独立

完全不在主线流程上。

- **`/grill-me`** — 与 `/grill-with-docs` 相同的锲而不舍的访谈，但**无状态**：它本地什么都不保存，也不构建 `CONTEXT.md`。当你在**非工作目录**中工作时使用它——打磨一个计划、一个设计、一篇写作，任何下面没有仓库的东西。如果你在工作目录中，改用 `/grill-with-docs`：它运行相同的访谈并留下文字记录，所以严格来说是更好的那个。
- **`/grilling`** — 访谈原语本身：轮次、前沿，事实是 agent 的工作、决策是你的。`/grill-me` 和 `/grill-with-docs` 是两个命名的入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有当你想要不带包装的访谈时，才直接取用它。
- **`/resolving-merge-conflicts`** — 逐个 hunk 处理进行中的 merge 或 rebase 冲突，根据追溯到的每一边的首要来源的**意图**来解决，而不是靠挑选行，然后完成该操作。它从不运行 `--abort`。独立且脱离所有流程：当你已经处于冲突中时取用它。
- **`/prototype`** — 一个小的、一次性的程序，回答一个设计问题：这个状态模型感觉对吗，或者这个 UI 应该长什么样。一次性是对代码编写方式的一种约束，而不是销毁它的承诺：答案折叠进真实代码，原型本身作为**首要来源**保存在 main 之外的一个 `prototype/<name>` 分支上，从实现 issue 指向它。它是主线流程第 2 步中的绕道，但任何时候一个设计问题难以在纸上解决，都可以取用它。
- **`/research`** — 把阅读的苦活委托给一个**后台 agent**：它针对**首要来源**调查一个问题，然后在仓库中留下一份带引用的 Markdown 文件。它阅读时你可以继续工作。它产出的文件是要带入主线流程 `/grill-with-docs` 的东西——研究喂给思考，而不是替代思考。
- **`/to-questionnaire`** — 当挡住你的东西不在你脑子里也不在代码库里，而在**别人的**脑子里时，这个技能写一份问卷给他们填写。它是 `/grill-me` 的反面：不是就主题采访你，而是就**发送**采访你——发给谁、你需要拿回什么——并把问题瞄准差距。拿回来的东西是 `/grill-with-docs` 或 `/to-spec` 的材料。
- **`/wizard`** — 用于只有**人类**能采取的步骤：配置基础设施、设置凭据或 CI 机密、点击陌生的第三方仪表盘、运行一次性迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL、捕获每个值，并把它们写入 `.env` 和 GitHub 机密——这样该流程就不再需要你每次向 agent 重新解释。模型调用，所以 agent 一碰到只有你能通过的墙就会取用它。如果 agent 能自己做，它就应该做；这是给一个人类真正在环里的情况。
- **`/wait-what`** — 对一条没落地的消息的纠正。在对话中途、任何其他技能内部使用它，agent 会用你缺失的上下文、以通俗英语、使用 `CONTEXT.md` 词汇重新解释它刚说过的话。它事后起作用；`/grill-with-docs` 是事先的解药，因为早先约定好的共享语言才是阻止行话一开始就出现的东西。
- **`/teach`** — 在多个会话中学习一个概念，使用当前目录作为有状态的工作空间。
- **`/writing-for-agents`** — 为 agent 消费的文档编写的参考：技能、AGENTS.md、被指向的文档。

## 前提条件
