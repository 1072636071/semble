# 逻辑原型

一个单一的、自包含的 HTML 文件——一个**可共享的演示**——让任何人通过点击按钮驱动一个状态模型。当问题涉及**业务逻辑、状态转换或数据形态**时使用——那种在纸上看合理、但只有当你把它推过真实用例时才会感觉不对劲的东西。

因为它是一个文件、无需安装，你可以把它交给非开发者——设计师、PM、领域专家——让他们自己感受这个模型。所以它说他们的语言，而不是代码的语言。

## 何时这是正确的形态

- "我不确定这个状态机是否能处理 X 然后 Y 的边缘情况。"
- "这个数据模型真的让我能表达……的情况吗？"
- "我想在写 API 之前先感受一下它应该是什么样。"
- 任何某人想要**按下按钮并观看状态变化**的情况。

如果问题是"这应该长什么样"——错误的分支。使用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

在写代码之前，写下你在原型化的状态模型和问题。一段话，放在演示的顶部（在一个可见的介绍中，而不仅仅是注释）。一个回答了错误问题的逻辑原型是纯粹的浪费——让问题明确，这样它可以稍后被检查，无论用户是现在看着还是 AFK 后回来。

### 2. 把逻辑隔离在一个可移植模块中

把实际逻辑——回答问题的那部分——放在一个单一的 `<script>` 块中，写成一个小的纯模块，以后可以抬出来放进真实代码库。它周围的页面是一次性的；这个模块不是。

正确的形态取决于问题：

- **一个纯 reducer** — `(state, action) => state`。当动作是离散事件且状态是单一值时很好。
- **一个状态机** — 显式的状态和转换。当"哪些动作现在甚至是合法的"是问题的一部分时很好。
- **一个普通数据类型上的一组纯函数**。当没有隐式的当前状态时——只是转换——很好。
- **一个有清晰方法表面的类或模块**，当逻辑真正拥有持续的内部状态时。

选择最贴合所问问题的形态，*而不是*最容易接线到页面的形态。保持纯：没有 DOM、没有 `document`、没有按钮处理程序伸进去。页面调用它；没有东西朝另一个方向流动。这正是让原型在它自己的生命周期之后还有用的东西：一旦问题被回答，验证过的 reducer / 机器 / 函数集会自行抬入真实模块。

### 3. 构建可共享的 HTML 文件

一个文件，纯 HTML/CSS/JS——没有框架、没有打包器、没有服务器，一切内联，这样它双击就能打开，被邮件转发也能存活。任何人都应该能通过打开它来运行它。

为非开发者写它。每个标签都使用**领域语言**，而不是代码——按钮和状态读起来像业务，而不是像 reducer。用通俗的话解释正在发生什么。

用干净的分层布局它，从上到下：

1. **标题和一行解释**，说明这个演示让你探索什么（第 1 步的问题）。
2. **当前状态** —— 完整的相关状态，渲染为一个可读的面板（带标签的字段，而不是原始 JSON 转储），每次点击后重新渲染，这样变化可见。在有助于非开发者跟上时，指出刚发生了什么变化。
3. **自由操作按钮** —— 每个动作一个按钮，总是可用，这样任何人都可以按任意顺序戳模型。每次点击派发它的动作并重新渲染状态。
4. **引导式走查** —— 一组**场景**，每个标签页一个。每个标签页持有一个简短的、通俗语言的场景描述——它建立的情况和要注意什么——在它下面，是该场景要按的**有序按钮**。每一步都是一个真实按钮：点击它执行那个动作并进入下一步。开始一次走查会重置到一个已知的初始状态，这样场景每次都以相同方式运行。

选择演示尴尬情况的场景——快乐路径、一个棘手的边缘情况、一次对应该非法的东西的尝试——那些在纸上难以推理的。

保持美观但克制：干净的排版、充足的空间、一个强调色。没有动画、没有噱头——没有什么与状态和按钮竞争。

### 4. 交接

把文件发给他们，或为他们打开。他们会在有空的时候点穿走查和自由操作；有趣的时刻是当他们说"等等，那不应该可能"或"嗯，我以为 X 会不同"时——那些是_想法_里的 bug，而这正是全部要点。如果他们想要新动作或新场景，添加它们。原型会进化。

### 5. 捕获答案和原型

一旦原型回答了它的[SKILL](SKILL.md)问题，捕获答案，然后按技能描述的方式捕获原型。逻辑特定的映射：验证过的 reducer / 机器 / 函数集抬入真实模块（决策，被吸收）；HTML 外壳搭车到保持原型作为首要来源的一次性分支——而且因为它是一个自包含文件，它在那边保持琐碎地可重新运行。

## 反模式

- **不要添加测试。** 一个需要测试的原型不再是原型。
- **不要把它接到真实数据库。** 使用内存状态，除非问题专门关于持久化。
- **不要泛化。** 没有"万一我们以后想支持 X 呢。"原型回答一个问题。
- **不要模糊逻辑和页面。** 如果纯模块引用了 DOM、`document` 或按钮处理程序，它就不再可抬升。保持页面作为纯模块上的一个薄外壳。
- **不要伸手去拿框架、打包器或服务器。** 接收者双击的一个文件；一个 React 应用或 dev 服务器会打败"可共享"。
- **不要把 HTML 外壳送进生产。** 页面为手工点击优化。它背后的逻辑模块才是值得保留的部分。
