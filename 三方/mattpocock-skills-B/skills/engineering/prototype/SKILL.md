# 原型

一个原型是**回答一个问题的抛弃型代码**。问题决定形态。

## 选择一个分支

识别正在回答哪个问题——从用户的提示、周围的代码，或如果用户在附近就问：

- **"这个逻辑 / 状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个单一可共享的 HTML 文件——自由操作按钮加上标签页的引导式走查——把状态机推向纸上难以推理的用例，并且非开发者也能驱动。
- **"这应该长什么样？"** → [UI.md](UI.md)。在单一路由上生成几个截然不同的 UI 变体，通过 URL 搜索参数和一个浮动底栏切换。

两个分支产生非常不同的工件——搞错这一点会浪费整个原型。如果问题确实模糊且用户不可达，默认选择更匹配周围代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这个假设。

## 两者都适用的规则

1. **从第一天起就是一次性的，并明确标记为如此。** 把原型代码放在靠近它实际会被使用的地方（紧挨着它为之原型设计的模块或页面），这样上下文是明显的——但命名要让普通读者能看出它是原型，而不是生产代码。对于一次性的 UI 路由，遵循项目已经使用的任何路由约定；不要发明新的顶层结构。
2. **易于运行。** UI 原型从项目任务运行器中的一个命令开始——`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是用户双击的一个单一 HTML 文件。无论哪种方式，启动它不需要思考。
3. **默认不持久化。** 状态存在于内存中。持久化是原型正在*检查*的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，使用一个带清晰"PROTOTYPE — wipe me（原型——擦掉我）"名字的 scratch 数据库或本地文件。
4. **跳过打磨。** 没有测试，没有超出让原型*可运行*所需的错误处理，没有抽象。关键是快速学到东西。
5. **浮现状态。** 在每次操作后（逻辑）或每次变体切换时（UI），打印或渲染完整的相关状态，这样用户能看到什么变了。
6. **完成后捕获。** 把任何已验证的决策折叠进真实代码，然后把原型本身作为**首要来源**捕获：提交到 main 之外的一个一次性分支，并在实现 issue 上留下一个指向该分支的上下文指针。也捕获答案——裁决和它解决的问题——写在 issue 或 commit 中。main 分支只保留已验证的决策。
