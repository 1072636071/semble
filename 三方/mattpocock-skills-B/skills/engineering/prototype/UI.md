# UI 原型

在单一路由上生成**几个截然不同的 UI 变体**，从一个浮动底栏切换。用户在浏览器中翻转变体，挑选一个（或从每个中偷取一些部分），然后把其余扔掉。

如果问题关于逻辑/状态而不是某个东西长什么样——错误的分支。使用 [LOGIC.md](LOGIC.md)。

## 何时这是正确的形态

- "这个页面应该长什么样？"
- "我想在承诺之前看看这个仪表盘的几个选项。"
- "为设置屏幕试试不同的布局。"
- 任何用户否则会在脑子里花一天在三个模糊 mockup 之间挑选的时候。

## 两个子形态——强烈偏好子形态 A

当一个 UI 原型**紧贴着应用的其余部分**时——真实 header、真实侧边栏、真实数据、真实密度——它更容易被评判。一个单独的抛弃路由是一个真空：每个变体在隔离中都看起来不错。每当有一个合理的现有页面可以承载变体时，默认为子形态 A。只有当原型真的没有附近的家时，才伸手去取子形态 B。

### 子形态 A — 对现有页面的调整（首选）

路由已经存在。变体在**同一路由**上渲染，由一个 `?variant=` URL 搜索参数门控。现有的数据获取、参数和认证都保留——只有渲染被替换。这是默认；除非有特定理由，否则选它。

如果原型是为还没有页面、但*自然会住在一个页面内部*的东西（仪表盘的新部分、设置屏幕上的新卡片、现有流程中的新步骤）——那仍然是子形态 A。把变体挂载在宿主页面内部。

### 子形态 B — 一个新页面（最后手段）

只有当被原型化的东西真的没有现有页面可以住在里面时——例如一个全新的顶层表面，或一个无法嵌入任何合理地方的流程——才使用这个。

创建一个**抛弃路由**，遵循项目已经使用的任何路由约定——不要发明新的顶层结构。命名让它明显是原型（例如在路径或文件名中包含 `prototype` 这个词）。相同的 `?variant=` 模式。

在承诺子形态 B 之前，做 sanity-check：真的没有这个可以被嵌入的现有页面吗？一个空路由会隐藏一个有内容的路由会暴露的设计问题。

在两种子形态中，浮动底栏是相同的。

## 流程

### 1. 陈述问题并挑选 N

默认为 **3 个变体**。超过 5 个就不再是截然不同，而开始变成噪音——封顶在那里。

用一行写下计划，放在原型的所在位置或文件顶部注释中：

> "设置页面的三个变体，通过 `?variant=` 切换，在现有的 `/settings` 路由上。"

无论用户在这里推回与否，这都有效。

### 2. 生成截然不同的变体

起草每个变体。让每个坚持：

- 页面的目的和它能访问的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，随便什么）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构性不同**——不同的布局、不同的信息层级、不同的主要操作——而不仅仅是不同的颜色。三个微调的卡片网格不是 UI 原型，是壁纸。如果两个草稿太相似，用明确的"不要使用卡片网格"指导重做一个。

### 3. 把它们接线在一起

在路由上创建一个单一切换器组件：

```tsx
// 伪代码——适配到项目的框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A（现有页面）：保持切换器上方所有现有数据获取；只有渲染的子树按变体变化。

对于子形态 B（新页面）：`/prototype/<name>` 下的抛弃路由挂载相同的切换器。

### 4. 构建浮动切换器

屏幕底部中央的一个小的固定位置栏，有三个部分：

- **左箭头** — 循环到上一个变体（环绕）。
- **变体标签** — 显示当前变体键，如果变体导出了名字，也显示那个名字。例如 `B — Sidebar layout`。
- **右箭头** — 向前循环（环绕）。

行为：

- 点击箭头更新 URL 搜索参数（使用框架的路由器——Next 上 `router.replace`、React Router 上 `navigate` 等），这样变体可共享且刷新稳定。
- 键盘：`←` 和 `→` 箭头键也循环。当 `<input>`、`<textarea>` 或 `[contenteditable]` 聚焦时不要拦截箭头键。
- 视觉上与页面区分（例如高对比度胶囊、微妙的阴影），这样它明显不是正在评估的设计的一部分。
- 在生产构建中隐藏——用 `process.env.NODE_ENV !== 'production'` 或等效检查门控，这样一个误合并的原型不会把栏送给用户。

把切换器放在一个单一共享组件中，这样两种子形态都能复用。把它放在项目共享 UI 所在的任何地方。

### 5. 交接

浮出 URL（和 `?variant=` 键）。用户会在有空时翻转。有趣的反馈通常是**"我想要 B 的 header 配 C 的侧边栏"**——那是他们真正想要的设计。

### 6. 捕获答案并清理

一旦一个变体获胜，捕获答案——哪个变体以及为什么——然后按 [SKILL](SKILL.md) 描述的方式捕获原型。把赢家折叠进真实代码，把其余移到抛弃分支上，而不是进 main：

- **子形态 A** — 把赢家折叠进现有页面；把失败的变体和切换器从 main 中丢弃。
- **子形态 B** — 把获胜变体提升为真实路由；把抛弃路由和切换器从 main 中丢弃。

完整的变体集是首要来源，所以它落在抛弃分支上，而不是垃圾箱——留在 main 分支的变体组件和切换器会快速腐烂并困惑下一个读者。

## 反模式

- **只在颜色或文案上不同的变体。** 那是一个调整，不是原型。真正的变体在结构上不同意。
- **在变体之间共享太多代码。** 一个共享的 `<Header>` 没问题；一个共享的 `<Layout>` 会打败目的。每个变体应该能自由扔掉布局。
- **把变体接到真实变更。** 只读原型没问题。如果变体需要变更，把它指向一个存根——问题是"这应该长什么样"，而不是"后端工作吗"。
- **把原型直接提升到生产。** 变体代码是在原型约束下写的（没有测试、最小错误处理）。当你折叠它时，正确地重写它。
