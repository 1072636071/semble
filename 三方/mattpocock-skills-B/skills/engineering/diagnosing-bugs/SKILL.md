# 诊断 Bug

一种针对难缠 bug 的纪律。除非有明确理由，否则不要跳过阶段。

探索代码库时，阅读 `CONTEXT.md`（如果存在）以获得相关模块的清晰心智模型，并检查你正在触碰的区域的 ADR。

## 脱敏

本技能会让你展示命令、输出和捕获的工件。**首先脱敏每一个机密**——用 `<REDACTED>` 写在它的位置。针对环境变量构建循环，这样凭据留在环境中而不是留在你展示的内容里。捕获的工件带有认证头：只引用携带信号的几行。

如果脱敏后的输出不足以诊断这个 bug，如实说明并询问用户。

## 阶段 1 — 构建一个反馈循环

**这才是这个技能。**其他一切都是机械性的。如果你有一个针对这个 bug 的**紧凑**的通过与失败信号——一个在*这个* bug 上变红的信号——你就会找到原因；二分、假设检验和插桩都只是消耗它。如果你没有，盯着代码看再多也救不了你。

在这里投入不成比例的精力。**要激进。要有创造力。拒绝放弃。**

### 构建一个的方式——大致按这个顺序尝试

1. **失败测试** —— 在到达 bug 的任何接缝处：单元、集成、e2e。
2. **Curl / HTTP 脚本** —— 针对运行中的开发服务器。
3. **CLI 调用** —— 用夹具输入，将 stdout 与已知良好的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）—— 驱动 UI，对 DOM/console/network 断言。
5. **重放捕获的跟踪。** 把一个真实的网络请求 / 载荷 / 事件日志保存到磁盘；通过代码路径在隔离中重放它。
6. **一次性 harness。** 启动系统的一个最小子集（一个服务、mock 依赖），用单个函数调用运行触发 bug 的代码路径。
7. **属性 / fuzz 循环。** 如果 bug 是"有时输出错误"，运行 1000 个随机输入并寻找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态之间（commit、数据集、版本），自动化"在状态 X 启动、检查、重复"，这样你可以 `git bisect run` 它。
9. **差异循环。** 对旧版本 vs 新版本（或两种配置）运行相同的输入，并 diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须由人类点击，用 `scripts/hitl-loop.template.sh` 驱动*他们*，这样循环仍然是结构化的。捕获的输出反馈给你。

构建正确的反馈循环，bug 就修好了 90%。

### 收紧循环

把循环当作产品来对待。一旦你有了_一个_循环，就**收紧**它：

- 我能让它更快吗？（缓存设置、跳过无关初始化、缩小测试范围。）
- 我能让信号更锋利吗？（针对具体症状断言，而不是"没有崩溃"。）
- 我能让它更确定性吗？（固定时间、播种 RNG、隔离文件系统、冻结网络。）

一个 30 秒的 flaky 循环几乎不比没有循环好；一个 2 秒确定性的循环就是紧凑——一种调试超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。循环触发 100 次、并行化、施加压力、收窄时序窗口、注入 sleep。一个 50% flake 的 bug 是可调试的；1% 不是——不断提高复现率，直到它可调试。

### 当你真的无法构建一个循环时

停下来并明确说明。列出你尝试过的东西。向用户请求：(a) 访问任何能复现它的环境，(b) 一个脱敏的捕获工件（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或 (c) 添加临时生产插桩的许可。**不要**在没有循环的情况下进入假设阶段。

### 完成标准——一个变红的紧凑循环

当循环**紧凑**且**可变红**时，阶段 1 完成：你能说出**一个命令**——一个脚本路径、一个测试调用、一个 curl——你**已经至少运行过一次**（展示调用和它的输出，已脱敏），并且它：

- [ ] **可变红** —— 它驱动实际的 bug 代码路径并断言**用户的精确症状**，因此它可以在本 bug 上变红、在修复后变绿。不是"运行不报错"——它必须能*抓住这个特定的 bug*。
- [ ] **确定性** —— 每次运行得出相同裁决（flaky bug：一个固定的高复现率，如上所述）。
- [ ] **快速** —— 秒级，不是分钟级。
- [ ] **agent 可运行** —— 你可以无人值守运行它；人类只在 `scripts/hitl-loop.template.sh` 中进入循环。

如果你发现自己在这个命令存在之前就阅读代码来构建理论，**停下——直接跳到假设正是这个技能要防止的确切失败。**没有可变红的命令，就没有阶段 2。

## 阶段 2 — 复现 + 最小化

运行循环。看着它变红——bug 出现了。

确认：

- [ ] 循环产生**用户**描述的失败模式——而不是恰好出现在附近的另一个失败。错误的 bug = 错误的修复。
- [ ] 失败在多次运行中可复现（或者，对于非确定性 bug，以足够高的比率可复现，足以针对它调试）。
- [ ] 你捕获了精确的症状（错误消息、错误的输出、缓慢的时序），以便后续阶段可以验证修复确实解决了它。

### 最小化

一旦它变红，把复现缩小到**仍然变红的最小场景**。一次削减一个输入、调用者、配置、数据和步骤，每次削减后重新运行循环——只保留对失败至关重要的部分。

为什么要费心：一个最小复现缩小了阶段 3 中的假设空间（剩下的可怀疑部件更少），并成为阶段 5 中干净的回归测试。

当**每个剩余元素都至关重要**时完成——移除其中任何一个都会让循环变绿。

在复现**并**最小化之前不要继续。

## 阶段 3 — 假设

在测试任何一个假设之前，生成 **3–5 个排名的假设**。单假设生成会锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：陈述它做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更糟。"

如果你无法陈述预测，这个假设就是一种感觉——丢弃或磨锋利它。

**在测试之前向用户展示排名列表。**他们往往拥有能立即重新排序的领域知识（"我们刚部署了对 #3 的变更"），或知道他们已经排除的假设。便宜的检查点，巨大的省时。不要阻塞在上面——如果用户 AFK，用你的排名继续。

## 阶段 4 — 插桩

每个探针必须对应阶段 3 中的一个特定预测。**一次改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查** —— 如果环境支持。一个断点胜过十个日志。
2. **定向日志** —— 在能区分假设的边界处。
3. 永远不要"记录一切然后 grep"。

**给每个调试日志打上唯一前缀的标签**，例如 `[DEBUG-a4f2]`。结尾的清理变成一次 grep。未打标签的日志会存活；打标签的日志会消亡。

**性能分支。** 对于性能回归，日志通常是错的。改为：建立一个基线测量（计时 harness、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 阶段 5 — 修复 + 回归测试

**在修复之前**写回归测试——但只在有**正确接缝**的情况下。

正确接缝是指测试在调用点锻炼**真实的 bug 模式**的地方。如果唯一可用的接缝太浅（bug 需要多个调用者时做单调用者测试、无法复现触发 bug 的链的单元测试），那里的回归测试会给出虚假的信心。

**如果没有正确的接缝，那本身就是发现。** 记下它。代码库架构正在阻止 bug 被锁住。为下一个阶段标记这一点。

如果存在正确的接缝：

1. 把最小化的复现变成该接缝上的一个失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 针对原始（未最小化）场景重新运行阶段 1 的反馈循环。

## 阶段 6 — 清理 + 复盘

在宣布完成之前必须完成：

- [ ] 原始复现不再复现（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或接缝缺失已被记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 前缀）
- [ ] 一次性原型已删除（或移到明确标记的调试位置）
- [ ] 结果正确的假设写在 commit / PR 消息中——这样下一个调试者能学到

**然后问：什么本可以阻止这个 bug？** 如果答案涉及架构变更（没有好的测试接缝、纠缠的调用者、隐藏的耦合），把细节交接给 `/improve-codebase-architecture` 技能。在修复完成**之后**提出建议，而不是之前——你现在拥有的信息比你开始时多。
