# 测试驱动开发

TDD 是红 → 绿循环。本技能是让那个循环产出值得保留的测试的参考：好测试是什么、测试放在哪里、反模式、以及循环的规则。每个章节在每个循环中都适用——在循环之前和期间查阅它们，而不是之后。

探索代码库时，阅读 `CONTEXT.md`（如果存在），让测试名称和接口词汇与项目的领域语言匹配，并尊重你正在触碰区域的 ADR。

## 什么是好测试

测试通过公开接口验证行为，而不是实现细节。代码可以彻底改变；测试不应该。一个好测试读起来像一份规格——"用户可以用有效购物车结账"准确告诉你存在什么能力——并且因为它不在乎内部结构，所以能在重构中存活。

示例参见 [tests.md](tests.md)，mock 指南参见 [mocking.md](mocking.md)。

## 接缝——测试放在哪里

**接缝（seam）** 是你测试的公开边界：你观察行为而不伸手进去的接口。测试位于接缝处，绝不针对内部。

**只在预先约定的接缝处测试。** 在写任何测试之前，写下正在测试的接缝并与用户确认。没有测试写在未确认的接缝上。你无法测试一切——提前约定接缝是让测试努力落在关键路径和复杂逻辑上、而不是每个边缘用例上的方式。

问："公开接口是什么，我们应该测试哪些接缝？"

当接口本身的形态也在讨论中——模块有多深、接缝在哪里、接口应暴露什么——使用 `/codebase-design` 技能获取词汇。它是模块、接口、深度、接缝、适配器、杠杆和局部性术语的共享来源，是一个要查阅的参考，而不是一个要运行的会话。

## 反模式

- **实现耦合** —— mock 内部协作者、测试私有方法，或通过侧通道验证（查询数据库而不是使用接口）。特征：当你重构但行为没变时测试会断。
- **同义反复** —— 断言用代码的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、一个用手同样方式做的快照、一个与自身相等的常量），所以它构造上就通过，永远无法与代码不一致。期望值必须来自独立的事实来源——已知良好的字面量、一个演练过的例子、规格。
- **水平切片** —— 先写所有测试，再写所有实现。批量测试验证*想象中的*行为：你测试东西的*形态*而不是面向用户的行为，测试对真实变更变得不敏感，而且你在理解实现之前就承诺了测试结构。改为按**垂直切片**工作——一个测试 → 一个实现 → 重复，每个测试都是一颗**曳光弹**，回应上一个循环教给你的东西。

## 循环的规则

- **绿之前先红。** 先写失败的测试，然后只写足以通过它的代码。不要预判未来的测试或添加推测性特性。
- **一次一个切片。** 每个循环一个接缝、一个测试、一个最小实现。
- **重构不是循环的一部分。** 它属于审查阶段（参见 `code-review` 技能），而不是红 → 绿实现循环。
