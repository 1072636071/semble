# 分流

让项目问题跟踪器上的 issue 穿过一个分流角色的小状态机。

如果本仓库把外部 pull request 视为一个请求表面（参见 issue-tracker 配置），分流也覆盖它们：**一个 PR 就是一个附带了代码的 issue**——相同的角色、相同的状态、相同的机器，只有几处下方标记为"for a PR"的差异。根据跟踪器配置，把裸 `#42` 解析为 issue 或 PR。

在分流期间发布到 issue 跟踪器的每条评论或 issue **必须**以这个免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — 如何编写耐用的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` 知识库如何工作

## 角色

两个**类别**角色：

- `bug` — 有东西坏了
- `enhancement` — 新功能或改进

五个**状态**角色：

- `needs-triage` — 维护者需要评估
- `needs-info` — 等待报告者提供更多信息
- `ready-for-agent` — 完全明确，可供 AFK agent 使用
- `ready-for-human` — 需要人类实现
- `wontfix` — 不会被处理

对于 PR，同样的状态针对附带的代码解读：`ready-for-agent` 意味着附有简报、agent 应该对 diff 采取下一步；`ready-for-human` 意味着它已准备好让人类合并。

每个已分流的 issue 应该恰好携带一个类别角色和一个状态角色。如果状态角色冲突，标记它并在做任何其他事情之前询问维护者。

这些是规范的角色名称——issue 跟踪器中实际使用的标签字符串可能不同。映射应已提供给你——若未提供，运行 `/setup-matt-pocock-skills`。

状态转换：一个未标记的 issue 通常先去 `needs-triage`；从那里它转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦报告者回复，`needs-info` 返回 `needs-triage`。维护者可以随时覆盖——标记看起来不寻常的转换并在继续之前询问。

## 调用

维护者调用 `/triage` 并用自然语言描述他们想要什么。解释请求并行动。示例：

- "Show me anything that needs my attention"
- "Let's look at #42"（issue 或 PR）
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## 展示需要关注的内容

查询 issue 跟踪器并呈现三个桶，最旧的在前：

1. **未标记** — 从未分流。
2. **`needs-triage`** — 评估进行中。
3. **自上次分流记录以来有报告者活动的 `needs-info`** — 需要重新评估。

当 PR 在范围内时，把外部 PR 包含进这些桶中，并在每行打 `[PR]` 或 `[issue]` 标签。发现只浮现*外部* PR（跟踪器配置定义谁算外部）——协作者的进行中 PR 不是分流工作。这个过滤只针对发现；一个被明确点名的 PR 无论作者是谁总是被分流。

显示每个条目的数量和一行摘要。让维护者挑选。

## 分流一个特定 issue 或 PR

1. **收集上下文。** 阅读完整的 issue 或 PR（正文、评论、标签、作者、日期；对于 PR，还有 diff）。解析任何先前的分流记录，这样你不会重新问已解决的问题。使用项目的领域词汇表探索代码库，尊重你正在触碰区域的 ADR。对代码库运行两个检查：(a) **冗余** —— 按领域概念搜索请求行为的现有实现（而不仅仅是请求的措辞），并报告你在哪里找过。如果找到了，就是一个已实现的 `wontfix`（第 5 步）。(b) **先前拒绝** —— 阅读 `.out-of-scope/*.md` 并浮现任何与这个请求相似的。

2. **建议。** 告诉维护者你的类别和状态建议及理由，加上与请求相关的简要代码库摘要——包括它是否已实现。等待指示。

3. **验证声明。** 在任何访谈之前，检查声明是否站得住脚。对于 bug，按报告者的步骤复现它。对于 PR，确认 diff 做了它声称的——把它 checkout，运行相关测试或命令。报告发生了什么：已确认（带代码路径）、失败、或细节不足（一个强烈的 `needs-info` 信号）。一个已确认的验证会做出一个强得多的 agent 简报。

4. **访谈（如果需要）。** 如果请求需要充实，一起运行 `/grilling` 和 `/domain-modeling` 技能——一轮一轮地问问题把它访谈成形，在决策落地时磨锋利领域术语并就地更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent` — 发布一条 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` — 结构与 agent 简报相同，但说明为什么不能委托（判断调用、外部访问、设计决策、手动测试）。
   - `needs-info` — 发布分流记录（下方模板）。
   - `wontfix` — 关闭，评论取决于*为什么*：
     - **已实现** — 变更已经存在于代码库中。指出它在哪里；**不要**写入 `.out-of-scope/`（那个知识库是给*被拒绝*的请求的，不是已构建的）。
     - **被拒绝（bug）** — 礼貌解释，然后关闭。
     - **被拒绝（enhancement）** — 写入 `.out-of-scope/`，从评论中链接到它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` — 应用角色。如果有部分进展，可选加评论。

## 快速状态覆盖

如果维护者说"move #42 to ready-for-agent"，相信他们并直接应用角色。确认你即将做的事（角色变更、评论、关闭），然后行动。跳过访谈。如果在没有访谈会话的情况下移到 `ready-for-agent`，询问他们是否想写一份 agent 简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把访谈期间解决的每件事都捕获在"established so far"下，这样工作不会丢失。问题必须具体且可操作，而不是"请提供更多信息"。

## 恢复之前的会话

如果 issue 或 PR 上存在先前的分流记录，阅读它们，检查报告者是否回答了任何未解决的问题，并在继续之前呈现一个更新的图景。不要重新问已解决的问题。
