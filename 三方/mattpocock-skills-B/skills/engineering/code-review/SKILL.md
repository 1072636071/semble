对 `HEAD` 与用户提供的固定点之间 diff 的双轴审查：

- **标准** —— 代码是否符合本仓库记录的编码标准？
- **规格** —— 代码是否忠实地实现了来源 issue / 规格？

两条轴线都作为**并行子 agent** 运行，这样它们不会污染彼此的上下文，然后本技能汇总它们的发现。

issue 跟踪器应该已经提供给你了——如果 `docs/agents/issue-tracker.md` 缺失，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定固定点

无论用户说的固定点是什么——一个 commit SHA、分支名、标签、`main`、`HEAD~5` 等。如果他们没指定，就问。

一次捕获 diff 命令：`git diff <fixed-point>...HEAD`（三个点，因此比较是针对 merge-base 的）。也通过 `git log <fixed-point>..HEAD --oneline` 记下 commit 列表。

在进一步之前，确认固定点可以解析（`git rev-parse <fixed-point>`）且 diff 非空。一个错误的引用或空的 diff 应该在这里失败——而不是在两个并行子 agent 内部。

### 2. 识别规格来源

按此顺序寻找来源规格：

1. commit 消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或特性匹配的规格文件。
4. 如果什么都没找到，问用户规格在哪里。如果他们说不存在，**规格**子 agent 将跳过并报告"无规格可用"。

### 3. 识别标准来源

仓库中任何记录代码应如何编写的文档，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

在仓库记录的规范之上，标准轴线总是携带下面的**坏味道基线**——一组固定的 Fowler 代码坏味道（《重构》第 3 章），即使仓库什么都没记录也适用。两条规则约束它：

- **仓库优先。** 已记录的仓库标准总是获胜；在它认可基线会标记的东西时，抑制该坏味道。
- **永远是判断调用。** 每个坏味道都是一个带标签的启发式（"可能的 Feature Envy"），绝不是硬性违规——并且，与这里的任何标准一样，跳过工具已经强制执行的任何东西。

每个坏味道读作*它是什么* → *如何修复*；把它与 diff 对照：

- **神秘命名** —— 函数、变量或类型的名字没有揭示它做什么或装什么。→ 重命名它；如果想不到诚实的名字，那设计就模糊了。
- **重复代码** —— 相同逻辑形态出现在变更中的多个 hunk 或多个文件中。→ 提取共享形态，从两处调用它。
- **依恋情结（Feature Envy）** —— 一个方法访问另一个对象的数据比访问自己的更多。→ 把方法移到它羡慕的数据上。
- **数据泥团** —— 同样的几个字段或参数一直结伴旅行（一个想诞生的类型）。→ 把它们捆绑成一个类型，传那个。
- **基本类型偏执** —— 一个基本类型或字符串替代了一个值得拥有自己类型的领域概念。→ 给这个概念它自己的小类型。
- **重复的开关** —— 相同的 `switch`/`if` 级联在相同类型上在变更中反复出现。→ 用多态替换，或两个站点共享的一个映射。
- **霰弹式修改** —— 一个逻辑变更迫使 diff 中许多文件进行零散编辑。→ 把一起变化的东西集中到一个模块。
- **发散式变化** —— 一个文件或模块因几个无关原因被编辑。→ 拆分，让每个模块只为一个原因变化。
- **过度通用** —— 为规格没有的需求添加的抽象、参数或钩子。→ 删除它；内联回去，直到出现真实需求。
- **消息链** —— 长的 `a.b().c().d()` 导航，调用者本不该依赖它。→ 把这条行走藏在第一个对象上的一个方法后面。
- **中间人** —— 一个类或函数大多只是转发。→ 砍掉它，直接调用真正的目标。
- **被拒绝的遗赠** —— 一个子类或实现者忽略或覆盖了它继承的大部分内容。→ 放弃继承，使用组合。

### 4. 并行生成两个子 agent

**标准子 agent 提示** —— 包含：

- 完整的 diff 命令和 commit 列表。
- 你在第 3 步找到的标准来源文件列表，**加上第 3 步的坏味道基线全文**——子 agent 没有其他途径访问它。
- 简报："报告——在相关时按文件/hunk——(a) diff 违反已记录标准的每个地方：引用标准（文件 + 规则）；以及 (b) 你发现的任何基线坏味道：命名并引用 hunk。区分硬性违规与判断调用——已记录标准的违反可能是硬性的，但基线坏味道永远是判断调用，而且已记录的仓库标准优先于基线。跳过工具强制执行的任何东西。400 词以内。"

**规格子 agent 提示** —— 包含：

- diff 命令和 commit 列表。
- 规格的路径或获取的内容。
- 简报："报告：(a) 规格要求的、缺失或部分实现的需求；(b) diff 中未被要求的、不应出现的行为（范围蔓延）；(c) 看起来已实现但实现看起来有误的需求。为每个发现引用规格原文。400 词以内。"

如果规格缺失，跳过规格子 agent 并在最终报告中注明。

### 5. 汇总

在 `## 标准` 和 `## 规格` 标题下呈现两份报告，逐字或轻清理。**不要**合并或重新排序发现——两条轴线故意分开（见_为什么是两条轴线_）。

以一个一句话总结结束：每条轴线的发现总数，以及*每条轴线内部*最严重的问题（如果有）。不要跨轴线选一个唯一的胜者——那正是这种分离要防止的重新排序。

## 为什么是两条轴线

一个变更可以通过一条轴线而失败另一条：

- 遵循了每条标准但实现了错误的东西 → **标准通过，规格失败。**
- 完全按 issue 要求做了但破坏了项目约定 → **规格通过，标准失败。**

分别报告可以防止一条轴线掩盖另一条。
