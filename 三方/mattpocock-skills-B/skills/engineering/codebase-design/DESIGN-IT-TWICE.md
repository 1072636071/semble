# 设计两次

当用户想为选中的深化候选者探索替代接口时，使用这个并行子 agent 模式。基于"Design It Twice"（Ousterhout）——你的第一个想法不太可能是最好的。

使用 [SKILL.md](SKILL.md) 中的词汇——**模块**、**接口**、**接缝**、**适配器**、**杠杆**。

## 流程

### 1. 界定问题空间

在生成子 agent 之前，为选中的候选者写一份面向用户的、关于问题空间的解释：

- 任何新接口都需要满足的约束
- 它将依赖的依赖项，以及它们属于哪个类别（参见 [DEEPENING.md](DEEPENING.md)）
- 一个粗略的、说明性的代码草图来锚定约束——不是一个提案，只是让约束具体化的一种方式

把这个展示给用户，然后立即进入第 2 步。子 agent 并行工作时，用户阅读并思考。

### 2. 生成子 agent

并行生成 3 个以上子 agent。每个必须为深化模块产出一个**截然不同**的接口。

用一份独立的技术简报提示每个子 agent（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝后面有什么）。简报独立于第 1 步中面向用户的问题空间解释。给每个 agent 一个不同的设计约束：

- Agent 1："最小化接口——目标是最多 1–3 个入口点。最大化每个入口点的杠杆。"
- Agent 2："最大化灵活性——支持许多用例和扩展。"
- Agent 3："为最常见的调用者优化——让默认情况变得琐碎。"
- Agent 4（如果适用）："围绕端口和适配器设计跨接缝依赖。"

在简报中包含 [SKILL.md](SKILL.md) 词汇和 CONTEXT.md 词汇，这样每个子 agent 用与架构语言和项目领域语言一致的命名。

每个子 agent 输出：

1. 接口（类型、方法、参数——加上不变量、顺序、错误模式）
2. 显示调用者如何使用它的用法示例
3. 实现隐藏在接缝后面什么
4. 依赖策略和适配器（参见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——杠杆在哪里高，在哪里薄

### 3. 呈现并比较

按顺序呈现设计，让用户能吸收每一个，然后用散文比较它们。按**深度**（接口处的杠杆）、**局部性**（变更集中在哪里）和**接缝位置**对比。

比较之后，给出你自己的建议：你认为哪个设计最强以及为什么。如果不同设计的元素组合起来会很好，提出一个混合方案。要有主见——用户想要一个强有力的解读，而不是一份菜单。
