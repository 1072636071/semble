# 改善代码库架构

浮现架构摩擦并提出**深化机会**——把浅模块变成深模块的重构。目标是可测试性和 AI 可导航性。

这个命令_由_项目的领域模型提供信息，并建立在一个共享的设计词汇上：

- 运行 `/codebase-design` 技能获取架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除测试、"接口就是测试表面"、"一个适配器 = 假设的接缝，两个 = 真实的"）。在每条建议中精确使用这些术语——不要漂移到"组件"、"服务"、"API"或"边界"。
- `CONTEXT.md` 中的领域语言为好接缝命名；`docs/adr/` 中的 ADR 记录了本命令不应重新辩论的决策。

## 流程

### 1. 探索

**在扫描之前先界定范围——YAGNI。** 深化一个模块的回报是让未来对它更易修改，所以把额外权重放在代码库最近变动的部分。在*看之前*决定*看哪里*：

- 如果用户指定了一个方向——一个模块、一个子系统、一个痛点——采用它，并跳过下面的推断。
- 否则，往回走一大段 commit 历史（`git log --oneline`）找出代码库的热点——反复出现的文件和区域——让这些路径首先吸引你的注意力。如果变更零散、没有清晰的热点，就扩大范围。

先阅读项目的领域词汇表（`CONTEXT.md`）以及你正在触碰区域中的任何 ADR。

然后生成一个子 agent 走查代码库。不要遵循僵硬的启发式——有机地探索，并记录你体验到的摩擦：

- 在哪里理解一个概念需要在小模块之间跳来跳去？
- 哪里模块是**浅**的——接口几乎和实现一样复杂？
- 哪里纯粹函数仅仅为了可测试性被提取，而真正的 bug 藏在它们如何被调用中（没有**局部性**）？
- 哪里紧密耦合的模块在它们的接缝上泄漏？
- 代码库的哪些部分未测试，或难以通过它们当前的接口测试？

对你怀疑浅的**任何东西**应用**删除测试**：删除它会把复杂性集中起来，还是只是移动它？"会，会集中"就是你要的信号。

### 2. 将候选者呈现为 HTML 报告

写一个自包含的 HTML 文件到 OS 临时目录，这样仓库里不会落下任何东西。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 上为 `%TEMP%`），并写入 `<tmpdir>/architecture-review-<timestamp>.html`，这样每次运行都会得到一个新文件。为用户打开它——Linux 上 `xdg-open <path>`，macOS 上 `open <path>`，Windows 上 `start <path>`——并告诉他们绝对路径。

报告使用 **Tailwind via CDN** 进行布局和样式，**Mermaid via CDN** 在图形/流程/序列能可靠传达结构时画图。将 Mermaid 与手工制作的 CSS/SVG 视觉效果混合——当关系是图形形状时（调用图、依赖、序列）使用 Mermaid，当你想要更编辑性的东西时（质量图、横截面、折叠动画）使用手工构建的 div/SVG。每个候选者都有一个**前/后可视化**。要视觉化。

对每个候选者，渲染一张卡片，包含：

- **文件** —— 涉及哪些文件/模块
- **问题** —— 当前架构为何引起摩擦
- **解决方案** —— 会用通俗英语描述会改变什么
- **收益** —— 用局部性和杠杆来解释，以及测试会如何改进
- **前/后图** —— 并排、手工绘制，说明浅和深化
- **建议强度** —— 三选一：`强`、`值得探索`、`推测性`，渲染为徽章

用 **Top recommendation（首选建议）** 部分结束报告：你会先处理哪个候选者以及为什么。

**领域使用 CONTEXT.md 词汇，架构使用 `/codebase-design` 词汇。** 如果 `CONTEXT.md` 定义了"Order"，就说"Order 接收模块"——而不是"FooBarHandler"，也不是"Order 服务"。

**ADR 冲突**：如果一个候选者与现有 ADR 矛盾，只有当摩擦真实到值得重新审视该 ADR 时才浮现它。在卡片中清晰标记（例如一个警告提示框：_"与 ADR-0007 矛盾——但值得重新开启，因为……"_）。不要列出每个 ADR 禁止的理论性重构。

完整的 HTML 脚手架、图表模式和陈设指导参见 [HTML-REPORT.md](HTML-REPORT.md)。

现在还**不要**提出接口。文件写好后，问用户："你想探索这些中的哪一个？"

### 3. 访谈循环

一旦用户选中一个候选者，运行 `/grilling` 技能与他们走决策树——约束、依赖、深化模块的形态、接缝后面有什么、哪些测试能存活。

副作用在决策结晶时内联发生——运行 `/domain-modeling` 技能，边走边保持领域模型最新：

- **把深化模块命名为 `CONTEXT.md` 中没有的概念？** 把这个术语添加到 `CONTEXT.md`。如果文件不存在就惰性创建。
- **在对话中磨锋利一个模糊术语？** 就地更新 `CONTEXT.md`。
- **用户以承重理由拒绝候选者？** 提供一份 ADR，框架为：_"想让我把它记录为 ADR 吗？这样未来的架构审查就不会重新建议它。"_ 只有当该理由真的会被未来的探索者需要、以避免重新建议同一个东西时才提供——跳过短暂的理由（"现在不值得"）和显而易见的理由。
- **想探索深化模块的替代接口？** 运行 `/codebase-design` 技能并使用它的 design-it-twice 并行子 agent 模式。
