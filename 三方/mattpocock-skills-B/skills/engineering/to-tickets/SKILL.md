# 转工单

将计划、规格文档或对话拆解为一组**工单**——曳光弹垂直切片，每张声明**阻塞**它的工单。

问题跟踪器和分流标签词汇表应已提供给你——若未提供，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

从对话上下文中已有的内容出发。如果用户传入一个引用（规格路径、issue 编号或 URL）作为参数，获取它并阅读其完整正文和评论。

### 2. 探索代码库（可选）

如果尚未探索过代码库，探索它以了解代码的当前状态。工单标题和描述应使用项目的领域词汇表词汇，并尊重你正在触碰区域的 ADR。

寻找机会预重构代码，使实现更容易。"让变更变容易，然后做容易的变更。"

### 3. 起草垂直切片

把工作拆成**曳光弹**工单。

<vertical-slice-rules>

- 每个切片切一条穿过每一层（schema、API、UI、测试）的狭窄但完整的路径——垂直的，而不是一层的水平切片
- 一个完成的切片本身是可演示或可验证的
- 每个切片的大小要适合放进单个全新上下文窗口
- 任何预重构都应先做

</vertical-slice-rules>

给每张工单它的**阻塞边**——必须先完成、它才能开始的工单。没有阻塞者的工单可以立即开始。

**宽重构是垂直切片的例外。** 一个**宽重构**是单一机械变更——重命名一列、重打一个共享符号——其**爆炸半径**扩散到整个代码库，所以单次编辑一次破坏数千个调用点，没有任何垂直切片能落地变绿。不要强行把它塞进曳光弹；把它按**扩展–收缩**排序。先扩展：在新形式旁边添加旧形式，这样什么都不破坏。然后按爆炸半径大小分批迁移调用点（按包、按目录），每批是它自己的工单，被扩展工单阻塞，逐批保持 CI 变绿，因为旧形式仍然存在。最后收缩：一旦没有调用者残留，删除旧形式，在一个被每个迁移批阻塞的工单中完成。当即使分批也无法单独保持绿色时，保持顺序但让它们共享一个集成分支，所有工单都阻塞一个最终的集成-验证工单——绿色只在那里承诺。

### 4. 询问用户

把提议的拆解呈现为编号列表。对每张工单，展示：

- **标题**：简短描述性名称
- **被阻塞于**：哪些其他工单（如果有）必须先完成
- **它交付什么**：这张工单使之工作的端到端行为

问用户：

- 粒度合适吗？（太粗 / 太细）
- 阻塞边正确吗——每张工单只依赖真正门控它的工单吗？
- 任何工单应该合并或进一步拆分吗？

迭代直到用户批准这个拆解。

### 5. 把工单发布到配置的跟踪器

发布已批准的工单。**如何**发布取决于 `/setup-matt-pocock-skills` 配置的跟踪器——工单本身都一样，只有阻塞边的形态不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下每张工单写一个文件，按依赖顺序从 `01` 编号（阻塞者在前）。每个文件的"Blocked by"列出它依赖的编号/标题。使用下面的按工单文件模板——每个文件一张工单，绝不用一个合并的大文件。
- **真实问题跟踪器（GitHub、Linear 等）** → 按依赖顺序（阻塞者在前）每张工单发布一个 issue，这样每张工单的阻塞边可以引用真实标识符。在平台有原生阻塞/子 issue 关系的地方使用它；否则把每张工单的"Blocked by"设置为阻塞它的 issues。应用 `ready-for-agent` 分流标签，除非另有指示——这些工单构造上就是 agent 可拿取的。

推进**前沿**：任何阻塞者都已完成、可立即拿取的工单。对于纯线性链，那就是从上到下。

不要关闭或修改任何父 issue。
