## 它做什么

`to-questionnaire` 把一个你无法独自落定的决策变成一份**问卷**——一份 Markdown 文档，你把它交给唯一持有你所缺之物的人，让他们异步填写，或你们俩在一个会议上一起过。

它拷问你的是**发送**，绝不是主题。在这里就主题访谈你是没有意义的：不知道主题正是你写信给别人（写给他人的原因）的原因。所以它问两件你总能回答的事——这是发给谁的，以及你需要从他们那里拿回什么——并把文档中的每个问题瞄准两者之间的**差距**。

## 何时使用

你通过输入 `/to-questionnaire` 调用它——[agent](https://www.aihero.dev/ai-coding-dictionary/agent) 不会自行触发它。

当一个决策被堵在一个住在另一个人脑子里的知识上时取用它：一个客户、一个领域专家、一个拥有业务规则的高管、一个你不在其团队里的同事。你想要的技能取决于答案实际在哪里：

| 答案在…… | 取用 |
| --- | --- |
| 你自己的脑子里，未磨锋利 | [grill-me](https://aihero.dev/skills-grill-me) |
| 代码库里 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 别人的脑子里 | `to-questionnaire` |
| 还没有任何人的脑子里——问题需要某种东西去反应 | [prototype](https://aihero.dev/skills-prototype) |

常见情况是一场[访谈](https://www.aihero.dev/ai-coding-dictionary/grilling)会话停滞：浮现出来的东西有些不是你的回答。在同一个对话中运行 `/to-questionnaire` 把那些问题带离线，然后把答案带回来继续。

## 发送，不是主题

访谈是两次交流，然后它停。

- **它是发给谁的？** 他们的角色、他们的专业领域、他们与你的关系。这固定了语气和文档必须承载多少上下文——一个外部客户需要引导，一个队友不需要。
- **你需要拿回什么？** 你无法独自解决的具体决策或事实。这成为完成文档所度量的清单：你点名的每个条目都得到一个瞄准它的问题。

那之后的一切都是起草。文件落在当前目录的 `to-questionnaire-<slug>.md`。没有设置、没有工作区、没有要配置的。

## 文档

它被框架化为一份**发现问卷**——你缺少上下文，接收者持有它——而那个框架驱动它的形态：

- 一个目的行，点名骑在它上面的决策，和一个给从未进过你脑子的接收者的简短上下文部分。
- 问题按**最重要优先**排序，并在主题标题下分组，因为异步意味着你可能只有一次机会。
- 每个问题一个想法，绝不复合，下面留一个作答空白，*为什么这很重要*一行只在问题可能被误读的地方。
- 明确允许回答"我不知道"——一个被标记的不确定性有用；一个读起来像事实的自信猜测没有。
- 一个收尾的兜底问题：我们没有问的、我们应该知道的任何东西？

两件它刻意不是的东西。它不是**分支的**——问题是一个扁平的、分组列表，不是一个跳过 D 节如果你回答了 A 的树。而且它不是**多接收者**的——一次运行为一个人产出一份文档。

## 常见问题

**它读我的访谈会话并从它提取问题吗？**

不作为它自己的一步。技能没有摄取阶段：它问发送，然后起草。让它在访谈会话之后有效的是你在**同一个对话**中运行它，所以[会话](https://www.aihero.dev/ai-coding-dictionary/session)已经在[上下文](https://www.aihero.dev/ai-coding-dictionary/context)里，起草可以靠它。在一个全新会话中开始它，它对你访谈一无所知——你回答"你需要拿回什么？"时会自己重新供应主题。

**缺失的答案不全住在同一个人那里。它能按接收者拆分吗？**

不能。第一步要*那个*接收者，单数，而整个文档的语气和上下文是对着他们定的。如果三个人持有答案的三部分，运行它三次，每人一次。在一个单一文档内部按学科或角色路由问题是一个人们已经提出过的请求；它不是已发布的。

**问题是依赖的吗——它会根据早先的答案跳过部分吗？**

不会。依赖问题的设计被探索过，没有发布。输出是一份静态文档：主题分组、最重要优先、每个问题都是活的。反对它的论证是公平的一个——一个在真实答案之前规划超过两三个问题的[模型](https://www.aihero.dev/ai-coding-dictionary/model)规划得很差，而一份分支文档必须对每个答案提前规划它们全部。

**如果接收者也不知道呢？**

文档告诉他们说出来。"我不知道"和部分答案被明确要求，而一个被标记的不确定性比一个猜测更值钱，因为一个含糊的答案和一个自信地错的答案一旦回到你的上下文里看起来一模一样。

**它把它送到任何地方吗——Slack、issue 跟踪器、邮件？**

不。它在当前目录写一个 Markdown 文件并告诉你路径。交付是你的：把它粘贴进一张[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)、丢进一个 Slack 线程、附到一封邮件，或在一个共享屏幕上打开并现场过。人们已经手工接好这四种。

**这不就是批量模式的 `/grill-me` 吗？**

不，而这个区别值得握住。`grill-me` 已经按**轮次**问——一次整个前沿，然后从你的答案重新计算——所以"一次把问题都给我"的需求在那里被满足。`to-questionnaire` 关于一个不同的轴：不是问题如何被交付，而是答案在谁的脑子里。更快地自己回答它们是 `grill-me`；从别人那里拿出去是这一个。

**我就不能不需要技能问 agent 要这个吗？**

能，而且在它存在之前很多人就这样做了——`OPEN_QUESTIONS.md` 文件、发给客户的电子表格、每个未回答的问题一张"needs more info"工单。技能给你买两样东西：访谈从不漂移到主题上，而文档以一个非技术接收者真的能填的形态出来。如果你已经有一个有效的自家格式，诚实的答案是你不需要这个。

## 正常工作的标志

- 它问接收者和你需要拿回什么，然后停止问。一个关于主题本身的问题就是技能脱轨了。
- 你命名为"我需要拿回什么"的每个条目都可以追溯到文件中的一个问题。
- 问题读起来是瞄准*接收者*知道的东西，而不是你自己的开放问题被逐字抄下来。
- 你能把文件交给一个不在对话中的人，他们会知道为什么收到它、什么时候回复。
- 回来的答案是可用的输入，用于新一轮访谈，而不是一套新问题。

## 在流程中的位置

`to-questionnaire` 是一个随时可取的独立项。它坐在你自己知识的边界上，在那里下一步是另一个人，而不是另一个技能——最常在流程中途，当规划被某样不是你该决定的东西卡住时。

它的邻居是 [grill-me](https://aihero.dev/skills-grill-me)，而两者按答案住在哪里拆分：访谈挖掘你，问卷挖掘别人。回来的东西是原材料——把它喂进另一轮访谈，或如果工作要走向构建，喂进 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)。当你不确定哪个技能适合此刻时，[ask-matt](https://aihero.dev/skills-ask-matt) 为你路由。
