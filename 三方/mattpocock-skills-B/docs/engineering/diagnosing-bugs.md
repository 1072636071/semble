## 它做什么

`diagnosing-bugs` 对难缠 bug 或性能回归运行六阶段诊断：构建复现、最小化它、排序假设、插桩、带回归测试修复、清理。

它不允许 agent 在**紧凑**反馈循环存在之前形成理论——一个指名的命令、已经运行过一次、能在*这个* bug 上变红、在修复后变绿。一个编码 agent 拿到 bug 报告的默认行为是读代码和猜；这个技能阻止那一点。如果没有可变红的命令，就没有阶段 2。那一个闸门就是这个技能存在的意义。它之后的一切——二分、假设测试、插桩——一旦信号存在就是机械性的。

## 何时使用

输入 `/diagnosing-bugs`，或当一个任务合适时 agent 自行触发它——它是模型调用的，在"diagnose" / "debug this"或一份有东西坏了、在抛错、在失败或在变慢的报告上触发。

在难缠的情况下取用它：一个抗拒第一眼的 bug、一个间歇性 flake、一个在两个已知良好状态之间悄悄爬进来的回归。它按设计很重，而且是你想要一个消息内回答的问题的错误工具。

| 你的情况 | 去哪里 |
| --- | --- |
| 一个你能描述为症状的具体缺陷 | 这个技能 |
| 一个慢端点或一个已知前后对比的时序回归 | 这个技能——它有性能分支（测量基线，然后二分） |
| "这个代码库的瓶颈在哪里？"——没有具体症状 | 不是这个技能。它诊断一个已知的失败，它不审计 |
| 一份别人的原始 bug 报告，尚未确认或成文 | 先 [triage](https://aihero.dev/skills-triage) |
| 一次性代码回答一个设计问题，而不是追一个缺陷 | [prototype](https://aihero.dev/skills-prototype) |
| 测试先行地构建一个计划好的行为 | [tdd](https://aihero.dev/skills-tdd) |
| 没有好的接缝来锁住这个 bug | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)——这个技能自己在那里交接 |

## 紧凑循环就是这个技能

阶段 1 得到不成比例的精力，因为它是唯一困难的阶段。技能给了一个构建循环的方式的梯子，大致按偏好顺序：

1. 在到达 bug 的任何接缝处的失败测试。
2. 针对运行中的开发服务器的 curl 或 HTTP 脚本。
3. 带夹具输入的 CLI 调用，与已知良好的快照做 diff。
4. 对 DOM、console 或 network 断言的无头浏览器脚本。
5. 重放的捕获——一个保存的请求、载荷或事件日志，在隔离中穿过代码路径运行。
6. 一次性 harness：系统的最小子集，一个函数调用。
7. 属性或 fuzz 循环，用于"有时输出错误"。
8. 你可以交给 `git bisect run` 的二分 harness。
9. 差异循环——相同输入，旧版对新版。
10. 一个[人类在环里](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop)的 bash 脚本，最后手段。技能为此发布 `scripts/hitl-loop.template.sh`：agent 运行脚本，你在终端里跟随提示，你的回答作为可解析输出回来。

*一个*循环不是目标。**紧凑**才是：快（秒级）、确定性（每次运行相同裁决）、锋利（断言你的精确症状，而不是"没崩溃"）、以及 agent 可无人值守运行。一个 30 秒的 flaky 循环几乎不比没有好。对一个只是偶尔出现的 bug，目标不是一个干净的复现，而是**更高的复现率**——循环触发、并行化、加压力、注入 sleep，直到 flake 率高到足以针对它调试。

当它真的无法构建一个时，它被指示停下并如实说明、列出它尝试过的、并请求[环境](https://www.aihero.dev/ai-coding-dictionary/environment)访问、一个捕获的工件、或添加临时插桩的许可。它无论如何都不应该继续进行假设。

## 阶段之间的闸门

阶段是闸门，不是清单。每个都拒绝打开，直到有特定的东西为真。

| 闸门 | 什么必须为真 |
| --- | --- |
| 进入阶段 2 | 一个指名的命令、已运行并带输出粘贴、能在这个 bug 上变红 |
| 进入阶段 3 | 复现被复现*并且*最小化——每个剩余元素都是承重的 |
| 进入阶段 4 | 存在 3–5 个排序的、可证伪的假设，每个陈述它的预测，在测试任何一个之前展示给你 |
| 进入阶段 5 | 探针映射到一个特定预测，一次一个变量，每个调试日志打上 `[DEBUG-a4f2]` 风格的标签，这样清理就是一次 grep |
| 完成 | 原始复现不再复现，插桩已移除，结果正确的假设写进 commit 消息 |

阶段 5 有一个值得知道的逃生舱。回归测试在修复之前写，但只有存在**正确接缝**时才写——一个测试锻炼调用点处真实 bug 模式的地方。在唯一可用的接缝太浅之处，技能被指示如实说，而不是写一个给出虚假信心的测试。那个缺失本身就是发现，而且正是它把复盘路由到 `improve-codebase-architecture`。

## 常见问题

**它在快速问题上触发，而我只要一个直接答案。**
这是关于这个技能被报告最多的问题，而且是真的。在 GPT-5.6-Sol 上尤其，用户报告它对一个问题的简单描述就触发："模型改为触发相当正式的 diagnosing-bugs 技能。然后它继续构建复现场景——通常构建一个价值有限的 mock 场景——然后才给我回应或建议。这造成相当大的回复延迟。"四个不同的人在 [issue #578](https://github.com/mattpocock/skills/issues/578) 上报告了相同的形态。已被接受的修复是从一个更轻的方法开始，只在问题值得时升级到更重的那个，但那个变更还没落地。技能是针对 Claude Code 的调用行为校准的；一个激活阈值更低的[模型](https://www.aihero.dev/ai-coding-dictionary/model)会过度触发它。在它被毕业之前，实际的修复是说出你想要什么（"只回答这个，别诊断"）或在你的 [harness](https://www.aihero.dev/ai-coding-dictionary/harness) 里为它禁用模型调用。

**我能把它指向一个代码库，问性能问题在哪里吗？**
不能。它诊断一个你已经能指名的失败。它的性能分支是为带症状的回归——建立基线测量、然后二分、先测后修——不是为主动清扫。主动版本的技能被[提议并关闭](https://github.com/mattpocock/skills/issues/431)；目前没有用于它的技能。

**它在写修复之前停下来问我吗？**
不会。只有阶段 3 有人类检查点——排序的假设列表在测试任何一个之前展示给你，如果你离开，它按自己的排序进行。插桩和修复之间没有闸门，所以 agent 可以在你同意它的根因之前开始写代码。[Issue #124](https://github.com/mattpocock/skills/issues/124) 要求那个闸门，仍然打开。如果你想要它，在调用技能时说一声。

**我已经在这个 bug 报告上运行过 `/triage` 了。这又是同样的工作吗？**
部分，而且两个技能都不承认。正如一位读者所说："Triage 的第 3 步本质上是 diagnosing-bugs 阶段 1–2 的一个浅的、有界的实例，但两个文件都没有提到对方。"Triage 做一个有界的"这真的是 bug 吗，表面是什么"的通过；这个技能做彻底的版本。先运行 triage 不是浪费——它的验证常常给你阶段 1 的大部分原材料——但预期在这里正确地重做它，而且别指望有交叉引用告诉你。

**它粘贴的复现输出会泄漏机密吗？**
可能会。技能要求 agent 粘贴调用和它的输出，并要求 HAR 文件、日志转储和核心转储等工件。这些没有一个按指令被脱敏。[Issue #674](https://github.com/mattpocock/skills/issues/674) 恰好提出这一点——凭据、token、cookie 和个人数据搭车进入聊天、issue 或 PR——并提议一个脱敏护栏。它打开未实现。暂时把脱敏当作你的工作，尤其是在输出去任何公开的地方之前。

**我的安全扫描器把这个技能标记为高风险。**
Snyk 标记它，而这个标记是误报。它是整套中唯一一个发布可执行 shell 脚本（`hitl-loop.template.sh`）连同运行它的指令和 curl 一个开发服务器的技能。发布的 `.sh` 加上运行指令加上出站 HTTP 足以触发一个静态扫描器。脚本本身只有大约 30 行 `read -r -p` 提示，暂停等待人类输入。扫描器在评估能力表面，而不是一个已被证明的漏洞。

**`/diagnose` 怎么了？**
在 v1.0.0 重命名为 `/diagnosing-bugs`。旧名字不再存在。你任何链接 `/diagnose` 的东西——一个包装技能、一个保存的提示——都需要更新。

## 正常工作的标志

- 它在给出任何理论之前向你展示一个命令和它的红色输出。如果理论先到，技能就没有在运行。
- 它复现的失败是你报告的失败，而不是它在路上发现的附近失败。
- 它在开始猜之前缩小复现，并能告诉你为什么每个剩余部分是承重的。
- 在测试任何假设之前，你被展示 3–5 个排序的假设列表，每个带一个你可以证伪的预测。
- 它添加的每个调试日志都带一个像 `[DEBUG-a4f2]` 这样的标签，而且当它宣布完成时，对该标签的一次 grep 回来是空的。
- commit 或 PR 消息点名哪个假设是对的。
- 当它无法用测试锁住 bug 时，它直白地说出来，而不是写一个浅的测试。

## 在流程中的位置

`diagnosing-bugs` 是一个随时可取的独立项。当有东西坏了时你落入它，当修复和它的回归测试就位时你退出；它不持有状态，不需要先前设置。[ask-matt](https://aihero.dev/skills-ask-matt) 把"有东西坏了"路由到这里。

两个邻居很重要。[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 在真正的发现是代码没有接缝锁住 bug 时接手[交接](https://www.aihero.dev/ai-coding-dictionary/handoff)——建议在修复就位*之后*给出，那时有更多信息。[triage](https://aihero.dev/skills-triage) 对作为其他人原始报告到达的 bug 坐在它的上游，并做同样的前两个阶段的更浅版本。
