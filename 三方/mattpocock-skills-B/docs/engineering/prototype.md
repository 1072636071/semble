## 它做什么

`prototype` 写**回答一个问题的抛弃型代码**——这个状态模型感觉对吗，或者这个屏幕应该长什么样。问题先来，决定之后一切事物的形态；一个回答了错误问题的原型是纯粹的浪费，无论它看起来多好。

一次性是对代码如何*编写*的约束，不是摧毁它的承诺。没有测试、没有超出让它运行的错误处理、没有抽象、没有持久化——因为这些都不能帮助你学到你试图学到的那一件事。存活下来的是答案，折叠进真实代码，以及原型本身，停放在 main 之外的一个分支上，作为答案来自的证据。

## 何时使用

输入 `/prototype`，或当一个任务合适时[agent](https://www.aihero.dev/ai-coding-dictionary/agent) 自动触发它。

在你碰到一个无法靠交谈解决的问题的那一刻取用它——一个你在脑子里装不下其边缘情况的状态机、一个你看到三个版本并排之前无法想象的屏幕。[访谈](https://www.aihero.dev/ai-coding-dictionary/grilling)会话恰好在这些问题上膨胀：agent 重述、你猜、范围增长去填满不确定性。停止访谈，构建抛弃版，看看它，然后用一行回答。如果相反，某样已构建的东西行为异常、你想知道为什么，用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)——原型设计探索*要构建什么*，而不是为什么已构建的东西坏了。

你也会不选择就来到这里。[wayfinder](https://aihero.dev/skills-wayfinder) 在地图上归档 `prototype` 决策[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)，而处理一张就是这个技能。

## 两个分支

问题选分支，而分支产出非常不同的工件：

- **"这个逻辑 / 状态模型感觉对吗？"** —— 一个**单一可共享的 HTML 文件**。一个自包含的页面，没有构建、没有服务器，有人双击打开。它携带一个带标签的状态面板，每次点击后重新渲染；自由操作按钮，用于以任意顺序戳模型；以及带标签页的**引导式走查**——每个标签页一个场景，每个场景下面是要按的有序按钮。一切都用领域语言标注，所以你可以把它交给设计师、PM 或领域专家，让他们自己感受模型。页面背后的逻辑是一个小的纯模块——一个 reducer、一个机器、一组函数——保持干净于 DOM 之外，这样验证过的版本直接抬进真实代码。
- **"这应该长什么样？"** —— 单一路由上的几个**截然不同**的 UI 变体，从浮动底栏和一个 `?variant=` URL 参数切换。变体必须在结构上不同意，而不是颜色；三个调整过的卡片网格是壁纸，不是原型。它们尽可能在真实页面内部、对着真实数据和真实密度渲染，因为在一个真空里被评判的变体总是看起来不错。

两者都保持状态在内存中、开始不需要思考、每一步之后向你展示完整状态。当你发现自己开始硬化一个——添加测试、接上真实数据库、为一个你以后可能想要的案例泛化——你就已经停止了原型设计。

## 原型是首要来源

一个完成的原型留下两样东西，它们去不同的地方。

**答案**——裁决加上它解决的提问——被持久捕获：一个 commit 消息、一份 ADR、实现 issue。那就是 main 分支保留的，折叠进真实代码。

**原型**是答案来自的可运行证据，它不被删除。它也不属于 main——那里没有要维护的东西，它很快腐烂——所以它被提交到 main 之外的一次性 `prototype/<name>` 分支，永不合并，并在实现 issue 上留一个指向该分支的[上下文指针](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。Main 保持干净；探索保持可发现，并且下一个拿起工作的任何人可以重新运行它。

## 常见问题

**等等——原型不是应该被删除吗？**
不再是了。过去是：构建它、保留答案、把代码扔掉。对那个最锋利的反对从来不是关于速度——而是*下一个[会话](https://www.aihero.dev/ai-coding-dictionary/session)谁来接手工作，他们有什么可依据？* 一个原型的散文摘要会失去让它有说服力的东西。所以原型现在被当作[首要来源](https://www.aihero.dev/ai-coding-dictionary/primary-source)：它落在 main 之外的一个 `prototype/<name>` 分支上，实现 issue 指向它。改变的是代码住哪里，而不是纪律——它仍然从不合并进 main。

**它以前构建一个终端应用。那个去哪了？**
逻辑分支现在改为发射一个单一可共享的 HTML 文件。一个终端应用只能被克隆了仓库并安装了运行时的人驱动，那恰好排除了原型需要其意见的人——知道状态模型应该意味着什么的设计师、PM、领域专家。一个双击打开、经得起被邮件转发的自包含文件，任何人都能驱动。底下的纯逻辑模块不变，而且仍然是抬进真实代码的部分。

**一个 agent 在我本该实现的时候告诉我 `/prototype`。**
已知，而且它是一个命名问题。`prototype` 是一个通用的、吸引人的词，对一个流程无感知的 agent 读作一旦工单存在就是"明显的下一步"，所以它会被按名字推荐，即使设计在对话中已经完全落定。如果你已经知道要构建什么，下一步是 `/implement`，按工单。只有当某个具体的设计问题真的未解决、而交谈无法解决它时，才取用一个原型。

**我应该在构建任何生产功能之前把整个应用原型化——比如说，给潜在客户演示它？**
那是穿着这个技能名字的另一种工件。这里的原型范围限定在一个问题上，而"整个应用是什么？"不是一个。"整个应用"的原型没有自然的停止点，所以它靠动量变成生产应用：清理通过永不发生，在原型规则下写的代码——没有测试、没有错误处理——最终出现在用户面前。如果你需要一个销售演示，刻意地把它作为演示构建，并明确其中没有东西是生产。如果你需要解决一个设计问题，把它削减到那个问题。

**我怎么在它自己的会话里运行它？**
一个原型住在它自己的目录里，产生大量你不想留在提出问题的线程中的[上下文](https://www.aihero.dev/ai-coding-dictionary/context)，所以把它跑到别处，只把答案带回来。[handoff](https://aihero.dev/skills-handoff) 是两个方向的桥。

**这不是烧 token 最快的可能方式吗？**
可能是，如果你原型化了本来可以用交谈回答的问题，或者让一个原型蔓延过整个功能。重要的比较不是 token 对零；是[token](https://www.aihero.dev/ai-coding-dictionary/token)对构建错误的状态模型、然后在它有了生产调用者之后才发现。保持问题窄、运行短，花费就保持成比例。

## 正常工作的标志

- 你能用一句话说出原型存在是为了回答什么问题——而且它写在演示的顶部，不只是在你脑子里。
- 一个不读代码的人能驱动逻辑演示。他们打开文件、按走查标签页中的按钮、用自己的话描述他们看到的。
- 有人说"等等，那不应该可能"或"嗯，我以为 X"。那是*想法*里的 bug，正是全部关键。
- UI 变体在布局和信息层级上不同意，而不只是颜色和文案——而你得到的反馈是"B 的 header 配 C 的侧边栏"。
- 它在一口气中被回答。如果你一天后还在构建它，问题太大了；拆分它。
- 当它结束时，main 包含决策和原型零部分，实现 issue 指向仍然持有它的分支。

## 在流程中的位置

`prototype` 是一个**随时可取的独立项**——你落入它解决一个设计问题，然后退出——它也是另一个技能运行的机械。

它最大的消费者是 [wayfinder](https://aihero.dev/skills-wayfinder)。一张 wayfinder 地图由**决策工单**构成，而 `prototype` 是工单可以是的四种类型之一：当阻塞问题"这应该长什么样"或"它应该怎么表现"、多少讨论都解决不了时使用的那一种。Wayfinder 通过制造一个具体的可反应的东西来提高模糊讨论的保真度，而这个技能就是那个具体东西如何被构建。一张原型工单由答案解决，原型作为资产从地图链接。

其他邻居在它的上游和下游。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 回答可访谈的问题；不可访谈的来这里，一行答案回到访谈中。下游，一个验证过的状态模型或 UI 方向成为 [to-spec](https://aihero.dev/skills-to-spec) 的已落定输入，它可以内联原型产出的决策密集片段，而不是用散文描述它。对于其他一切，[ask-matt](https://aihero.dev/skills-ask-matt) 在整套之间为你路由。
