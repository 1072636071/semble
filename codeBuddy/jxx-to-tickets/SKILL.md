# 转化工单

将计划、规格文档或对话拆解为一组**工单**——追踪弹式（tracer-bullet）垂直切片（vertical slice），每个声明**阻塞它的**工单。

issue tracker 和 triage 标签词汇表应该已提供给你——如果没有，运行 `/jxx-setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

从对话上下文中已有的内容出发。如果用户传入引用（规格文档路径、issue 编号或 URL）作为参数，获取并阅读其完整内容和评论。

### 2. 探索代码库（可选）

若尚未探索代码库，先了解代码当前状态。工单标题和描述应使用项目的领域词汇表，并遵守相关区域的 ADR。

寻找预重构机会以简化实现。"先让变更变容易，再做容易的变更。"

### 3. 起草垂直切片

将工作拆解为**追踪弹**工单。

<vertical-slice-rules>

- 每个切片切出一条狭窄但完整的路径，贯穿每一层（schema、API、UI、测试）——垂直切片，不是单层的水平切片
- 完成的切片可独立演示或验证
- 每个切片的大小适合单个新上下文窗口
- 任何预重构应优先完成

</vertical-slice-rules>

为每个工单设定其**阻塞边**——必须在它之前完成的其他工单。没有阻塞的工单可以立即开始。

**广泛重构是垂直切片的例外。** **广泛重构**是一种机械性变更——重命名列、重新类型化共享符号——其**影响半径（blast radius）**遍及整个代码库，单次编辑同时破坏数千个调用点，没有任何垂直切片能保持绿色。不要强塞进追踪弹；按**扩展-收缩（expand-contract）**顺序排列。先扩展：在旧形式旁添加新形式，不破坏任何东西。然后按影响半径分批迁移调用点（按包、按目录），每批是独立工单，阻塞于扩展工单，由于旧形式仍然存在，每批之间 CI 保持绿色。最后收缩：一旦没有调用者剩余，删除旧形式，此工单阻塞于所有迁移批。当连批次都无法单独保持绿色时，保持顺序但让它们共享一个集成分支，它们都阻塞最终的集成验证工单——绿色只在那个工单上承诺。

### 4. 询问用户

以编号列表形式呈现提议的拆解。对每个工单，展示：

- **标题**：简短描述性名称
- **阻塞于**：哪些其他工单（如有）必须先完成
- **交付内容**：此工单使什么端到端行为可用

询问用户：

- 粒度是否合适？（太粗 / 太细）
- 阻塞边是否正确——每个工单是否只依赖于真正阻塞它的工单？
- 是否有工单应合并或进一步拆分？

迭代直到用户批准拆解。

### 5. 将工单发布到本地跟踪器

将已批准的工单发布到本地 issue 跟踪器——在仓库根目录的 `.scratch/<NN>-<工作简称-slug>/issues/` 下为每个工单创建独立文件 `<NN>-<slug>.md`（从 `01` 编号，按依赖顺序放置，阻塞者在前）。功能目录的 `<NN>` 为从 `01` 起的全局递增顺序号，按创建先后排列。每个文件顶部附近含 `Status: ready-for-agent` 行（triage 词汇见 `triage-labels.md`）；阻塞边以 `Blocked by: NN, NN` 文本行表示（列出它依赖的工单编号，无阻塞则写"无——可立即开始"）。评论与对话历史追加到文件底部 `## 评论` 标题下。使用下方本地工单文件模板。

<local-issue-file-template>

# <工单标题>

**Status:** ready-for-agent

**Blocked by:** 01, 02   （列出此工单依赖的工单编号；无阻塞则省略此行，或写"无——可立即开始"）

**构建内容：** 此工单使什么端到端行为可用，从用户视角——不是逐层的实现列表。

**验收标准：**

- [ ] 验收标准 1
- [ ] 验收标准 2

## 评论

（评论与对话历史追加于此，新内容置于最前。）

</local-issue-file-template>

> 本地工单存放于 `.scratch/<NN>-<工作简称-slug>/issues/`，每个工单一个独立文件。目录与文件如不存在则创建。功能目录的 `<NN>` 为从 `01` 起的全局递增顺序号；工单编号从 `01` 起，文件名为 `<NN>-<slug>.md`（例如 `01-add-schema.md`、`02-wire-api.md`）。上下文指针与所做决策可汇总到 `.scratch/<NN>-<工作简称-slug>/map.md`。

> 若改用远程 tracker（GitHub / Linear 等），以 tracker 原生 issue 形式发布，使用下方通用模板（标题 + 构建内容 + 验收标准 + 阻塞于），阻塞边用 tracker 原生依赖链接。

<issue-template>

## 构建内容

此工单使什么端到端行为可用，从用户视角——不是逐层实现。

## 验收标准

- [ ] 标准 1
- [ ] 标准 2

## 阻塞于

- 对每个阻塞工单的引用，或"无——可立即开始"。

</issue-template>

无论哪种形式，避免具体文件路径或代码片段——它们很快过时。例外：如果 prototype 产出了一个比文字更精确地编码决策的片段（状态机、reducer、schema、类型形状），在此内联并简要注明它来自 prototype。只保留决策密集部分——不是可运行的演示，只是关键信息。

按前沿逐个工单推进，使用 `/jxx-implement`，在工单之间清理上下文。

## 反模式

- **水平切片** — 按层拆（先 schema 后 UI），而非窄而完整的垂直路径。每个切片应独立可演示。
- **强塞广泛重构** — 影响半径遍及全库的机械变更不放进追踪弹。按扩展-收缩顺序分批。
- **不设阻塞边** — 工单不声明依赖，导致并行时破坏。每个工单明确其阻塞它的工单。
- **含具体文件路径 / 代码片段** — 工单描述用领域词汇，避免易过时的路径细节。

## 异常处理

| 场景 | 处理方式 |
|------|---------|
| issue tracker / triage 标签未配置 | 提示先运行 `/jxx-setup-matt-pocock-skills` |
| 用户传入引用（spec 路径 / issue 编号） | 先获取并阅读其完整内容和评论 |
| 广泛重构无法单批保持绿色 | 共享集成分支，阻塞最终集成验证工单，绿色只在那个工单上承诺 |
| prototype 产出决策片段 | 内联到相关工单并注明来源，只保留决策密集部分 |
