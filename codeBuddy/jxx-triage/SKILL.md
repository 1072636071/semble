# Triage

将项目 issue tracker 上的 issue 推过一个小型 triage 角色状态机。

triage 期间写入 issue 文件的每条评论**必须**以此免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — 如何编写持久的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` 知识库的工作方式

## 角色

两个**分类**角色：

- `bug` — 某些功能损坏
- `enhancement` — 新功能或改进

五个**状态**角色：

- `needs-triage` — 维护者需要评估
- `needs-info` — 等待报告者补充信息
- `ready-for-agent` — 已完全定义，可由 AFK agent 接手
- `ready-for-human` — 需要人工实现
- `wontfix` — 不会处理

每个经 triage 的 issue 应恰好携带一个分类角色和一个状态角色。如果状态角色冲突，先标记并询问维护者再做其他操作。

这些是规范角色名——issue tracker 中使用的实际标签字符串可能不同。映射应该已提供给你——如果没有，运行 `/jxx-setup-matt-pocock-skills`。

状态转换：未标记的 issue 通常先进入 `needs-triage`；然后移至 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。`needs-info` 在报告者回复后返回 `needs-triage`。维护者可随时覆盖——标记看起来异常的转换并在继续前询问。

## 调用

维护者调用 `/jxx-triage` 并用自然语言描述需求。解释请求并执行。示例：

- "给我看需要注意的事项"
- "看看 #42"
- "将 #42 移到 ready-for-agent"
- "有哪些是 agent 可以接手的？"

## 展示需要注意的事项

查询 issue tracker 并按最旧优先展示三个桶：

1. **未标记** — 从未 triage。
2. **`needs-triage`** — 评估进行中。
3. **`needs-info` 且报告者在上次 triage 备注后有活动** — 需要重新评估。

展示计数和每项的一行摘要。让维护者选择。

## triage 特定 issue

1. **收集上下文。** 阅读完整的 issue（正文、评论、标签、作者、日期）。解析之前的 triage 备注以免重复提问。使用项目的领域词汇表探索代码库，遵守相关区域的 ADR。对代码库运行两项检查：(a) **冗余性**——按领域概念（而非仅请求的措辞）搜索请求行为的已有实现，报告你查找了哪里。如果找到，则属于已实现的 `wontfix`（步骤 5）。(b) **先前拒绝**——阅读 `.out-of-scope/*.md`，展示与此请求相似的条目。

2. **推荐。** 向维护者说明你的分类和状态推荐及理由，加上与请求相关的简要代码库摘要——包括是否已实现。等待指示。

3. **验证声明。** 在 grill 之前，检查声明是否成立。对于 bug，按报告者的步骤复现。报告结果：已确认（附代码路径）、失败、或细节不足（强烈的 `needs-info` 信号）。经过确认的验证能产生更有力的 agent 简报。

4. **grill（如需要）。** 如果请求需要充实，同时运行 `/jxx-grilling` 和 `/jxx-domain-modeling` 技能——逐一 grill 使之成型，锐化领域术语，并在决策落定时内联更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent` — 发布 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`——与 agent 简报相同结构，但注明为何不能委托（判断决策、外部访问、设计决策、手动测试）。
   - `needs-info`——发布 triage 备注（模板如下）。
   - `wontfix`——关闭，评论取决于*原因*：
     - **已实现**——变更已存在于代码库中。指向其位置；**不要**写入 `.out-of-scope/`（该知识库用于*被拒绝*的请求，非已实现的）。
     - **拒绝（bug）**——礼貌说明，然后关闭。
     - **拒绝（enhancement）**——写入 `.out-of-scope/`，从评论中链接，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`——应用角色。如有部分进展可选择性评论。

## 快速状态覆盖

如果维护者说"将 #42 移到 ready-for-agent"，信任他们并直接应用角色。确认你即将执行的操作（角色变更、评论、关闭），然后执行。跳过 grill。如果在没有 grill 会话的情况下移至 `ready-for-agent`，询问是否要编写 agent 简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

将 grill 期间解决的所有内容记录在"established so far"下，以免工作丢失。问题必须具体且可操作，而非"请提供更多信息"。

## 恢复之前的会话

如果存在之前的 triage 备注，阅读它们，检查报告者是否已回答任何待决问题，并在继续前展示更新后的状况。不要重复已解决的问题。

## 反模式

- **跳过免责声明** — triage 期间写入 issue 的每条评论必须以 `> *This was generated by AI during triage.*` 开头。
- **忽略已有 triage 备注** — 不读之前的备注就重复提问。解析之前已解决的问题。
- **未标记状态冲突就行动** — 状态角色冲突时先标记并询问维护者，再做其他操作。
- **对 agent 已可用工单再做 triage** — `/jxx-to-tickets` 产出的工单已 ready-for-agent，不要再 triage。
- **对已实现请求写 .out-of-scope** — `.out-of-scope/` 用于被*拒绝*的请求，非已实现的（已实现的指向其位置）。

## 异常处理

| 场景 | 处理方式 |
|------|---------|
| issue tracker 未配置 | 提示先运行 `/jxx-setup-matt-pocock-skills` |
| 状态角色冲突 | 先标记并询问维护者，再继续 |
| 需要充实请求 | 并行运行 `/jxx-grilling` 与 `/jxx-domain-modeling`，锐化领域术语 |
| 冗余性检查发现已实现 | 属于已实现的 `wontfix`，指向其位置 |
