# 解决合并冲突

解决进行中的 git merge/rebase 冲突，以保留**双方意图**的方式。

## 流程

1. **查看 merge/rebase 的当前状态**。检查 git 历史和冲突文件。

2. **追溯每个冲突的原始来源**。深入理解每项变更的原因和原始意图。阅读 commit message，查看 PR，追溯原始 issue/ticket。

3. **逐 hunk（段）解决冲突。** 尽可能保留双方意图。若不兼容，选择符合合并既定目标的一方，并记录取舍。**不要**凭空创造新行为。始终解决冲突，绝不 `--abort`。

4. 发现项目的**自动化检查**并运行——通常是 typecheck，然后测试，然后格式化。修复合并导致的任何问题。

5. **完成 merge/rebase。** 暂存所有内容并 commit。若正在 rebase，继续 rebase 流程直到所有 commit 都完成。

## 反模式

- **凭空创造新行为** — 不基于任何一方的意图，自己发明第三种逻辑。
- **直接 `--abort`** — 放弃整个 merge/rebase。除非用户明确要求，否则始终解决冲突。
- **不读双方意图就合并** — 只看冲突文本不看 commit 背景，选了个看似可行实则错误的版本。
- **跳过自动化检查** — 解决冲突后不跑 typecheck / 测试 / 格式化，遗留合并引入的问题。

## 异常处理

| 场景 | 处理方式 |
|------|---------|
| 冲突双方意图不兼容 | 选符合合并既定目标的一方，记录取舍，不创造新行为 |
| 合并后测试失败 | 定位到冲突解决引入的回归，修复后重跑检查 |
| rebase 中途需停止 | 完成所有 commit 前不中途退出；如需中止需用户明确确认 |
| 用户误操作导致状态混乱 | 检查 git 状态确认现状，再决定继续解决还是回退 |
