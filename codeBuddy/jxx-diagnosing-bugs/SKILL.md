# 诊断 Bug

诊断棘手 bug 的纪律。仅在确有理由时跳过阶段。

探索代码库时，阅读 `CONTEXT.md`（如果存在）以建立相关模块的心智模型（mental model），并检查你涉及区域的 ADR。

## 脱敏（Redact）

本技能会让你展示命令、输出和捕获的产物。**先脱敏每一个机密**——在原位写 `<REDACTED>`。循环要基于环境变量构建，让凭证留在环境中，而不是出现在你展示的内容里。捕获的产物带有 auth 头：只引用携带信号的行。

如果脱敏后的输出不足以诊断 bug，明确说明并询问用户。

## 阶段 1 — 构建反馈循环（feedback loop）

**这就是本技能的全部。** 其他一切都是机械操作。如果你有一个针对此 bug 的**紧密**通过/失败信号——一个能在此 bug 上变红的——你就会找到原因；二分法、假设检验和插桩（instrumentation）都只是在利用它。如果没有，再怎么看代码也无济于事。

在此投入超常精力。**要激进。要有创意。绝不放弃。**

### 构建方式 — 大致按此顺序尝试

1. **会失败的测试** 在任何能触及 bug 的接缝（seam）处——单元、集成、e2e。
2. **Curl / HTTP 脚本** 对运行中的开发服务器。
3. **CLI 调用** 用 fixture 输入，将 stdout 与已知正确快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，断言 DOM/控制台/网络。
5. **重放捕获的 trace。** 将真实网络请求 / payload / 事件日志保存到磁盘；在隔离环境中沿代码路径重放。
6. **一次性测试桩。** 启动系统的最小子集（一个服务，mock 依赖），用单次函数调用执行 bug 代码路径。
7. **属性测试（property-based testing）/ 模糊测试（fuzz testing）循环。** 如果 bug 是"有时输出错误"，运行 1000 个随机输入寻找失败模式。
8. **二分测试桩。** 如果 bug 出现在两个已知状态之间（commit、数据集、版本），自动化"启动状态 X，检查，重复"以便 `git bisect run`。
9. **差分循环。** 将相同输入通过旧版本 vs 新版本（或两种配置）运行并 diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须有人点击，用 `scripts/hitl-loop.template.sh` 驱动他们，使循环仍有结构。捕获的输出反馈给你。

构建正确的反馈循环，bug 就修复了 90%。

### 收紧循环

把循环当作产品。一旦有了循环，**收紧**它：

- 我能让它更快吗？（缓存设置，跳过无关初始化，缩小测试范围。）
- 我能让信号更清晰吗？（断言具体症状，而非"没崩溃"。）
- 我能让它更确定吗？（固定时间，种子 RNG，隔离文件系统，冻结网络。）

30 秒的 flaky 循环比没有循环好不了多少；2 秒的确定性循环才是紧密的——一种调试超能力。

### 非确定性 bug

目标不是干净复现而是**更高复现率**。循环触发 100×，并行化，加压力，缩小时间窗口，注入 sleep。50% flake 的 bug 可调试；1% 不行——持续提高比率直到可调试。

### 当你确实无法构建循环时

停下来明确说明。列出你尝试了什么。向用户要：(a) 能复现它的任何环境的访问权限，(b) 脱敏后的捕获产物（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或 (c) 添加临时生产插桩的许可。**不要**在没有循环的情况下继续假设。

### 完成标准 — 一个能变红的紧密循环

阶段 1 在循环**紧密**且**能变红**时完成：你能说出**一个命令**——脚本路径、测试调用、curl——你已经**至少运行过一次**（展示调用及其输出，脱敏后），并且它：

- [ ] **能变红**——它驱动实际的 bug 代码路径并断言**用户描述的确切症状**，所以它能在此 bug 上变红，修复后变绿。不是"运行不报错"——它必须能*捕获这个特定 bug*。
- [ ] **确定性**——每次运行相同结论（flaky bug：固定的高复现率，如上所述）。
- [ ] **快速**——秒级，不是分钟级。
- [ ] **Agent 可运行**——你可以无人值守运行；人只在通过 `scripts/hitl-loop.template.sh` 时参与。

如果你发现自己在该命令存在之前就读代码构建理论，**停——直接跳到假设正是本技能要防止的错误做法。** 没有能变红的命令，就没有阶段 2。

## 阶段 2 — 复现 + 最小化

运行循环。看它变红——bug 出现了。

确认：

- [ ] 循环产生的是**用户**描述的失败模式——不是碰巧在附近的另一个失败。错误的 bug = 错误的修复。
- [ ] 失败在多次运行中可复现（或对于非确定性 bug，以足够高的比率可复现以供调试）。
- [ ] 你已捕获确切症状（错误消息、错误输出、慢时序），以便后续阶段验证修复确实解决了它。

### 最小化

一旦变红，将复现缩小到**仍然变红的最小场景**。逐一削减输入、调用者、配置、数据和步骤，每次削减后重新运行循环——只保留对复现失败不可或缺的。

为什么要费这个劲：最小复现在阶段 3 中缩小假设空间（更少的可变因素），并在阶段 5 中成为干净的 regression 测试。

当**每个剩余元素都不可或缺**时完成——移除任何一个都使循环变绿。

在你复现**且**最小化之前不要继续。

## 阶段 3 — 假设

在测试任何假设之前生成 **3–5 个排好序的假设**。单假设生成会锚定在第一个看似合理的想法上。

每个假设必须**可证伪（falsifiable）**：陈述它做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会使 bug 消失 / <改变 Z> 会使它恶化。"

如果你无法陈述预测，假设只是臆测——丢弃或细化它。

**在测试之前向用户展示排序列表。** 他们通常有能立即重新排序的领域知识（"我们刚部署了 #3 的变更"），或知道已排除的假设。低成本检查点，大幅节省时间。不要阻塞——如果用户不在就按你的排序继续。

## 阶段 4 — 插桩

每个探针必须对应阶段 3 中的特定预测。**一次改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查** 如果环境支持。一个断点胜过十条日志。
2. **目标日志** 在区分假设的边界处。
3. 绝不"记录一切然后 grep"。

**给每条调试日志打标签**，用唯一前缀，如 `[DEBUG-a4f2]`。清理只需一次 grep。未打标签的日志会残留；打标签的日志可清除。

**性能问题分支。** 对于性能 regression，日志通常是错的工具。替代方案：建立基线测量（计时工具、`performance.now()`、分析器、查询计划），然后二分。先测量，后修复。

## 阶段 5 — 修复 + regression 测试

在修复**之前**写 regression 测试 — 但仅当有**正确的接缝**时。

正确的接缝是测试在调用点执行**真实 bug 模式**的接缝。如果唯一可用的接缝太浅（bug 需要多调用者时只有单调用者测试、无法复现触发 bug 的链路的单元测试），在那里的 regression 测试只会带来虚假信心。

**如果没有正确的接缝，这本身就是重要发现。** 记录它。代码库架构阻止了 bug 被锁定。为下一阶段标记。

如果正确的接缝存在：

1. 将最小复现转为该接缝处的失败测试。
2. 看它失败。
3. 应用修复。
4. 看它通过。
5. 对原始（未最小化）场景重新运行阶段 1 反馈循环。

## 阶段 6 — 清理 + 复盘

声明完成之前必需：

- [ ] 原始复现不再复现（重新运行阶段 1 循环）
- [ ] regression 测试通过（或接缝缺失已记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 前缀）
- [ ] 一次性 prototype 已删除（或移至明确标记的调试位置）
- [ ] 被证明正确的假设陈述在 commit / PR 消息中 — 让下一个调试者学到

**然后问：什么本可以防止这个 bug？** 如果答案涉及架构变更（没有好的测试接缝、纠缠的调用者、隐藏的耦合），将具体信息交接给 `/jxx-improve-codebase-architecture` 技能。在修复到位**之后**而非之前给出推荐——你现在比开始时有更多信息。

## 反模式

- **没有循环就开始理论** — 在存在能变红的命令之前就读代码构建假设。先建循环。
- **单假设锚定** — 只生成一个假设就深入。先排序 3–5 个可证伪假设。
- **"记录一切然后 grep"** — 无差别日志堆砌。只在区分假设的边界处目标插桩，并打 `[DEBUG-xxx]` 标签。
- **不脱敏就展示** — 把凭证、auth 头原样贴出来。先 `<REDACTED>`。
- **过早下结论** — 未复现最小场景就断言根因。先复现 + 最小化。

## 异常处理

| 场景 | 处理方式 |
|------|---------|
| 无法构建反馈循环 | 停下说明，列出尝试过什么，向用户要环境访问权限 / 脱敏捕获产物 / 临时生产插桩许可 |
| 脱敏后输出不足以诊断 | 明确说明并询问用户 |
| 非确定性 bug | 目标是更高复现率，循环触发 100×、并行化、加压力，持续提高比率直到可调试 |
| 无正确接缝写 regression 测试 | 记录"代码库架构阻止了 bug 被锁定"，为下一阶段标记 |
