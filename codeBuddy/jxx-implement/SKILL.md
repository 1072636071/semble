实现用户在 spec 或工单中描述的工作。

尽可能在预先约定的接缝（seam）处使用 `/jxx-tdd`。

定期运行类型检查和单个测试文件，结束时运行完整测试套件。

## 完成步骤（不可跳过）

以下两步是实现的硬出口——不执行视为未完成：

- [ ] **代码审查**：调用 `/jxx-code-review` 审查所有变更。在审查通过前不得提交。
- [ ] **提交**：将工作 commit 到当前 branch。commit message 遵循 conventional commits 格式，body 说明变更原因。

### 审查发现问题时的处理流程

当 `/jxx-code-review` 返回的报告中存在发现项时，按以下步骤执行：

1. **禁止提交**：审查有发现项，不得执行提交步骤。
2. **输出审查报告**：将 `/jxx-code-review` 的输出原样呈现给用户，不做格式转换或摘要。
3. **用户决策**：在报告末尾追加选项：

```
请选择处理方式：
A. 修复审查发现的问题后重新审查
B. 无视问题，直接提交（需用户明确确认）
```

4. **选项 A — 修复**：逐项修复审查报告中的发现项，修复后重新执行 `/jxx-code-review`，重复此流程直到审查无发现项或用户选择 B。
5. **选项 B — 无视提交**：用户明确确认后，跳过审查要求直接提交。commit message 中注明"代码审查未通过，用户确认无视"。

## 反模式

- **审查有发现项仍提交** — 跳过硬出口，审查未通过就 commit。禁止提交。
- **不跑测试就收工** — 只实现不验证。结束时必须运行完整测试套件。
- **在非接缝处盲目写测试** — 未预先确认接缝就写测试。按 `/jxx-tdd` 先确认接缝。
- **提交时忽略审查报告** — 有发现项不呈现给用户就自行决定。必须原样输出审查报告并让用户决策。

## 异常处理

| 场景 | 处理方式 |
|------|---------|
| 审查报告有发现项 | 禁止提交，原样输出报告，让用户在"修复重审"与"无视提交"间选择 |
| 测试套件失败 | 定位并修复，重跑直到通过再提交 |
| 无可用 spec / 工单 | 基于用户描述实现，向用户确认关键决策 |
| commit message 不符合约定 | 用 conventional commits 格式，body 说明变更原因 |
