# 领域建模

在设计时主动构建和锐化项目的领域模型。这是*主动*纪律 — 挑战术语、发明边界场景、在术语确定时立即写下词汇表和决策。

仅仅*阅读* `CONTEXT.md` 获取词汇不是这个技能 — 那是任何技能都可以做的一行习惯。本技能用于**改变模型**，而非仅仅消费模型。

## 首次进入

1. 检查根目录是否存在 `CONTEXT.md` 或 `CONTEXT-MAP.md`
2. 若存在，读取现有词汇表，后续操作以此为基础
3. 若不存在，惰性创建（见「文件结构」）
4. 检查 `docs/adr/` 是否存在，了解已有架构决策

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，仓库有多个上下文。映射指向每个上下文所在的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文特定决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

按需创建文件 — 只在有东西要写时才创建。如果 `CONTEXT.md` 不存在，在第一个术语被确定时创建。如果 `docs/adr/` 不存在，在第一个 ADR 需要时创建。

**处理上下文间关系时**（上游/下游、双向依赖、共享内核、防腐层），参见 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 的「关系模式」表选用正确的模式与符号。典型场景：一个上下文向另一个发出事件（上游/下游）、两个上下文共享类型（双向依赖或共享内核）、某上下文需隔离外部系统模型（防腐层）。

## 核心循环

每次用户提及业务概念时，执行以下循环。当退出信号出现时自然收尾（见末尾）。

```
识别 → 质疑 → 压测 → 验证 → 记录
  ↑                               |
  └───────────────────────────────┘
```

关键原则：**每个概念有且仅有一个名字，每个名字有且仅有一个概念。**

### 识别

捕捉模糊、过载或未定义的术语。这是循环的入口 — 没有识别到问题就不进入后续步骤。

### 质疑

立即挑战，提出精确的规范术语。两种触发方式：

**对照词汇表质疑** — 当用户使用的术语与 `CONTEXT.md` 中的现有语言冲突时，立即指出：

> "你的词汇表将'取消'定义为整个订单取消，但你似乎指的是部分取消 — 是哪个？"

**锐化模糊语言** — 当用户使用模糊或过载的术语时，提出精确的规范术语：

> "'账户' — 你指的是客户（Customer）还是用户（User）？它们是不同的概念。"

### 压测

发明探测边界情况的场景，迫使用户精确界定概念之间的边界。

好的边界场景特征：

- 涉及两个概念的交界处
- 有明确的"应该属于 A 还是 B"的模糊性
- 能暴露隐含假设

示例：如果讨论"订单"和"退款"的关系，问："一个已发货但部分退款的订单，状态是'已完成'还是'部分退款'？"

### 验证

对照代码检查用户陈述是否一致。无代码库时跳过此步骤。

如果发现矛盾，揭示它：

> "你的代码取消整个订单，但你刚说部分取消是可能的 — 哪个是对的？"

检查方式：

- 搜索类型/接口定义，看命名是否与词汇表一致
- 检查枚举值，看状态是否覆盖了讨论的场景
- 查看数据库 schema，看关系是否与领域模型匹配
- 检查 API 端点命名，看是否与领域术语对齐

### 记录

术语确定后立即更新 `CONTEXT.md`，决策确定后按需创建 ADR。不要批量处理 — 即时捕获。

`CONTEXT.md` 应完全不含实现细节。不要将 `CONTEXT.md` 当作 spec、草稿本或实现决策的仓库。它是词汇表，仅此而已。格式参见 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

**术语演化** — 当已有术语定义需要变更时（而非首次定义）：

1. **标注变更** — 在 `CONTEXT.md` 中更新定义，必要时在术语旁加注变更说明
2. **评估影响面** — 确认代码中依赖旧定义的位置（类型名、变量名、条件分支），告知用户需同步修改的范围
3. **按需创建 ADR** — 如果术语变更反映了架构决策的转向，创建 ADR 记录原因
4. **清理同义词** — 如果规范名称本身变了，旧名称移入 `_避免_`（见反模式「一个概念多个名字」）

示例：原来"会员"定义为"付费用户"，现在需扩展为"拥有特定权益的用户（含付费和邀请获得）"：

> "会员定义从'付费用户'扩展到'拥有特定权益的用户' — 这意味着免费邀请用户也是会员。确认后我会更新 CONTEXT.md 并检查代码中 `isPaidMember` 等假设。"

**谨慎提供 ADR** — 仅当以下三个条件都为真时才提供创建 ADR：

1. **难以逆转** — 后来改变想法的成本不可忽略
2. **没有上下文会令人惊讶** — 未来的读者会想知道"他们为什么这样做？"
3. **真实权衡的结果** — 有真正的替代方案，你因特定原因选择了一个

如果三个中任何一个缺失，跳过 ADR。格式和完整示例参见 [ADR-FORMAT.md](./ADR-FORMAT.md)。

### 退出信号

以下信号表明领域建模会话可以自然收尾：

- 连续 2-3 个术语讨论未产生新的词汇表变更
- 用户的话题从"概念是什么"转向"怎么实现"
- 所有讨论的术语已在 `CONTEXT.md` 中有清晰定义且无冲突

退出时简要总结本次会话新增/变更的术语和决策。

## 反模式

避免以下常见错误：

- **把 CONTEXT.md 当 spec 或设计文档写** — 它是词汇表，仅此而已。不要写"订单应该支持部分退款"（功能规格），也不要写"订单存储在 Postgres 的 orders 表"（实现细节）。正确写法："**部分退款**：对已交付订单中部分行项目的退款，区别于全额退款。"
- **批量更新词汇表** — 术语确定后立即更新，不要攒着。延迟记录会导致后续讨论基于过时定义。
- **记录显而易见的决策** — "我们用 REST API" 不需要 ADR，除非有真实替代方案被否决。
- **忽略代码与模型的矛盾** — 发现代码与词汇表不一致时必须揭示，不能假装没看见。
- **一个概念多个名字** — 如果团队中有人用"客户"有人说"客户方"，必须选定一个，另一个列入 `_避免_`。
- **静默变更术语定义** — 修改已有术语定义时，必须告知用户变更内容和影响面，不能偷偷改。
- **过度建模** — 不要为通用编程概念（如"超时"、"重试"）创建术语条目，只记录项目特有的领域概念。

## 协作技能

- **grill-with-docs** — 通过 grill 会话打磨想法，过程中同步驱动领域建模
- **codebase-design** — 深模块（deep module）设计词汇，与领域模型互补
- **improve-codebase-architecture** — 改善代码库架构，依赖领域模型提供术语

其他技能调用本技能的方式：当任何技能在执行中遇到术语歧义或需要更新领域模型时，应暂停当前流程，调用本技能的会话行为（质疑、锐化、记录），然后继续。

## 异常处理

| 场景 | 处理方式 |
|------|---------|
| `CONTEXT.md` / `docs/adr/` 不存在 | 惰性创建——在第一个术语确定 / 第一个 ADR 需要时创建 |
| 代码与模型矛盾 | 揭示矛盾，让用户确认哪个是对的 |
| 无代码库可对照验证 | 跳过验证步骤，基于对话继续 |
| 术语定义需变更 | 标注变更 → 评估影响面 → 按需建 ADR → 清理同义词 |
| 多上下文仓库 | 读取 `CONTEXT-MAP.md`，定位各上下文位置 |
