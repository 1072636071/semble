# 设计两次

当用户想为选定的深化候选者探索替代接口时，使用此并行子 agent 模式。基于"设计两次"（Ousterhout）— 你的第一个想法不太可能是最好的。

使用 [SKILL.md](SKILL.md) 中的词汇 — **模块**、**接口**、**接缝**、**适配器**、**杠杆**。

## 流程

### 1. 框定问题空间

在启动子 agent 之前，为选定候选者写一个面向用户的问题空间说明：

- 任何新接口需要满足的约束
- 它的依赖，以及各自所属类别（见 [DEEPENING.md](DEEPENING.md)）
- 一个粗略的示意性代码草图来落实约束 — 不是提案，只是让约束具体化的手段

展示给用户，然后立即进入步骤 2。用户阅读思考的同时子 agent 并行工作。

### 2. 启动子 agent

用你所在 harness 的子 agent 机制并行启动 3+ 个子 agent。每个必须为深化模块产生一个**截然不同**的接口。

用独立的技术简报提示每个子 agent（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝（seam）后面是什么）。简报独立于步骤 1 中面向用户的问题空间说明。给每个 agent 不同的设计约束：

- Agent 1："最小化接口 — 目标最多 1–3 个入口点。最大化每个入口点的杠杆。"
- Agent 2："最大化灵活性 — 支持多种用例和扩展。"
- Agent 3："优化最常见的调用者 — 让默认情况变得简单。"
- Agent 4（如适用）："围绕端口与适配器设计跨接缝依赖。"

在简报中包含 [SKILL.md](SKILL.md) 词汇和 CONTEXT.md 词汇，使每个子 agent 的命名与架构语言和项目领域语言一致。

每个子 agent 输出：

1. 接口（类型、方法、参数 — 以及不变量、顺序、错误模式）
2. 使用示例，展示调用者如何使用
3. 实现在接缝后面隐藏了什么
4. 依赖策略和适配器（adapter）（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡 — 杠杆在哪里高，哪里薄

### 3. 呈现和比较

按顺序呈现设计，让用户消化每一个，然后用散文比较。按**深度**（接口处的杠杆）、**局部性**（变更集中在哪里）和**接缝位置**对比。

比较后给出你自己的推荐：你认为哪个设计最强以及为什么。如果不同设计的元素组合效果好，提出混合方案。要有立场 — 用户要的是明确判断，不是菜单。
